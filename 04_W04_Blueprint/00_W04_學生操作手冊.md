## 2. 先建立角色清單

從 Persona 和 CJM 推導所有會做事或產生互動的角色。角色不只包含人，也包含會主動顯示、接受輸入或改變服務狀態的設施。

至少檢查：

- 顧客／主要使用者
- 店員、客服或交付者
- 廚師、作業者或後台角色
- 老闆、管理者或決策者
- 看板、取餐櫃、KDS 等設施角色

先填研究工作表 B 節：

| 角色 | 從哪個 Persona／CJM 推導 | 工作事項 | 責任邊界 | 來源 |
|---|---|---|---|---|
| | | | 不負責什麼 | |

「系統」不是角色。若要寫系統，改問：哪一個具體角色或設施執行了什麼動作？

## 3. Step 1：把 CJM 前台接到 Blueprint

逐一讀取 `03_cjm.md` 的階段與前台行動，填入研究工作表 A 節：

| CJM 階段 | 前台行為 | 後台需要做什麼 | 誰來做 | 支援需求 |
|---|---|---|---|---|
| | 顧客看到／做什麼 | 角色＋動作 | 人或設施 | 還缺什麼支撐 |

後台行為用「角色＋動作」，例如：

```text
店員確認訂單內容
廚師安排製作順序
店員確認餐點備妥並放入取餐櫃
看板顯示已確認可取餐號碼
```

不要寫：

```text
建立訂單 API
使用資料庫同步
呼叫通知服務
```

## 4. Step 2：描述責任邊界

每個角色要回答三件事：

1. 他負責完成什麼？
2. 他明確不負責什麼？
3. 完成後交給誰、交付什麼？

例如：

```text
廚師：負責完成餐點並回報完成；不負責決定顧客是否可取餐；交給店員確認備妥。
店員：負責確認餐點已可交付、放入櫃位並讓顧客知道；不負責修改已開始製作的餐點。
```

這一步是避免「廚師完成」被誤當成「顧客可以取餐」的關鍵。

- 交接方式
- 失敗後果

| 交接 ID | 從誰 → 到誰 | 交接內容 | 成功條件 | 失敗風險 | 例外處理 |
|---|---|---|---|---|---|

交接成功條件要可觀察，例如「店員知道哪一張訂單已完成」，不要只寫「順利完成」。

## 6. Step 4：提出服務方案選項

對每個需要選擇的服務需求建立穩定代碼 `SD-01`～`SD-11`。本週只做候選，不填最後採用方案。

每項至少列 A／B／C 或合理的候選數，並填：

- 優點
- 缺點
- 適合條件
- 可能影響的角色、物件與交接
- 建議方向（建議不是定案）
- 分析來源

例如：

| 代碼 | 服務需求 | 選項 | 優點 | 缺點 | 適合條件 |
|---|---|---|---|---|---|
| SD-01 | 訂單如何被接收 | A 人工確認／B 規則通知／C 未來 AI | | | |

禁止在這裡寫「已採用」。最後定案在 W5 的 `07_decisions.md`。

## 8. Step 6：畫可見線與內部互動線

在 `04_blueprint.md` 中保留三層：

```text
前台行為：顧客看到或直接參與的行動
──────────── 可見線 ────────────
後台行為：角色執行但顧客通常看不到的工作
────────── 內部互動線 ──────────
支援需求：支撐前台與後台的業務需求
```

判斷方式：

- 顧客能直接看到或感受到的，放前台。
- 服務人員為交付服務而做的，放後台。
- 讓角色能完成工作的條件、資訊或設施，放支援需求。

## 9. Step 7：補物件與任務句種子

本週先在 Blueprint 的物件清單列出從「對象」欄看到的候選物件，例如訂單、餐點、菜單品項、取餐號碼。只需標記候選，不做完整生命週期。

再把角色工作事項改寫成業務任務句種子：

```text
前置業務狀態 → 角色做業務動作 → 物件狀態改變 → 下一個角色做決策 → 時效
```

不要使用：頁面、畫面、按鈕、按下、輸入框、API、資料庫。
