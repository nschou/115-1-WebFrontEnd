## 1. 模組定位

### 1.1 這一週做什麼、不做什麼

| 做 | 不做 |
|---|---|
| 將 CJM 痛點與 Blueprint 角色任務整合成**服務需求索引** | 直接從 CJM 或喜好猜頁面 |
| 先寫無畫面的 **US-B**，確認角色價值 | 把 US-B 寫成按鈕或畫面功能 |
| 從任務與物件推導元素、資訊規格、狀態與線框 | 先開編輯器再回頭補元素來源 |
| 由線框與狀態形成 **US-I ＋ AC** | 在沒有狀態時先寫具體 AC |
| 走查規則層與體驗層，交給 W7 彙整 `spec.md` | 在 `spec.md` 第一次設計需求或畫面 |


W5 定義視覺語言；W6 先定義服務需求，再把價值變成可走、可驗的行為結構。

### 1.2 三個名詞先分清楚

多數人把這三個詞混著用，導致「畫了線框就以為做完 UX」。它們其實是三種東西：

| 名詞 | 是什麼 | 在哪一層 | 本週角色 |
|---|---|---|---|
| **UX** | 結構與行為：有哪些頁、每頁做什麼、出錯怎麼辦 | 行為層 | **主角** |
| **UI** | 視覺：顏色、字級、間距、元件長相 | 視覺層 | 已在 `DESIGN.md` 完成 |
| **Wireframe** | 上面兩者的**呈現格式**（灰階版面） | 不是層，是視圖 | 驗證工具 |

> 所以「第 6 週做 UX/UI 設計」這個說法是**錯的**：UI 已經做完了，線框也不是階段。
> 正確說法：**第 6 週做 UX 設計，線框是它的其中一個交付視圖。**

### 1.3 五層定位

```
服務層   baseline          誰、在什麼階段、要什麼感受        ← 第 2–5 週
UX 層    本週               有哪些線框、每頁做什麼、什麼狀態   ← 你現在在這裡
視覺層   DESIGN.md          同一個元件長什麼樣                ← 第 5 週
契約層   `spec.md`            W2–W6 證據的業務彙整與驗收契約       ← 第 7 週
實作層   `plan.md`／程式碼    用什麼技術做                      ← 第 8 週起
```

### 1.4 本週產出

這六項是**你要交的**。左半是「空白範本」，右半是「本案填好的示範答案」——
範本用來動手，示範答案用來對照「做到完整長什麼樣」。**不要照抄示範答案**：你的 baseline 不同，產出必然不同。

| # | 產出 | 格式 | 對應章 | 空白範本 | 本案示範答案 |
|---|---|---|---|---|---|
| 1 | 服務需求索引＋US-B | Markdown | §2、§8 | `11_service-requirements.md`、`13_UserStory-B.md` | `98_示範案例/雲端早餐店/11_service-requirements.md` |
| 2 | `15_UX.md` | Markdown | §4–§7 | `15_UX/15_UX_template.md` | `98_示範案例/雲端早餐店/15_UX.md` |

| 5 | 遠距顯示與走查 | Markdown／原型 | §10 | `validation/` | `06_W06_UX/validation/` |

**怎麼用示範答案（三種正確用法）**

1. **對照完整度**：你的 UX.md 有沒有這六章？ST 表有沒有六欄？
2. **對照語氣**：MSG 是「指出怎麼修」還是「你錯了」？
3. **對照顆粒度**：AC 是不是每條都對到一個狀態？

## 1.6 這一節的推導，是修出來的

在講 UX 之前，先誠實說一件事：**我們這一節的流程，是改了八次才成形的。**

這不是教材沒寫好，而是這門課真正要教的能力——**當某個東西推導不出來時，找出是哪一層的表述錯了**。

### 八個回合（每一次都是「推不下去」逼出來的）

| 回合 | 撞到什麼 | 修正 |
|---|---|---|
| 1 物件 | 要回答「菜單該長什麼樣」，發現沒有文件在管「物件」 | 把 Blueprint 的「對象」升級成物件（OBJ） |
| 2 資訊流 | 物件模型答不出時序、傳播、競爭 | 補動態原型與時效需求 |
| 3 決策依據 | 「為什麼要圖片上傳」答不出來 | 依據＝人的需求 ＋ **物的本質** |
| 4 可驗 | 「打開來看，驗證在哪裡？」 | 可點 → 可查 → **可驗**（斷言＋負向測試） |
| 5 兩層 | 23 條全綠，但沒人用過 | 規則層 ＋ **體驗層** |
| 6 任務句 | 任務句裡寫了「按下按鈕」 | 七格文法 ＋ **禁用介面詞** ＋ 店長測試 |
| 7 設施 | 設施被當成憑空出現的執行者 | 設施＝**角色替代**，驗收基準＝被替代的那段互動 |
| 8 US 位置 | 先寫故事對不上畫面，先畫線框沒有任務支撐 | **US 出現兩次**（US-B／US-I）＋ SCR 三件套 |

> 完整過程（含每回合的原本想法、撞牆點、教訓）見 `18_推導修正的思考軌跡.md`。

### 修正只有三種類型

| 類型 | 症狀 | 例子 |
|---|---|---|
| **補漏** | 要素完全沒有住的地方 | 物件、資訊流、體驗層 |
| **換層** | 東西放錯樓層（把結果當需求） | 任務句混進 UI |
| **改序** | 順序錯導致推導對不上 | US 只出現一次 |

**不是這三種就不要改。** 這條能擋掉「憑感覺想改」。

### 回滾的紀律

| 規則 | 內容 |
|---|---|
| 觸發條件 | 只有「某個要素推導不出來」才回滾，不是「覺得不好」 |
| 最小單位 | 只回滾出問題的那一層，不動上游與無關下游 |
| 必留紀錄 | 背景／選項／決定／代價／影響範圍／怎麼回滾 |
| 舊版凍結 | 不刪舊版，標記凍結，讓人看得到演化 |
| 可檢查 | 修正後要能被 lint，否則只是換了說法 |

### 為什麼這是正常現象，不是教材不穩

| 現實理由 | 說明 |
|---|---|
| 表述精度會隨理解提高 | 一開始只知道「要做點餐」，做一半才知道「菜單需要照片」——這是需求具體化，不是需求變更 |
| 下游會暴露上游的錯 | 畫線框才發現任務寫不出狀態轉換；做驗證才發現 AC 沒有來源 |
| 不改的代價更大 | 硬做完，上線才發現「這一頁沒有人需要」 |

```
錯誤不會自己消失，只會被後面的層包起來。
```

> **改，不是因為之前的錯；是因為我們現在有能力看見它錯在哪。**
> 一套不能被檢查出錯的方法，比抓錯一百次更危險。

## 1.7 每次修正留一頁：ADR（決策紀錄）

§1.6 講了「我們改了八次」。但**改了要留下痕跡**，否則三個月後沒有人知道為什麼。

### 1.7.1 ADR 是什麼

> **ADR（Architecture Decision Record）＝ 一頁紀錄，回答「為什麼這樣決定、考慮過什麼、代價是什麼、怎麼回頭」。**

它記錄**決策**，不是記錄**進度**。兩者差別：

| | CHANGELOG | ADR |
|---|---|---|
| 回答 | 改了什麼 | **為什麼不是別的** |
| 生命週期 | 只增不改 | 被**取代**，但永不刪除 |
| 讀者 | 想知道版本差異的人 | 三個月後的自己 |

### 1.7.2 誰提出、誰核准、誰受影響

**這三個角色必須分開寫**，否則 ADR 會變成「有權力的人的想法」。

| 角色 | 職責 | 本案 |
|---|---|---|
| **提出者** | 發現問題、寫下選項與代價 | **任何人都可以**——工程師、設計師、PM、學生、AI。提出者不必有決定權 |
| **決策者** | 選一個選項並負責 | 有權決定的人（本案：課程教師；業界：tech lead／架構師／PO） |
| **受影響者** | 會因此改變工作的人 | 修課學生、助教、後續維護者 |

> **為什麼提出者不必是決策者**：工程師最常先看到問題（例如「這個任務句推不出 AC」），但他沒有權決定要不要回滾。ADR 讓他把問題**連同選項與代價**交給決策者，而不是只丟一句「我覺得要改」。

「ADR 由誰提出」的背景也決定了它的可信度：

| 提出者 | 業界常見情境 |
|---|---|
| 架構師／tech lead | 技術選型（資料庫、框架、雲端服務） |
| 工程師 | 重構、模組邊界、命名與目錄結構 |
| 設計師／PM | 流程、狀態模型、責任邊界 |
| **學生** | 課程專案的表述修正、狀態機調整 |

### 1.7.3 什麼時候要寫（三條任一成立就寫）

| # | 條件 | 例子 |
|---|---|---|
| 1 | **影響結構** | 改任務句格式、改頁面拆分依據、改狀態機 |
| 2 | **有替代方案** | 「任務句要五格還是七格」 |
| 3 | **日後會被問「為什麼」** | 「為什麼設施要標 substitutes」 |

**不寫的情況**：改錯字、修 bug、調樣式、換圖——這些進 CHANGELOG 就好。

### 1.7.4 一則 ADR 的八個欄位

| 欄位 | 寫什麼 |
|---|---|
| 狀態 | 提案中／已採用／被 ADR-00x 取代 |
| 提出者／決策者／受影響者 | 三個角色分開寫 |
| 背景 | 什麼東西**推導不出來**（附證據） |
| 驅動因素 | 依據（來源：哪份文件、哪條規則） |
| 考慮過的選項 | A／B／C，每個都要寫「為什麼不選」 |
| 決定 | 選了什麼，一句話 |
| 影響範圍 | **要改什麼，也要寫「不受影響的」** |
| 代價／如何回滾／驗證方式 | 錯了怎麼退、怎麼知道這次是對的 |

完整範例見 `adr/ADR-001_任務表述層升級.md`；空白格式見 `adr/000_範本.md`。

### 1.7.5 學生要交什麼

| # | 每組每學期至少 3 則 ADR |
|---|---|
| 1 | **一則自己做的決定**（例：為什麼把某兩頁合併） |
| 2 | **一則被推翻的決定**（記錄「原本怎麼想、後來為什麼變」） |
| 3 | **一則回滾**（記錄「哪一層出問題、只回滾到哪裡」） |

### 1.7.6 四個常見錯誤

| 錯誤 | 為什麼不行 |
|---|---|
| 寫成工作日誌 | ADR 只記決策，不記進度 |
| 只寫結論，不寫選項 | 沒有「為什麼不選 B」，三個月後無法判斷是否該推翻 |
| 不敢寫代價 | 沒有代價的決定，通常是沒想清楚 |
| 刪掉舊 ADR | 決策演化史被抹除，下次會重犯 |

## 2. 為什麼 UX 從 Service Blueprint 切入

### 2.1 一個被推翻的假設

原本的設計是：**CJM（顧客旅程）→ 數位接觸點 → 頁面清單 → 線框**。

實際跑出來的結果：

| 來源 | 產出 | 問題 |
|---|---|---|
| CJM 的 7 個數位接觸點 | 首頁、菜單、點餐確認、結帳、訂單狀態、取餐通知、店內看板 | **全部是顧客端** |
| 店員端 | **0 頁** | 但 Blueprint 後台明明有「接單／確認／入櫃／收款」 |
| 廚房端 | **0 頁** | 但「排製作順序／回報進度」是廚師在做 |

**這不是執行疏漏，是根源選錯。**
CJM 描述「顧客的體驗序列」，它天生只有一條線；用它推整個系統的介面，等於用「體驗的長度」推「系統的寬度」。

### 2.2 三個論證

**論證 1｜UX 的最小單位是「任務在一個介面上被完成」**
CJM 回答「顧客感受到什麼」；Blueprint 回答「**誰必須做什麼、交給誰**」。體驗是連續的，任務是可切分的；介面只能照可切分的單位切。

**論證 2｜介面數量 ＝ 角色任務的聯集，≠ 顧客旅程的長度**

| 來源 | 幾條線 | 能推出的介面 |
|---|---|---|
| CJM | 1 條（顧客） | 只有顧客端 |
| Blueprint | N 條（每個角色一條） | 顧客 ＋ 店員 ＋ 廚房 ＋ 設施 |

**論證 3（決定性）｜設施角色有任務，但沒有旅程**
「取餐櫃通知顧客號碼」「看板顯示進度」——它們會執行動作、會與顧客互動，是介面。
但它們沒有 Persona、沒有情緒、沒有旅程階段，**CJM 永遠生不出「看板」這個介面**。

> 只要系統裡有一個非人的角色，CJM 就不足以當 UX 的根源。
> 而本案的商業模式（數位複合連鎖）本來就依賴數位設施，所以這不是特例，是常態。

### 2.3 主從關係：不是二選一，是把主從倒過來

| 問題 | 由誰回答 |
|---|---|
| 有哪些介面？ | **Blueprint**（角色 × 任務） |
| 每個介面屬於哪一端？ | **Blueprint**（可見線／內部互動線） |
| 每頁要做完什麼？ | **Blueprint**（動作 ＋ 受詞） |
| 介面之間怎麼串？ | **Blueprint**（5 個 handoff） |
| 會出什麼錯？ | **Blueprint**（4 個例外） |
| **先做哪一個？** | **CJM**（情緒曲線 −2） |
| **用什麼語氣？** | **CJM ＋ Persona** |
| 版面多密？什麼裝置？ | **Persona**（通勤、單手、戶外） |

**一句話**：Blueprint 決定「有哪些介面、每個介面做什麼」；CJM 決定「先做哪個、用什麼話說」。
CJM 沒有被淘汰，它從「主要輸入」降為「兩個特定問題的答案來源」。

### 2.4 兩個新發現（這一節是本週的轉折）

**發現 1｜設施介面要獨立設計**

| | 手機 | 看板／KDS |
|---|---|---|
| 觀看距離 | 30–40 cm | **1.5–5 m** |
| 輸入 | 觸控 | 看板無輸入 |
| 環境 | 一般 | 強光、油煙 |
| 資訊量 | 可捲動 | **一屏定生死** |

**發現 2｜主 Design.md 缺一整層「遠距顯示」**
它只有 web breakpoints 與 16px 內文，沒有遠距字級、強光對比、1920×1080 佈局。
→ 對策：**另立 `DESIGN-DISPLAY.md`**（見 `03_遠距顯示_獨立Designmd規格與Prompt.md`）。

> 這兩個發現證明：**選對根源，會逼出真實缺口**，而不是只換一個說法。

## 3. 上游盤點：從角色任務到線框

### 3.1 輸入清單

| 輸入 | 從哪來 | 用來做什麼 |
|---|---|---|
| 角色表（含設施角色） | baseline §五 | 誰要做什麼 |
| 服務藍圖（含 5 handoff、4 例外） | baseline §八 | 任務、端別、錯誤 |
| 11 項決策 | baseline §六 | 哪些功能存在（例：會員不做 → 沒有登入頁） |
| CJM 情緒曲線 | baseline §七 | 只決定**優先序** |
| DESIGN.md / DESIGN-DISPLAY.md | 第 5 週 ＋ 本週 | token、限制、遠距尺度 |

### 3.2 角色任務盤點（第一步，動手抄）

把 Blueprint 的後台動作**逐條原文照抄**，不要改寫、不要合併。範例：

| # | 角色 | 動作（原文） | 對象 | 線的位置 | 端別 |
|---|---|---|---|---|---|
| 1 | 店員 | 接收訂單並確認內容 | 訂單 | 兩線之間 | 店員 |
| 2 | 店員 | 通知廚師製作 | 訂單 | 兩線之間 | 店員 |
| 3 | 廚師 | 安排製作順序 | 訂單 | 兩線之間 | 廚房 |
| 4 | 廚師 | 回報製作進度 | 訂單狀態 | 兩線之間 | 廚房 |
| 5 | 店員 | 確認進度、通知顧客 | 顧客 | 兩線之間 | 店員 |
| 6 | 店員 | 放置餐點至取餐櫃 | 餐點 | 兩線之間 | 店員 |
| 7 | 店員 | 收錢 | 訂單 | 兩線之間 | 店員 |
| 8 | 取餐櫃 | 通知顧客取餐號碼 | 顧客 | **可見線上** | 設施 |

> 「原文照抄」很重要：一旦開始改寫（「店員接收訂單」→「接單功能」），
> 後台動作就變成功能名稱，覆蓋率就算不出來了。

### 3.3 端別切分（用兩條線）

| 線 | 以上 | 以下 |
|---|---|---|
| 可見線 | 顧客端（手機） | 店員／廚房端 |
| 內部互動線 | 店員／廚房端（平板、KDS） | 支援系統（通常無介面） |

**四個端別**：顧客／店員／廚房／設施。少一個就是沒盤點完。

### 3.4 人工 vs 系統自動（決定覆蓋率怎麼算）

| 類型 | 定義 | 落點 |
|---|---|---|
| **人工作業** | 需要有人判斷或輸入 | 必須有 SCR 承接（**覆蓋率 100%**） |
| **系統自動** | 由某項決策指定自動執行 | 記在系統行為清單，交 `spec.md` |
| **無介面** | SOP、實體流程 | 不在 UX 範圍（但要說明） |

本案實例：

| 動作 | 類型 | 落點 |
|---|---|---|
| 店員通知廚師製作 | 系統自動（決策 2：KDS 路由） | spec |
| 店員通知顧客進度 | 系統自動（推播）＋人工觸發 | SCR-06 → spec |
| 生成取餐號碼 | 系統自動 | spec |
| 老闆記錄銷售 | 系統自動（POS） | spec |
| 店員維護環境清潔 | 無介面（SOP） | 不在範圍 |

> **不這樣分，學生會為了湊 100% 而替自動化動作硬造頁面**——那是「AI 味介面」的來源之一。

> **先備知識**：任務句七格（前置業務狀態／A／業務動作／物件／狀態轉換／B／B 的決策）見「第 5 週 §3.8」。本節從「任務句已寫好」開始。

### 3.5 資訊元素：線框的來源

> **名詞先統一**（ADR-003）：
> - **資訊規格**、**線框（wireframe）**、**tokens** 是三個可獨立產出的**元件**；
> - **SCR-xx（螢幕／介面單元）＝ 資訊規格 ＋ 線框 ＋ 樣式（tokens）**，三者同一編號、同一資料夾；
> - 所以 **SCR 不是設計的起點，是套用公式後自然產生的產物**——「線框」只是它的零件之一，不要用零件名稱去稱呼整個單元。

**先修正一個很容易犯的錯**：不是「從任務切線框」，而是「從任務**長出元素**，元素聚成群，才形成線框」。

| | 錯的做法 | 對的做法 |
|---|---|---|
| 起點 | 任務 | 任務 |
| 中間 | **（跳過）** | **資訊元素** |
| 結果 | 一個編號 | 元素群 → 線框 → 才給編號 |

> 頁面不是設計的對象，是**設計的結果**。它是元素聚夠了以後，我們給它的一個名字。

#### 3.5.1 資訊元素的定義

> **資訊元素 ＝ 支撐一次決策所需的「最小資訊單位」。**

不是「一個欄位」，也不是「一個按鈕」，而是「使用者為了做某個判斷，必須看到或給出的一件事」。

三種**功能類型**（先分這個，再談型態）：

| 類型 | 意思 | 例 |
|---|---|---|
| **顯示** | 使用者要讀它才能判斷 | 合計、品項清單、取餐號碼 |
| **輸入** | 使用者要給它才能繼續 | 取餐時段、顧客姓名 |
| **操作** | 使用者要按它才能推進 | 送出訂單、前往付款 |

> **順序很重要**：先決定它是「顯示／輸入／操作」，再決定「用什麼元件」。反過來就會變成「先想按鈕」。

#### 3.5.2 元素表（十一欄，缺一不可）

| 欄位 | 回答 | 誰要填 |
|---|---|---|
| 元素 | 叫什麼 | 全部 |
| **用途** | 它幫使用者回答哪個問題 | 全部 |
| **資料來源** | 哪個物件的哪個屬性（OBJ-xx.欄位） | 全部 |
| **功能類型** | 顯示／輸入／操作 | 全部 |
| 建議型態 | 文字、按鈕、下拉、加減器… | 全部 |
| **型態依據** | 為什麼用這個型態（不是美感） | 全部 |
| **歸屬視圖** | 哪個角色、哪個任務要看它 | 全部 |
| **狀態改變** | 哪個物件、從什麼變成什麼 | **只有操作** |
| **去處** | 留在原地／前往哪個線框／離開系統 | **只有操作** |
| **回饋** | 成功時看到什麼 | **只有操作** |
| **失敗去處** | 失敗時停在哪個狀態 | **只有操作** |

> 操作元素的最後四欄，是這一節最重要的設計工作——**沒有它們，按鈕只是一個方框**。

#### 3.5.3 五步產生法

| 步 | 做什麼 | 依據 |
|---|---|---|
| 1 | 從任務句的 **B 的決策** 出發：他需要知道什麼才能決定？ | 任務句第 7 格 |
| 2 | 從任務句的 **z（物件）** 找屬性：哪些屬性能回答那些問題？ | 物件模型（角色 × 物件 × 需求） |
| 3 | 每個屬性 → 一到多個元素；標上功能類型 | 顯示／輸入／操作 |
| 4 | 為輸入與操作元素定「建議型態」與「型態依據」 | 選項數、數值範圍、決策重要性 |
| 5 | 標註歸屬視圖（可能一個元素跨多個視圖） | 視圖矩陣 |

#### 3.5.4 從元素到線框：顯示／輸入是節點，操作是邊

| 元素類型 | 在結構裡的角色 | 後果 |
|---|---|---|
| 顯示／輸入 | **節點**（留在同一線框內） | 不產生新的線框 |
| **操作** | **邊**（把人送到別處，或改變狀態） | **終點不存在，就要新增線框** |

> **線框不是被「切」出來的，是被「走」出來的。**
> 使用者每按一次，就必須有地方去；那個地方不存在，就得生一個線框。

**線框的三個來源**

| # | 來源 | 例 |
|---|---|---|
| ① | 元素群聚（同上下文、≤5–7 個） | 6 個元素聚成 SCR-03 |
| ② | **邊的終點** | E-16 送出訂單 → 要去付款 → SCR-04 必須存在 |
| ③ | 例外（錯誤／空／逾時） | 付款失敗留在原線框的 error 態；逾時則自動返回 |

**步驟**

| 步 | 做什麼 | 依據 |
|---|---|---|
| 1 | 元素依**決策順序**排序 | 使用者第一個要判斷什麼，放最上面 |
| 2 | 分群：同上下文、≤5–7 個元素 | 認知負荷 |
| 3 | 每群選容器（頁面／分步／彈窗／區塊） | §5 的四種容器 |
| 4 | **逐一檢查每個操作元素：它的「去處」存在嗎？** | 不存在 → 新增線框或標為狀態 |
| 5 | 畫成線框（HTML ＋ tokens） | 元素 ＋ 順序 ＋ 容器 |
| 6 | **此時才給編號 SCR-xx** | 群與邊都成形了 |

**例子：E-16 送出訂單的完整後果**

| 欄位 | 內容 |
|---|---|
| 狀態改變 | 訂單 S1 草稿 → S2 已下單 |
| 去處 | **前往 SCR-04 結帳**（所以 SCR-04 必須存在） |
| 回饋 | success 態 0.5 秒後前進 |
| 失敗去處 | 留在 SCR-03 的 **error 態**（錯誤指到欄位，不跳頁） |

**不是所有線框都靠點擊進入**——這一點要特別教：

| 入口類型 | 例 |
|---|---|
| 介面入口（有邊指過來） | SCR-04 由「前往付款」進入 |
| **非介面入口** | 店員台／KDS（開店常駐）、取餐櫃面板（顧客走到櫃檯）、報表與菜單維護（後台登入）、看板（常駐設施） |

> 每條「非介面入口」都要寫理由；寫不出的，就是孤兒線框。

> **線框的排列順序不是美感，是決策順序。** 這也是「為什麼取餐時段放最上面」的唯一依據。

#### 3.5.5 完整例子：T-02（顧客提出訂單）→ SCR-03

任務句：當顧客已決定餐點內容，顧客向店家提出訂單（S1→S2），店員接收，據以判斷「現在做還是排隊」。

**視圖**：顧客的「提出訂單」面（B 是店員，這一面是 A 的操作面）。

| 元素 | 用途 | 資料來源 | 功能類型 | 建議型態 | 型態依據 |
|---|---|---|---|---|---|
| 取餐時段 | 決定幾點拿 | 訂單.pickup_slot | 輸入 | 下拉 | 固定 4–6 個選項，要全部看到 |
| 品項清單 | 確認點了什麼 | 購物車.items | 顯示 | 清單 | 需逐項核對 |
| 客製備註 | 記住偏好 | 購物車.remark | 顯示（唯讀） | 小字 | 次要資訊 |
| 合計 | 判斷值不值得 | 訂單.total | 顯示 | 大字 | 決策關鍵數字 |
| 顧客姓名 | 叫號辨識 | 訂單.customer_name | 輸入 | 文字框 | 自由輸入 |
| 送出 | 提出訂單 | — | 操作 | 主按鈕 | T-02 的唯一觸發點 |

**決策順序**：取餐時段（主決策）→ 品項與合計（確認）→ 姓名（辨識）→ 送出。
**分群**：6 個元素、同一上下文（一次下單確認）→ 一頁 → **此時才叫 SCR-03**。

#### 3.5.6 可檢查的七條

| # | 檢查 | 抓什麼 |
|---|---|---|
| 1 | 每個元素都有用途、資料來源、功能類型 | 有欄位卻說不出用途 |
| 2 | 每個元素至少歸屬一個視圖 | 元素孤兒 |
| 3 | 每群元素 ≤7 | 一頁塞太多 |
| 4 | 每個「操作」元素都回指一個任務句 | 按鈕沒有出處 |
| 5 | **每個操作元素都有狀態改變、去處、回饋、失敗去處** | 按了不知道會怎樣的按鈕 |
| 6 | **每個線框至少有一條進來的邊，或標明非介面入口** | 孤兒線框（沒有任何操作能走到它） |
| 7 | **元素的「去處／狀態改變」要與動作定義一致** | 設計與實作漂移 |

#### 3.5.7 推展流程：把線框「推」出來，不是「畫」出來

前面講的是原則。實際跑一遍的順序是：

| 步 | 做什麼 | 產出 |
|---|---|---|
| 1 | 任務句（七格） | `tasks.js` |
| 2 | 從 B 的決策與物件屬性長出元素 | `elements.js` |
| 3 | 元素依決策順序排、聚成群（≤7） | 各線框的元素群 |
| 4 | 檢查每個操作元素的「去處」是否存在 | 不夠就新增線框 |
| 5 | 檢查每個線框有沒有入口（介面邊或非介面入口） | 孤兒線框清單 |
| 6 | 給編號 SCR-xx、畫線框、套 tokens | 線框本體 |

**這一步可以執行**，不是純文字：

```
node derive-wires.mjs   # 從任務句＋元素重新推出線框，輸出 21_WIRE推展表.md
```

它會檢查四件事：

| 檢查 | 抓什麼 |
|---|---|
| 每頁元素 ≤7 | 一頁塞太多 |
| **每頁至少一個顯示元素** | **空線框**（只有按鈕、沒有資訊） |
| 每個操作元素都有任務 | 按鈕沒有業務目的 |
| 每個線框都有入口 | 孤兒線框 |

**本課程實際跑一次的結果**：推出 **11 個線框、53 個元素**，與現有畫面一致（11 → 11）。
過程中抓到一個真問題：**取餐櫃面板只有輸入與按鈕，沒有任何「顯示」元素**——
顧客按了第幾位、有沒有按錯，畫面上沒有東西告訴他。補上「已輸入號碼」後才通過。

> 這就是「推展」的價值：它會告訴你「少了一個元素」，而畫圖不會。

---
#### 3.5.8 版面順序：不是美感，是決策順序

元素有了順序，線框才有依據。這一步也可以執行：

```
node check-layout-order.mjs   # 比對「宣告的決策順序」與「畫面實際出現順序」
```

### 怎麼定順序

| 問法 | 例 |
|---|---|
| 使用者第一個要判斷什麼？ | SCR-05：先知道「幾點可以拿」，再看進度 → 預計時間在進度之前 |
| 哪些是「並列的選項」？ | SCR-09：掃碼與鍵盤是替代方案，應並列，不能把替代方案放在確認之後 |
| 哪個是「最後的承諾動作」？ | 送出訂單、確認開櫃、儲存變更——永遠最後 |

### 這一輪抓到的兩個問題

| # | 問題 | 處理 |
|---|---|---|
| 1 | SCR-05 把「進度條」放在「預計時間」前面——但顧客最想知道的是幾點能拿 | 調整順序資料（預計時間 → 進度） |
| 2 | SCR-09 把「掃碼」放在數字鍵盤**之後**——替代方案太晚出現 | **改版面**：掃碼移到鍵盤之前 |

### 順帶發現的模型缺口：全局常駐元件

加上「購物車小計」後，SCR-02 變成 8 個元素，撞上 ≤7 上限。追下去發現：

> **購物車條是跨頁常駐元件，不屬於任何一頁的元素群。**

所以在元素上加 `scope: "global"`，它仍要定義、仍要驗收，但**不計入單頁的元素群上限**。
常見的全局元件還有：導覽列、通知橫幅、離線提示。

---
#### 3.5.9 怎麼「定位」一個元素（以及一個真實的坑）

要比較順序，得先知道「這個元素在畫面的哪裡」。兩種定位方式：

| 方式 | 做法 | 適用 |
|---|---|---|
| **錨點**（建議） | 在節點上加 `data-element="E-11"` | 所有元素，尤其是圖片、點狀顯示這種**沒有文字**的 |
| 文字比對 | 用畫面文字（例如「取餐時段」）找位置 | 有文字的元件 |

**真實的坑**：第一版只比對文字，11 個線框有 **17 個元素找不到**（圖片、鍵盤、點狀顯示沒有可比的文字）。
改成錨點後歸零。

**第二個坑**：混用兩種座標系。

```
錨點位置 = 在「原始 HTML」裡的索引
文字位置 = 在「去掉標籤後」的文字裡的索引
兩個索引不能直接比大小 → 全紅
```

> 規則：**同一次比較，只能用同一種座標系。** 這條在程式與在設計上一樣成立。

#### 3.5.10 四層檢查：每一層都會紅

到這裡，我們的檢查分成四層，各自抓不同的錯：

| 層 | 工具 | 抓什麼 | 這一輪抓到的 |
|---|---|---|---|
| **業務** | `verify-stories`（任務句） | 缺格、介面詞、物件沒對上 | 復原動作不屬任務 |
| **資訊** | `derive-wires` | 空線框、元素過多、孤兒線框 | 取餐櫃面板沒有顯示元素 |
| **版面** | `check-layout-order` | 順序與決策不合 | 掃碼排在確認之後 |
| **實作** | `lint-tokens`／`smoke-dom` | token、狀態數、頁面渲染 | — |

**四層都要有，缺一層就會有某一類錯永遠抓不到。**

```
node check-all.mjs   # 一支指令跑完四層，結果寫進入口頁
```

入口頁會顯示五個燈號：業務／資訊／版面／實作／負向測試。

### 3.6 檢查點（checkpoint）

| 檢查 | 標準 |
|---|---|
| 後台動作是否逐條抄完 | 與 Blueprint 一字不差 |
| 四個端別是否都出現 | 顧客／店員／廚房／設施 |
| 人工／自動是否分類 | 每條都有標記 |
| 人工動作覆蓋率 | 100% |

## 4. 訂單狀態機：所有頁面狀態的來源

### 4.1 為什麼先做狀態機

因為「頁面狀態」不是 UI 的四種樣子，而是**任務進度在介面上的投影**。
不先定狀態機，就會出現三種病：

- 每頁各自發明狀態（同一件事在 A 頁叫「處理中」、在 B 頁叫「製作中」）
- 只做 happy path（因為沒有把例外列出來）
- AC 寫不出來（因為不知道要驗收哪些轉換）

### 4.2 主線 7 態

| 狀態 | 代碼 | 觸發 | 誰觸發 | 落在哪頁 |
|---|---|---|---|---|
| 購物車草稿 | `S1 Draft` | 加入品項 | 顧客 | SCR-02／03 |
| 已下單 | `S2 Received` | 送出訂單 | 顧客 | SCR-03 → 05 |
| 已確認 | `S3 Confirmed` | 確認內容 | 店員 | SCR-06 |
| 製作中 | `S4 Preparing` | 開始製作 | 廚師 | SCR-07 |

### 4.3 例外 4 態

| 例外 | 代碼 | 觸發 | 落點 |
|---|---|---|---|
| 品項缺貨 | `SX1` | 廚師確認缺貨 | SCR-02 標記／SCR-03 提示／SCR-06 換品項 |

### 4.4 一條不能跳過的箭頭

```
S4 製作中 ──廚師按完成──▶ S5 製作完成（待確認）──店員確認備妥──▶ S6 可取餐
                                        │
                                        └─ 此時【不上看板】、不通知顧客
```

**「廚師完成」≠「顧客可以拿」。** 這條業務規則（baseline §六 決策 2 的 KDS 操作流程）
直接決定 UI 必須是**兩個狀態**，不是一個。這也是本週最值得講的一個例子：

> 業務規則 → 狀態機 → UI 元件。三層是同一個決定的三次投影。

## 5. 頁面拆分機制（本週最核心）

> **先修正一個前提**：頁面不是「切」出來的，是「**聚**」出來的。
> 元素（§3.5）依決策順序排好、聚成群（≤5–7），一群才成為一頁。所以「拆分」其實是「**分群規則**」。

> 這一節是整週的核心。前面談「有哪些頁」，這裡談「**為什麼是這些頁、不是別的切法**」。

### 5.1 先拆掉一個錯誤預設

新手（與 AI）的預設是：**一個功能 ＝ 一個頁面**。
於是「加入購物車」一頁、「客製」一頁、「確認」一頁、「付款」一頁、「完成」一頁——使用者要點五次才吃到早餐。

真實系統是**二分圖**：

```
任務 T1 ──承接狀態子集──▶ 頁面 P1
任務 T1 ──────────────▶ 頁面 P2
任務 T2 ──────────────▶ 頁面 P1
```

| 現象 | 本案實例 |
|---|---|
| **一個任務跨多頁** | 「取餐」＝ SCR-05（知道去哪）＋ 08（找到號碼）＋ 09（開櫃） |
| **一頁承接多任務** | SCR-06 同時承接「接單／備妥入櫃／收款」 |

**所以「頁面數量」不是設計目標，「切點位置」才是。**

### 5.2 兩句核心

> **① 頁面不是任務的容器，是「狀態機的視圖」。**
> **② 切頁不是切資料表，是切 episode（使用者心裡的一段事）。**

**為什麼是狀態機的視圖**：SCR-06 同時承接四個任務，因為它只是同一台狀態機的四個視圖（S2 顯示新單、S3 顯示明細、S5 顯示完成鈕、S6 顯示收款）。

**為什麼切在 episode 邊界**：

| 切法 | 判斷 | 理由 |
|---|---|---|
| 選主餐 → 選飲料 → 選加購 切三頁 | ❌ | 同一個 episode（決定吃什麼），切了會失憶 |
| 決定 → 確認 → 付款 切三頁 | ✅ | 三個 episode：探索／承諾／付錢 |

**判準一句話**：在「選飲料的中間」切頁，使用者會出現「我剛剛在幹嘛？」的失憶感。

> **資料邊界是工程師的直覺；episode 邊界是使用者的直覺。**

### 5.3 四種容器（不是只有「頁面」）

「拆分」的答案不一定是「換頁」。先選容器，再談頁面。

| 容器 | 何時用 | 代價 |
|---|---|---|
| **頁面**（換路由） | 跨角色／跨裝置；需深連結；前置狀態不同 | 需持久化；返回鍵語意 |
| **分步**（同頁 stepper） | 決策有先後依賴、同上下文、步驟 ≤ 3 | 失去深連結；「上一頁」變「上一步」 |
| **彈窗／抽屜** | 補充性任務，不改變上下文 | 阻斷感；手機易誤觸 |
| **區塊**（同頁可捲） | 同一任務的次群組 | 長頁遮蔽；需錨點 |

**決策樹（課堂可直接照著走）**

```
任務要落在哪裡？
├─ 跨角色 or 跨裝置？                → 頁面（強制）
├─ 需要被通知／QR／連結直接開啟？      → 頁面
├─ 前置狀態不同（未登入 vs 已登入）？   → 頁面，或同頁兩狀態
├─ 共用同一資料上下文，決策有先後依賴？
│    ├─ 步驟 ≤ 3 且不需中斷恢復        → 分步
│    └─ 步驟多／需中斷恢復             → 頁面（每步一頁）
├─ 純補充資訊，不改變上下文？          → 彈窗／抽屜
└─ 同一任務的次群組？                  → 區塊
```

### 5.4 三條切線、兩條合線

| 類型 | 規則 | 例子 |
|---|---|---|
| **切線 1** 資料邊界 | 需要不同資料集才能決定 | 菜單（餐點清單）vs 結帳（付款資料） |
| **切線 2** 狀態邊界 | 前置狀態不同 | 未下單 vs 已下單 |
| **切線 3** 端邊界 | 不同角色／不同裝置（**最硬**） | 顧客手機 vs 取餐看板 |
| **合線 1** 同上下文 | 同一份資料、動作可同時呈現 | 店員台的四個任務 |
| **合線 2** 不超載 | 合併後決策數 ≤ 5–7（Hick's law） | 超過要分群或分頁 |

> 三條切線裡，**端邊界最硬**（不可能合）；資料邊界次之；狀態邊界最軟（可用同頁狀態切換解決）。

### 5.5 頁面契約（頁面背後的狀態）

頁面不是一張圖，是一組「條件」。每個頁面交出一張契約：

| 欄位 | 例（SCR-03 下單確認） | 說明 |
|---|---|---|
| 路由 | `/checkout` | |
| 讀取的全局狀態 | `session`（可匿名）、`cart`（必非空） | 缺一不可 |
| 寫入的全局狀態 | `pendingOrder` | |
| 進入條件 | cart 非空；否則導回 SCR-02 | **斷點檢查點** |
| 離開條件 | 成功 → SCR-05；失敗 → 停本頁 error | |
| 狀態機來源 | `ST-ORDER`（S1–S3） | 不自己發明狀態 |
| 資料需求 | 品項、金額、取餐時段（**只寫名，型別給 spec**） | 不越界 |

### 5.6 全局狀態 × 頁面矩陣

| 全局狀態 | 型別 | SCR-02 | SCR-03 | SCR-05 | SCR-06 |
|---|---|---|---|---|---|
| `session` 未登入 | 會話 | 讀 | 讀（可匿名） | 讀 | — |
| `cart` 空 | 資料 | 忽略 | **進入失敗** | — | — |
| `orderStatus` | 交易 | — | 寫入 | **讀（驅動 7 態）** | 寫入 |
| `notificationPermission` | 裝置 | — | 請求 | **讀（拒絕時降級）** | — |

> 這張表把「登入與否」「購物車空不空」從口頭默契變成**可檢查的條件**。

### 5.7 課堂練習（3 題，各 3 分鐘）

1. **合併題**：SCR-06 與「出餐確認」為什麼能合併？指出共享的資料與狀態。
2. **拆分題**：「付款」與「下單確認」為什麼不能合併？用 episode 邊界說明。
3. **容器題**：「客製化（去冰、蛋半熟）」是頁面、抽屜、還是分步？走一次決策樹並說明代價。

### 5.8 一句話

> **任務是連續的意圖，介面是離散的容器。**
> 切得對，使用者覺得「順」；切得錯，就會出現「我剛填的資料不見了」。

## 6. 線框清單：13 → 11 的重算示範

> 這一節的每一頁，都要能回答三件事：**一群哪些元素、依什麼決策順序、用哪種容器**。
> 只寫「SCR-05 訂單狀態」是不夠的——那是編號，不是設計。

### 6.1 為什麼要示範「重算」

第一版用「任務 → 頁面」一對一推，得到 13 頁；改用「狀態機視圖」重算，變成 11 頁。
**這個過程本身就是教材**：模型換了，答案就會變，而且新的答案更正確。

| 動作 | 原本 | 重算後 | 理由 |
|---|---|---|---|
| 合併 | 取餐通知 | → SCR-05 | 通知只是深連結開同一頁，顯示 S6 |
| 合併 | 出餐確認 | → SCR-06 | 「入櫃」是 S5→S6 的狀態轉換，長在訂單卡上 |
| 其餘 | — | 保留 | 端邊界或 episode 邊界 |

> 合併**不是縮水**。原本那兩頁各自維護一份同一張訂單的畫面，正是「兩份事實」的開始。

## 7. 狀態、互動、文案

### 7.1 頁面狀態：6 欄，缺一不可

| 狀態 | 這一頁要回答什麼 | 常見錯誤 |
|---|---|---|
| default | 正常進來的樣子 | — |
| loading | 資料還沒到時顯示什麼 | 只放一個轉圈，沒有文字 |
| empty | 沒有資料時（空購物車、查無訂單） | 直接顯示空白頁 |
| error | 失敗時說哪一句、能不能重試 | 「錯誤！」不說明怎麼修 |
| success | 完成後給什麼回饋 | 沒有明確終點 |
| interrupted | 被例外打斷（缺貨／付款失敗／修改） | 完全沒做 |

> 「元件狀態」（normal／focus／pressed／disabled）屬第 8 章，不要和頁面狀態混用。
> 混用會讓學生寫出「整頁 disabled」這種不存在的東西。

### 7.2 互動規格（IX）：行為要可以被驗收

| ID | 元件 | 行為 | 觸發時機 |
|---|---|---|---|
| IX-01 | 表單欄位 | 顯示錯誤 | **失焦時**，不是輸入時 |
| IX-02 | 主按鈕 | 送出後 disabled | 送出瞬間（防重複提交） |
| IX-03 | 錯誤提示 | 顯示在欄位下方 | 驗證失敗 |
| IX-04 | 數量加減 | 到 0 時詢問是否移除 | 點減號到 0 |
| IX-05 | 付款 | 處理中鎖住返回 | 送出付款 |

**驗證時機為什麼是失焦**：邊打字邊報錯會讓使用者覺得「我還沒打完你就罵我」。

### 7.3 文案（MSG）：錯誤要幫人，不是罵人

| 情況 | ❌ 不要這樣寫 | ✅ 這樣寫 |
|---|---|---|
| 沒選取餐時間 | 錯誤！請輸入正確資料 | 請選取一個取餐時間，讓我們準時為你準備 |
| 購物車空 | 無資料 | 你的購物車還是空的，先看看今天的套餐？ |
| 付款失敗 | 交易失敗 | 付款沒有完成，你可以換一種付款方式再試一次 |
| 載入中 | Loading... | 正在為你準備菜單⋯ |
| 主要按鈕 | 確定 | 送出訂單 |

**三條規則**：
1. 錯誤要**指出怎麼修**，不是指出誰錯了。
2. 按鈕用**動詞**（送出訂單），不用「確定／送出」這種無資訊的詞。
3. 字數上限：按鈕 6 字、錯誤 30 字、空狀態 40 字。

### 7.4 檢查點（checkpoint）

| 檢查 | 標準 |
|---|---|
| 狀態完整 | L3 的每頁都有 6 欄 |
| 文案覆蓋 | 每個 error／empty 都有 MSG 編號 |
| 按鈕 | 全部是動詞 |
| 驗證時機 | 明寫「失焦」或「送出」 |

## 8. User Story 與 AC

### 8.1 兩階段 Story：US-B → US-I → AC

| 時點 | 產出 | 目的 | 不能寫什麼 |
|---|---|---|---|
| UX 之前 | **US-B 業務版** | 確認角色任務值得做，以及它回應哪個 CJM 痛點／機會 | 頁面、按鈕、元件、API |
| UX 之中 | 元素／狀態／Wireframe | 把 US-B 變成可操作的結構 | 沒有來源的裝飾 |
| UX 之後 | **US-I 介面版** | 指出故事實際走過哪些 SCR | 尚未存在的路徑 |
| 狀態定案後 | **AC** | 定義怎樣算完成、哪些事禁止發生 | 只描述畫面外觀 |

> 若只有 US-I，線框可能先做完才事後補價值；若只有 US-B，又無法驗證故事是否真的走得完。兩者同編號但承擔不同責任。

### 8.2 角色任務 vs User Story（回顧）

| | 角色任務（Blueprint） | US-B／US-I |
|---|---|---|
| 回答 | 誰必須做什麼、交給誰 | 誰想達成什麼、為什麼／如何走完 |
| 視角 | 供給側（生產流程） | 需求側（價值意圖＋介面路徑） |
| 主體 | 人**或設施** | **只有人** |
| 完成判準 | handoff 完成 | US-B 有價值；US-I 有路徑；AC 可驗收 |
| 來源 | Blueprint 的角色工作與交接 | 角色任務＋CJM 痛點，之後再加 UX 證據 |

**試紙**：不能寫出「以便」的是角色任務；沒有角色任務與痛點來源的「以便」則是憑空想像。

### 8.3 業務語言測試

> 把句子裡的「系統」換成「店員」，還讀得通，就是業務語言。

| 句子 | 替換後 | 判定 |
|---|---|---|
| 系統通知顧客進度 | 店員通知顧客進度 | ✅ 業務語言 |
| 系統呼叫推播 API | 店員呼叫推播 API | ❌ 工程語言 |
| 系統顯示取餐號碼 | 店員顯示取餐號碼 | ✅（改「店員出示」更順） |

### 8.4 EARS 五型（AC 的寫法）

| 型 | 關鍵字 | 用在 |
|---|---|---|
| 無條件 | the system shall… | 永遠成立的行為 |
| 事件驅動 | **When**…, the system shall… | 某件事發生時 |
| 狀態驅動 | **While**…, the system shall… | 某狀態持續時 |
| 可選 | **Where**…, the system shall… | 有這功能時 |
| 異常 | **If**…, then the system shall… | 出錯時 |

### 8.5 示範：從狀態表反寫 AC（SCR-05 訂單狀態）

| 狀態 | 對應的 AC |
|---|---|
| success（送出） | When 顧客送出訂單成功，the system shall 顯示訂單號、預計取餐時間，狀態標為「已下單」。 |
| default（已確認） | When 店員確認訂單，the system shall 把狀態更新為「已確認」，並保留原預計時間。 |
| loading | While 訂單為「製作中」，the system shall 顯示進度或倒數，且**不得**顯示取餐號碼。 |
| success（完成待確認） | When 廚師標記完成，the system shall **仍顯示「製作中」**，不得顯示「可取餐」。 |
| success（可取餐） | When 店員確認備妥入櫃，the system shall 顯示取餐號碼與櫃位，並發送通知。 |
| error（通知失敗） | If 推播未送達，then the system shall 提示「請注意店內看板」，並提供手動重新整理。 |

> 注意第 4 條：它驗收的是「**不可以**做什麼」。
> **狀態表最大的價值，就是逼你寫出這種「禁止型 AC」。** 這種 AC 靠 Story 是推不出來的。

#### 8.7.1 每個可點元件都要交代三件事

線框不是畫好看的圖，是按下去會動的東西。所以每個可點元件都要能回答：

| # | 問題 | 寫在哪 |
|---|---|---|
| 1 | **會去哪？**（跳頁／外部／不離開） | 動作的 `kind` ＋ `next` |
| 2 | **會改什麼？**（哪個物件、哪個狀態） | 動作的 `changes` |
| 3 | **失敗會怎樣？** | 動作的 `ac` ＋ 錯誤態 |

三題答不出來，代表這個按鈕還沒設計完，只是畫了一個方框。

**三種動作，三種處理**

| 類型 | 行為 | 例子 |
|---|---|---|
| **內部跳頁**（nav） | 先顯示「→ 前往 SCR-03」再跳 | 前往結帳 |
| **外部系統**（external） | **不跳頁**，先說明會去哪、回來會怎樣 | 前往付款（外部金流） |
| **改資料**（mutate） | 顯示說明 → 進入 loading（按鈕消失）→ 計時後套用 | 送出訂單 |

#### 8.7.2 非同步要有「行為」，不是只有一張截面

「loading 態」不是畫一張骨架圖就好，它必須**真的跑起來**：

```
點「送出訂單」
  → 按鈕立刻停用（不能連點）
  → 畫面進入 loading，顯示「正在送出你的訂單⋯」
  → 2 秒後才前進到結帳頁
```

| 規則 | 為什麼 |
|---|---|
| 非同步動作要有**最短時長**（本案 1.5–2.5 秒） | 讓「處理中」看得見；太快會閃一下 |
| 期間**所有可點元素停用** | 防重複提交（AC-03／AC-07） |
| 每個 loading 態都要有**文字**（不是只有骨架） | 骨架看不出在做什麼 |
| 外部動作要**說明會去哪、回來會怎樣** | 使用者不能突然被丟到陌生頁面 |

**外部跳轉的寫法**（本案「前往付款」）：

```
點「前往付款」
  → 不跳頁，先顯示：「會離開原型，前往外部支付頁面；付款後回報成功或失敗」
  → 由使用者選擇模擬結果：成功 → 前往 SCR-05；失敗 → 留在本頁 error 態
```

> 原型碰不到真實金流，但**流程與回報一定要演出來**；不然測的人不知道「回來會怎樣」。

**可自動檢查的三條**（已寫進 `verify-stories.mjs`）

| 檢查 | 抓什麼 |
|---|---|
| 每個動作都有 `notes` | 有按鈕卻沒交代會發生什麼 |
| 說明不得含禁用詞（「系統」「請稍後」） | 空話 |
| 外部動作必須有 `next` | 失敗後不知道去哪 |

### 8.7 可走的故事：把「可點」升級成「可驗」

線框與資訊流都講清楚之後，User Story 可以更進一步：**用線框把情境串起來**。
可點元件分成兩種處理：

| 動作類型 | 行為 | 例子 |
|---|---|---|
| **nav**（跳轉） | 直接跳到下一個畫面 | 前往結帳 → SCR-03 |
| **mutate**（操作資料） | 彈出面板說明**意圖、會改什麼、驗收條件** | 送出訂單 → S1→S2 |

#### 8.5.1 三個層次要分開

| 層次 | 定義 | 證據 |
|---|---|---|
| **可點** | 流程走得通 | 人點一遍，畫面會動 |
| **可查** | 每個動作對得到 AC，人可核對 | 動作面板 ＋ 稽核模式 |
| **可驗** | **做錯了會紅、做對了會綠** | 斷言 ＋ PASS／FAIL 報告 |

> 差別不在工具有多炫，而在**「它會不會失敗」**。不會失敗的檢查，是說明書；會失敗的檢查，才是規格。

#### 8.5.2 動作定義：一份資料，兩個地方吃

```json
{
  "id": "submit-order", "screen": "scr-03-checkout", "label": "送出訂單",
  "kind": "mutate",              // nav | mutate
  "intent": "把草稿訂單送出並鎖定內容",
  "changes": ["order.status: S1 → S2", "pickup_slot: 寫入"],
  "ac": ["AC-01", "AC-02"],
  "next": "scr-04-payment"
}
```

HTML 只要加 `data-action="submit-order"`；面板內容由 `story-data.js` 讀取，
所以「意圖與 AC」只寫一份，不會和 `stories.md` 漂移。

#### 8.5.3 禁止型 AC 用「守衛卡」

「廚師完成**不得**通知顧客」這種規則**點不出來**——任何走一遍的呈現都只展示 happy path。
所以在會被違反的畫面放一張守衛卡，並用斷言證明它成立：

| 寫法 | 內容 |
|---|---|
| 守衛卡 | 「此畫面在廚師按完成後，不會出現取餐號碼，也不會發通知」 |
| 斷言 | `SCR-05/S5 不存在 [data-pickup-no]，且通知次數 = 0` |

#### 8.5.4 AC 的驗證等級（不要假裝都驗過了）

| `verify` | 意思 | 誰做 | 本案估比 |
|---|---|---|---|
| **auto** | 可寫成斷言，會 pass／fail | 學生寫、指令跑 | 60–70% |
| **manual** | 有步驟，但要人看 | 助教照清單 | 20% |
| **human** | 只能人判斷（可用性、情緒、4 公尺可讀） | 使用者測試 | 10–20% |

回報要說清楚：**自動 16 條、人工 5 條、需使用者測試 2 條**——三種證據等級分開列。

#### 8.5.5 兩個指令

```
node verify-stories.mjs     # 結構＋內容檢查，輸出 PASS／FAIL
node selftest-stories.mjs   # 負向測試：故意做錯，確認檢查會紅
```

> `selftest` 是關鍵：如果「做錯也 PASS」，那套檢查就是空的。

### 8.8 把「只能人工」變成「可自動」：四問法

先講一個發現：原本被判為「人工檢查」或「只能人判斷」的 8 條 AC，實際上有 **8 條全都能自動**。

> **「只能人工」通常不是因為它主觀，而是因為還沒設計錨點。**

#### 8.8.1 四問法（每次想把 AC 自動化就跑一遍）

| # | 問自己 | 答不出來會怎樣 |
|---|---|---|
| 1 | **你怎麼知道它成立？**列三個證據 | 表示這條 AC 根本沒定義清楚 |
| 2 | 證據是「可讀的值」還是「感覺」？ | 是感覺 → 先找**代理指標** |
| 3 | 判準能寫成**布林**（是／否）嗎？ | 不能 → 再拆 |
| 4 | 有**錨點**嗎？（`data-*`） | 沒有 → 加一個，不要一直靠眼睛 |

「代理指標」的意思是：把感受換成可量的東西。
例如「按鈕要顯眼」→ 代理 = 「一頁只有一個 primary 按鈕」＋「對比 ≥4.5:1」，兩個都可算。

#### 8.8.2 八種述詞（可自動的檢查長這樣）

| 類型 | 問法 | 我們的例子 |
|---|---|---|
| **存在性** | 有沒有這個元素？ | AC-11 不得出現取餐號碼 |
| **文字內容** | 有沒有這句話？ | AC-12「待店員確認」 |
| **數量** | 有幾個？ | AC-07 處理中「付款按鈕數 = 0」 |
| **順序** | 前後關係對嗎？ | **AC-20 佇列由早到晚** |
| **屬性值** | 值在範圍內嗎？ | 對比 ≥4.5:1、字級 ≥ 距離/200 |
| **相對位置** | A 在 B 的哪裡？ | AC-02 錯誤訊息要指到欄位 |
| **狀態互斥** | 兩者不能同時出現？ | AC-11 製作中 vs 可取餐 |
| **互動後變化** | 點了之後 DOM 變了嗎？ | AC-03 送出後按鈕消失 |

#### 8.8.3 實例：AC-20 從「人判斷」變「可計算」

| | 寫法 |
|---|---|
| **原本** | 「KDS 佇列排序要合理」→ 只能人看 |
| **四問法** | ①怎麼知道？看卡片順序 ②可讀的值（時間）③可以寫成「遞增」④錨點：卡片上的取餐時間 |
| **轉換後** | 抽出所有 `\d{2}:\d{2}(?= 取餐)`，依序比較是否遞增 |

**踩到的坑（真實發生）**：第一版用 `\d{2}:\d{2}`，把計時器 `03:12` 也抓進來，
結果 `08:20 → 03:12` 看起來是遞減，檢查誤判。
→ **述詞要精確到「只抓什麼」，否則會抓到不該抓的。**

#### 8.8.4 一個 AC 只能有一個述詞

AC-02 原本寫「未選時段不得跳頁，錯誤留在原頁」——這其實是兩件事：

| 拆分後 | 驗證方式 |
|---|---|
| AC-02a 錯誤訊息要指到是哪個欄位 | **可自動**（兩個錨點同時存在） |
| AC-02b 不得跳頁 | 仍靠人工（或整合測試） |

> AC 若有兩個述詞，就會出現「一半可驗、一半不可驗」的灰色地帶。拆開，界線就清楚了。

#### 8.8.5 邊界：自動化率 ≠ 體驗達標

23 條 AC 全部自動化，只證明**規則被實作**，不證明**好用**。
體驗驗證（可用性測試、情緒、4 公尺可讀）是另一層，不能用斷言取代。

| 層 | 問什麼 | 證據 |
|---|---|---|
| 規則 | 有沒有照規則做 | 斷言（PASS／FAIL） |
| 體驗 | 好不好用 | 使用者測試 |

#### 8.8.6 檢查表

| # | 檢查 |
|---|---|
| 1 | 這條 AC 的述詞是哪一型？（八型之一） |
| 2 | 有沒有錨點？沒有就加 `data-*` |
| 3 | 判準是布林嗎？不是就拆 |
| 4 | 述詞會不會抓到不該抓的東西？（AC-20 的計時器） |
| 5 | 負向測試做過嗎？做錯會不會紅？ |

### 8.9 兩層證據：規則層與體驗層

把 23 條 AC 全部自動化之後，會出現一個危險的錯覺：**「全綠 = 做完了」**。但 23/23 只證明規則被實作。

| 層 | 問什麼 | 載體 | 誰做 | 會失敗嗎 |
|---|---|---|---|---|
| **規則層** | 有沒有照規則做 | 斷言（`verify-stories`） | 機器 | ✅ 會紅 |
| **體驗層** | 好不好用 | 走查清單（`review.html`） | 人 | ✅ 會不通過 |

> 兩層都要有證據，才算完成。只有規則層全綠，是「規則正確但沒人用過」。

#### 8.9.1 走查清單怎麼寫（14 項，四類）

| 類別 | 例子 | 方法 | 誰 |
|---|---|---|---|
| 可用性 | 等待頁是否降低焦慮 | 5 人測試，請他找「還要多久」 | 使用者測試 |
| 無障礙 | 內文對比 ≥ 4.5:1 | 實測取色並記錄比率 | 課程 |
| 遠距 | 看板 4 公尺可讀 | 畫面縮到 1/5，站 4 公尺外讀 | 課程 |
| 文案 | 錯誤訊息不責備 | 抽 5 則，確認指出怎麼修 | 助教 |

**每一項都要有三件事**：①**方法**（怎麼測）②**owner**（誰做）③**證據**（數字，不是感想）。

```
❌ 證據：「看起來還不錯」
✅ 證據：「5 人測試，4 人 3 秒內找到預計時間」
```

#### 8.9.2 回報要同時講兩層

```
規則層：23 / 23（自動，全綠）
體驗層：6 / 14（可用性 2/4、無障礙 1/4、遠距 2/3、文案 1/3）
不通過：RV-09 看板 4 公尺可讀（縮到 1/5 後號碼糊掉）
```

> 只報「全部通過」而沒有分層，就是在把「規則」當成「體驗」。

#### 8.9.3 入口頁會顯示這個落差

`prototype/index.html` 的「兩層證據」區塊會同時顯示：
規則層 23/23（綠）與體驗層 x/14（橘），並在規則全綠但體驗未完成時明講：
**「規則全綠，但體驗只完成 x%——這正是能驗不等於好用。」**

#### 8.9.4 檢查表

| # | 檢查 |
|---|---|
| 1 | 每個體驗項目都有方法、owner、證據 |
| 2 | 證據是數字或觀察，不是形容詞 |
| 3 | 不通過的項目有「誰、什麼時候修」 |
| 4 | 回報同時列兩層，不只報規則層 |
| 5 | 規則全綠時，有沒有一種「沒人用過」的心虛？ |

## 9. 線框

### 9.1 線框是視圖，不是階段

**HTML 線框的兩個標記約定**（§8.5 的基礎）：

| 標記 | 給誰用 | 例子 |
|---|---|---|
| `data-action="xxx"` | 可點元件 → 對應動作定義（意圖／AC） | `data-action="submit-order"` |
| `data-pickup-no` 等錨點 | 可被斷言的元素（尤其「不得出現」） | 號碼、櫃位、開櫃碼 |


本課程的線框**以 HTML 實作**（見 `prototype/`），理由與五條硬規則：

| 理由 | 說明 |
|---|---|
| token 要被執行 | 灰階圖用不到 `var(--color-primary)`；HTML 才是真的套規格 |
| 狀態要可切換 | `?state=error` 一點就知道有沒有做 |
| 可驗收 | 改一個 token 看有沒有連動（第 5 週的方法） |
| 可無障礙 | 鍵盤焦點、aria-live、reduced-motion，畫圖做不到 |

| # | 硬規則 |
|---|---|
| 1 | 只能用 token，不得寫死色碼／間距（跑 `node lint-tokens.mjs`） |
| 2 | 六態可切換：`?state=default\|loading\|empty\|error\|success\|interrupted` |
| 3 | 灰階優先：`?mode=wire` 先驗結構，再談顏色 |
| 4 | 一個目錄一個 SCR，檔案結構固定（`index.html／screen.css／screen.js／README.md`） |
| 5 | **HTML 不取代 AC**：驗收仍以 `stories.md` 為準 |

> 沒有第 5 條，這門課就會退回「看起來對就好」。

它驗證的是「**資訊層次與動線**」，不是美感。所以：

| 規則 | 理由 |
|---|---|
| 只用灰階 | 一旦上色，討論就會變成「這個顏色不好看」 |
| 用真實 token 尺寸 | 375px；間距標 `space-lg`、字級標 `headline-sm`，不寫 px |
| 必須畫狀態變體 | 只畫 happy path 的線框，等於沒畫 |
| 每個區塊標元件名 | 對應 `DS-COMP`，順便檢查有沒有缺元件 |

### 9.2 必畫的狀態

| 深度 | 必畫 |
|---|---|
| L1 | default |
| L2 | default ＋ empty ＋ error |
| **L3** | **6 個狀態全部** |

### 9.3 三秒測試

> 把畫面遮住文字，只看版面：3 秒內能不能指出「主 CTA 在哪」？
> 指不出來 → 視覺層次有問題（不是線框的問題，是結構的問題）。

### 9.4 元件對應與回流

線框畫完，把每個區塊對到 `DESIGN.md` 第 8 章（DS-COMP）：

| 情況 | 處理 |
|---|---|
| 有對應元件 | 標元件名（例如 `PrimaryButton`） |
| 沒有對應元件 | 記進「待補元件清單」，回寫 `DESIGN.md` → **v1.1** |
| 需要新狀態 | 同上；不准在線框旁寫「這裡先這樣」 |

> 這一步是 Design.md 從「工具產出」變成「專案權威」的唯一機會。
> 不回寫，程式碼裡就會長出第二套規格。

## 10. 遠距顯示（KDS／看板）

### 10.1 五種介面：距離 × 輸入（兩個獨立維度）

**距離決定字多大，輸入決定能不能操作。** 把兩者混在一起，就會出現「KDS 不能點」這種錯。

| # | 介面 | 尺寸 | 距離 | **輸入** | 可用互動狀態 |
|---|---|---|---|---|---|
| T1 | 手機（顧客） | 375 | 30–40cm | 觸控 | pressed／focus／disabled |
| T2 | 平板（店員／老闆） | 768 | 60–80cm | 觸控 | pressed／disabled／selected |
| T3 | **取餐櫃面板** | 768 直立 | **約 1m** | **觸控 ＋ 數字鍵 ＋ 掃碼** | pressed／disabled／error |
| T4 | **KDS（廚房）** | 1920 | 1.5–2.5m | **觸控（可戴手套）** | pressed／disabled／selected／**二次確認** |
| T5 | 取餐看板 | 1920 | 3–5m | **無（純顯示）** | 無 |

> **只有 T5 完全不可操作。** T3／T4 是「遠距 ＋ 可操作」，最容易被搞錯的一格。
> 廚師正是靠點 KDS 改訂單狀態（開始製作 → 完成）；如果把 KDS 當看板，服務就斷了。

### 10.2 字級不是憑感覺

```
可讀下限：字高 ≥ 距離 ÷ 200
掃視辨識（號碼）：字高 ≥ 距離 ÷ 100
```

**算例**：55 吋、4 公尺、1920×1080
→ 可讀 ≥ 20mm、號碼 ≥ 40mm；1px ≈ 0.634mm → 內文 ≥ 32px、號碼 **64–96px**。

> 同一個 96px：在手機上是錯的，在看板上是對的，**對錯由距離算出**。

### 10.3 為什麼要獨立的 DESIGN-DISPLAY.md

| | 主檔（手機） | 遠距 |
|---|---|---|
| 內文 | 16px | 32–48px |
| 間距 | 4px 基準 | 8／16px |
| 互動 | hover／focus／active | 看板無 |
| 佈局 | 可捲動 | 1920 一屏定生死 |

塞在一份會出現「16px 又 32px」的矛盾 token → 所以**獨立一份，但繼承品牌**：

> 遠距版**不得重新定義任何顏色**，只能引用主檔 token。否則會重演「三份色值」。

### 10.4 產出方式

用 `03_遠距顯示_獨立Designmd規格與Prompt.md` 的 Prompt 貼進 Stitch（已寫死 1920×1080、55 吋、4 公尺、純顯示），匯出 `DESIGN-DISPLAY.md`。

### 10.5 驗收（30 秒可做）

> 把 1920 的畫面**縮到手機寬度（約 1/5）**，還讀得出號碼，就差不多等於 4 公尺外的效果。

---

### 10.6 KDS 與取餐櫃面板：遠距但可操作

**這是本章最容易犯的錯**：把「遠距」等同「不可操作」。只有取餐看板（T5）不能操作。

**KDS（T4）的互動規則**

| 規則 | 為什麼 |
|---|---|
| 主按鈕 ≥ 120px 高、≥ 240px 寬 | 戴手套、手上有油，精度下降 |
| **無 hover、無滑動、無多層選單** | 觸控 ＋ 只看 2 秒 |
| 破壞性操作要**二次確認** | 誤觸「完成」會讓顧客被通知錯 |
| 需要 disabled／selected 狀態 | 已完成的單不能再按；多選標記缺貨 |
| 要有**聲音回饋** | 廚房吵，視覺不夠 |
| 計時器顏色 **＋ 數字** | 不只靠顏色 |

可以做的操作：開始製作、標記完成、標記缺貨、調整排序、展開明細。
不可以做：改顧客訂單內容、改價格（要回店員台）。

**取餐櫃面板（T3）的互動規則**

| 規則 | 為什麼 |
|---|---|
| **數字鍵盤 ＋ 掃碼，兩種都給** | 有人記不住號碼、有人不想打字 |
| 按鍵 ≥ 120px | 1 公尺外手指定位不精確 |
| 錯誤要指出下一步（「請確認通知上的 4 位數」） | 不是「錯誤」兩個字 |
| 逾時自動返回 | 安全，且不留下他人輸入 |
| 單一任務：只能取餐 | 不在這裡付款或點餐 |

> 完整矩陣（五種介面 × 輸入 × 回饋 × 禁忌）與檢查清單見 `13_裝置與互動能力矩陣.md`。

| 面向 | 比重 | 判準 |
|---|---|---|
| **A 產出完整性** | 60% | |

### 11.4 四項指標

| 指標 | 公式 | 標準 |
|---|---|---|
| 人工動作覆蓋率 | 被 SCR 承接的人工動作 ÷ 人工動作總數 | 100% |
| 狀態覆蓋率 | 被頁面承接的訂單狀態 ÷ 11 態 | 100% |
| 頁面過載度 | 單頁承接任務數 ／ 動作數 | ≤ 3 ／ ≤ 7 |
| 斷點率 | 沒有進入條件的頁面數 | 0 |

### 11.5 五個最常見的失分

| 失分 | 症狀 | 怎麼救 |
|---|---|---|
| 從 CJM 起手 | 只有顧客端 5 頁 | 回去抄 Blueprint 後台動作 |
| 忘了設施 | 沒有看板／KDS | 端別一定要有「設施」 |
| 只有 happy path | 狀態表只填 default | 六欄缺一不可 |
| AC 寫成元件行為 | 「點擊後出現彈窗」 | 改寫成狀態轉換 |
| 一頁塞太多 | 超過 3 個任務 | 走一次拆分決策樹 |

### 11.6 與第 7 週的銜接

| 本週產出 | 下週用途 |
|---|---|
| `UX.md` 的 SCR／ST／MSG | 收斂進 `spec.md` 的行為章 |
| `stories.md`（US ＋ AC） | `spec.md` 的契約章（驗收條件直接沿用） |
| 線框 | 實作的版面依據 |
| 待補元件清單 | 回寫 `DESIGN.md` v1.1 |
| 四項指標 | 第 16 週回顧的品質基線 |

**語言換檔的位置**：User Story 與 AC **仍然是業務語言**；
真正換成工程語言的地方是 `spec.md` 的**實作附錄**（API、資料表、型別）。

所以有兩個邊界，不要混在一起：
- **選項 → 決定**：第 5 週 Blueprint 之後
- **業務 → 工程**：第 7 週 `spec.md` 的實作附錄

### 11.7 本週核心一句話

> **CJM 告訴你顧客在哪裡痛；Blueprint 告訴你誰要動手。**
> **頁面不是任務的容器，是狀態機的視圖；切頁不是切資料，是切 episode。**
> **先有狀態，才有 AC；先有結構，才有線框。**
