## 3. Step 1：建立 `11_service-requirements.md`

這份文件是跨來源索引，不是畫面清單。每列至少包含：

| REQ | 需求敘述 | 主要角色 | 來源痛點／機會 | 角色任務 | 物件／狀態 | 交接／例外 | 下游承接 |
|---|---|---|---|---|---|---|---|
| REQ-001 | | | | | | | |

填寫順序：

1. 從 baseline 找已定案服務規則。
2. 接上 CJM 的痛點／機會。
3. 接上 Blueprint 的角色、交接與例外。
4. 接上物件、狀態與資訊流時效。
5. 指定下游由哪個 role-task、US-B、元素或 UX 承接。

沒有來源的需求退回上游，不要以「使用者需要」作為來源。

## 4. Step 2：建立 `12_role-tasks.md`

`role-tasks` 是供應側業務任務，不是程式實作 tasks，也不是介面按鈕清單。

每條任務使用七格：

```text
T-ID｜前置業務狀態｜A 角色｜業務動作｜物件／狀態轉換｜B 角色｜B 的決策｜時效
```

實際表格：

| T | 前置業務狀態 | A | 業務動作 | 物件 | 狀態轉換 | B | B 的決策 | 時效 |
|---|---|---|---|---|---|---|---|---|
| T-01 | | | | OBJ-xx | | | | |

操作步驟：

1. 從 `11_service-requirements.md` 一列一列找出需要人工或設施完成的業務動作。
2. 寫出動作發生前的業務狀態。
3. 指定真正執行者 A；設施可作為 A，但不能把「系統」當成含糊角色。
4. 指定物件與狀態轉換。
5. 指定交接後的 B，以及 B 要做的決策。
6. 由 `06_infoflow.md` 填時效，不任意寫「即時」。
7. 做店長測試：把任務句交給不看 UI 的店長，他是否知道誰做什麼、交給誰、何時完成？

禁止使用：頁面、畫面、按鈕、點選、輸入框、跳轉、API、資料表。

## 5. Step 3：建立 `13_UserStory-B.md`

由 CJM 痛點／機會、服務需求與 role-tasks 萃取需求側價值：

```text
作為〔角色〕，我想要〔任務成果〕，以便〔價值〕。
```

逐條檢查：

- 角色必須是人，不是系統。
- 任務成果不能是「看到一個按鈕」或「打開某頁」。
- `以便` 必須描述顧客、店員、廚師或老闆得到的業務價值。
- 每條故事回指至少一個 CJM 痛點／機會、REQ 與 T-ID。

錯誤：

```text
作為顧客，我想要一個送出按鈕，以便完成操作。
```

正確方向：

```text
作為第一次使用的顧客，我想在送出前確認完整金額與品項，以便避免點錯後才發現。
```

## 6. Step 4：建立 `14_elements.md`

資訊元素是支撐一次決策的最小資訊單位。不是先想按鈕，再補理由。

### 6.1 從任務句推導元素

依序問：

1. B 要做什麼決策？
2. 物件的哪個屬性能支持這個決策？
3. 該屬性要被顯示、輸入還是操作？
4. 需要哪種呈現型態，理由是什麼？
5. 屬於哪個角色、哪個任務與哪個視圖？

### 6.2 十一欄表格

| ID | 元素 | 用途 | 資料來源 | 類型 | 建議型態 | 型態依據 | 歸屬角色／任務 | 狀態改變 | 去處 | 回饋／失敗去處 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| E-01 | | | OBJ-xx.屬性 | 顯示／輸入／操作 | | | | | | |

操作元素的最後四欄不可空白：

- 會改變哪個物件、哪個狀態？
- 成功後留在原地、前往哪個 SCR，或離開系統？
- 成功看到什麼回饋？
- 失敗停在哪個狀態？

## 7. Step 5：建立 `15_UX.md`

依 `15_UX/15_UX_template.md` 填六章。

### 7.1 前言與範圍

寫版本、日期、全部 SCR、MVP L3 頁面、來源文件與 ID 規則。

### 7.2 SCR 線框清單

每列包含：

| SCR | 端 | 承接任務 | 承接狀態 | 進入點 | 離開點 | 深度 | 涉及物件／時效 |
|---|---|---|---|---|---|---|---|
| SCR-01 | 顧客／店員／廚房／設施 | | | | | L1/L2/L3 | |

端別只能是顧客、店員、廚房、設施。看板與取餐櫃必須有設施端 SCR。

使用 `15_UX_screen-state-matrix.md` 的 11 個 SCR 與 S1–S7、SX1–SX4 作為檢查基準；若你的服務不同，保留差異理由，不要悄悄刪除狀態。

### 7.3 FLOW 與狀態

每個 L3 SCR 建立六態表：

| 狀態 | 顯示什麼 | 主要動作 | MSG |
|---|---|---|---|
| default | | | |
| loading | | | |
| empty | | | |
| error | | | |
| success | | | |
| interrupted | | | |

有些 L1／L2 頁面可以合理省略某些狀態，但要寫出「為什麼不存在」，例如取餐櫃不一定有 empty。

### 7.4 IX 互動規格

每個操作元素寫：觸發時機、狀態改變、是否防重複提交、成功去處、錯誤去處。不要只寫「點擊後跳轉」。

### 7.5 MSG 文案

- 錯誤要指出怎麼修。
- 按鈕使用動詞。
- 不能只用顏色傳達狀態。
- 每個 error、empty、success、loading 都要有可讀訊息。

### 7.6 可用性與待驗證

至少檢查：對比、觸控目標、鍵盤焦點、減少動效、遠距可讀性。尚未測試標為待驗證，不得寫已驗證。

## 8. Step 6：建立 `16_wireframes/`

線框不是自由畫圖，而是 `14_elements.md` 與 `15_UX.md` 的結構驗證。

### 8.1 推展順序

```text
role-tasks
  ↓
資訊元素（每群 5–7 個）
  ↓
元素群與容器（頁面／分步／彈窗／區塊）
  ↓
檢查操作元素的去處
  ↓
命名 SCR-xx
  ↓
畫線框與狀態變體
```

規則：顯示／輸入是節點，操作是邊；每個操作元素都必須有去處或明確狀態改變。每個線框要有進入邊，或標明是常駐／非介面入口。

### 8.2 原型操作

若使用 HTML Prototype，先讀 `16_wireframes/00_Prototype整合操作手冊.md`，再依下列順序操作：

1. 開 `16_wireframes/prototype/index.html`。
2. 先使用灰階 `?mode=wire` 檢查結構，再看彩色。
3. 逐一切換 `?state=default`、`loading`、`empty`、`error`、`success`、`interrupted`。
4. 顧客畫面以 375、店員以 768、KDS／看板以 1920 檢查；遠距畫面另做 1/5 等效縮放。
5. 在 `16_wireframes/prototype/` 執行：

```text
node gen-tables.mjs
node derive-wires.mjs
node check-layout-order.mjs
node gen-stories.mjs
node verify-stories.mjs
node lint-tokens.mjs
node selftest-stories.mjs
node check-all.mjs
node smoke-dom.mjs
```

`gen-stories.mjs` 會更新正式 `17_UserStory-I_AC.md`；不要建立或交付 `17_UserStory-I_AC_generated.md`。

若修改故事或動作，至少重跑 `gen-stories.mjs`、`verify-stories.mjs`、`selftest-stories.mjs` 與 `check-all.mjs`；若修改狀態、文案或版面，還要重跑 `smoke-dom.mjs` 並重新做人工走查。

## 9. Step 7：validation 走查

分兩層：

### 規則層

- 任務覆蓋元素與畫面。
- 元素的成功、失敗、狀態轉換有來源。
- Wireframe 與 UX 的 SCR、狀態一致。
- US-I 能回指 US-B。
- AC 能回指狀態或業務規則。

### 體驗層

- 實際走過主要故事，不只看表格。
- 檢查手機、平板、KDS、看板與取餐櫃的觀看距離。
- 檢查錯誤是否留在原處、提示是否足夠久、是否能復原。
- 記錄未通過項目、證據、責任人與修正後結果。

可使用：

```text
node check-all.mjs
node smoke-dom.mjs
```

`check-all` 通過不能取代人工走查；自動檢查與體驗走查都要留下紀錄。

## 10. Step 8：建立 `17_UserStory-I_AC.md`

### 10.1 US-I

每條 US-I 必須列出：

- 對應 US-B
- 來源痛點
- 實際經過的 SCR 順序
- 每個路徑的入口與完成點

格式：

```text
US-I-01：從 SCR-02 → SCR-03 → SCR-04，完成下單與付款。
來源：US-B-01、REQ-003、T-02／T-03。
```

不得列不存在的 SCR，也不得把單一畫面直接當成完整故事而沒有業務價值。

### 10.2 AC

從狀態表、例外、資訊流與禁止規則反寫 EARS：

```text
When／While／Where／If …, the system shall …
```

每條 AC 只驗證一個狀態轉換或禁止規則，並標記驗證責任：`auto`、`manual` 或 `human`。

必須包含禁止型規則，例如：

```text
While 訂單為製作中，the system shall 不顯示取餐號碼。
When 廚師標記完成，the system shall 仍標示待店員確認，不提前通知顧客。
If 付款失敗，then the system shall 留在付款頁並提供重試或更換方式。
```
