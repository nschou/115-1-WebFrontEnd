# 05 頁面拆分機制：任務、頁面、狀態

> 這是第 6 週最核心的一章。前面談「有哪些頁」，這一章談「**為什麼是這些頁、不是別的切法**」。
> 讀完應該能回答：一個任務為什麼要切成三頁？兩個任務為什麼能共用一頁？

---

## 一、先拆掉一個錯誤預設

新手（與多數 AI）的預設是：**一個功能 = 一個頁面**。
於是「加入購物車」一頁、「客製」一頁、「確認」一頁、「付款」一頁、「完成」一頁——使用者要點五次才吃到早餐。

真實系統是**二分圖**，不是一對一：

```
任務 T1 ──承接狀態子集──> 頁面 P1
任務 T1 ──────────────> 頁面 P2
任務 T2 ──────────────> 頁面 P1
```

- **一個任務跨多頁**：取餐 ＝ 訂單狀態頁（知道去哪）＋ 看板（找到號碼）＋ 取餐櫃面板（打開櫃門）
- **一頁承接多任務**：店員訂單台同時承接「接單／確認／標記完成／收款」

**所以「頁面數量」不是設計目標，「切點位置」才是。**

---

## 二、兩句核心

> **① 頁面不是任務的容器，是「狀態機的視圖」。**
> **② 切頁不是切資料表，是切 episode（使用者心裡的一段事）。**

### 為什麼是「狀態機的視圖」

以店員訂單台（SCR-06）為例，同一頁承接四個任務，因為它只是同一台狀態機的四個視圖：

| 任務 | 訂單狀態 | 這一頁顯示 | 可做什麼 |
|---|---|---|---|
| 接收訂單 | 已下單 | 新單高亮 | 確認 |
| 確認內容 | 已確認 | 品項明細 | 退回／放行 |
| 標記備妥 | 製作完成 | 完成鈕、櫃號 | 入櫃 |
| 收款 | 可取餐 | 金額、付款方式 | 確認收款 |

**判準**：如果兩個任務「在同一份資料上下文中、不同狀態下發生」，它們就該同一頁。

### 為什麼要切在 episode 邊界

「選主餐 → 選飲料 → 選加購」是**同一個 episode**（決定吃什麼），切三頁會讓使用者失去上下文。
「決定 → 確認 → 付款」是**三個 episode**（探索／承諾／付錢），三段心理狀態不同，該切。

> **資料邊界是工程師的直覺；episode 邊界是使用者的直覺。**
> 在「選飲料的中間」切頁，使用者會出現「我剛剛在幹嘛？」的失憶感。

---

## 三、四種容器（不是只有「頁面」）

「拆分」的答案不一定是「換頁」。先選容器，再談頁面。

| 容器 | 何時用 | 代價 |
|---|---|---|
| **頁面**（換路由） | 跨角色／跨裝置；需要深連結（通知可直接開）；前置狀態不同 | 需持久化；返回鍵語意要處理 |
| **分步**（同頁 stepper） | 決策有先後依賴、共用同一資料上下文、步驟 ≤ 3 | 失去深連結；「上一頁」變「上一步」 |
| **彈窗／抽屜** | 補充性任務，不改變主要上下文 | 阻斷感；手機易誤觸 |
| **區塊**（同頁可捲） | 同一任務的次群組 | 長頁遮蔽；需錨點 |

### 決策樹

```
任務要落在哪裡？
├─ 跨角色 or 跨裝置？                    → 頁面（強制）
├─ 需要被通知／QR／連結直接開啟？         → 頁面
├─ 前置狀態不同（未登入 vs 已登入）？      → 頁面，或同頁兩狀態
├─ 共用同一資料上下文，決策有先後依賴？
│    ├─ 步驟 ≤ 3 且不需中斷恢復           → 分步
│    └─ 步驟多／需中斷恢復                → 頁面（每步一頁）
├─ 純補充資訊，不改變上下文？             → 彈窗／抽屜
└─ 同一任務的次群組？                     → 區塊
```

## 四、三條切線、兩條合線

| 類型 | 規則 | 例子 |
|---|---|---|
| **切線 1** 資料邊界 | 需要不同資料集才能決定 | 菜單（餐點清單）vs 結帳（付款資料） |
| **切線 2** 狀態邊界 | 前置狀態不同 | 未下單 vs 已下單（同一路由，不同視圖） |
| **切線 3** 端邊界 | 不同角色／不同裝置 | 顧客手機 vs 取餐看板 |
| **合線 1** 同上下文 | 同一份資料、動作可同時呈現 | 店員台的四個任務 |
| **合線 2** 不超載 | 合併後決策數 ≤ 5–7（Hick's law） | 超過就要分群或分頁 |

> 三條切線裡，**端邊界最硬**（不可能合）；資料邊界次之；狀態邊界最軟（可用同頁狀態切換解決）。

## 五、頁面契約（頁面背後的狀態）

頁面不是一張圖，是一組「條件」。每個頁面交出一張契約：

| 欄位 | 例（SCR-03 下單確認） | 說明 |
|---|---|---|
| 路由 | `/checkout` | |
| 讀取的全局狀態 | `session`（可匿名）、`cart`（必非空） | 缺一不可 |
| 寫入的全局狀態 | `pendingOrder` | |
| 進入條件 | cart 非空；否則導回 SCR-02 | **斷點檢查點** |
| 離開條件 | 成功 → SCR-05；失敗 → 停本頁 error | |
| 狀態機來源 | `ST-ORDER`（Received→Preparing→Ready→…） | 不自己發明狀態 |
| 資料需求 | 品項、金額、取餐時段（**只寫名，型別給 spec**） | 不越界 |

### 全局狀態 × 頁面 矩陣

這是本週最有價值的一張表——它把「登入與否」「購物車空不空」變成可檢查的條件：

| 全局狀態 | 型別 | SCR-02 | SCR-03 | SCR-05 | SCR-06 |
|---|---|---|---|---|---|
| `session` 未登入 | 會話 | 讀 | 讀（可匿名） | 讀 | — |
| `cart` 空 | 資料 | 忽略 | **進入失敗** | — | — |
| `orderStatus` | 交易 | — | 寫入 | **讀（驅動 7 態）** | 寫入 |
| `notificationPermission` | 裝置 | — | 請求 | **讀（拒絕時降級）** | — |

**原則**：頁面的狀態不是「UI 的四種樣子」，而是**任務進度在介面上的投影**。
所以狀態表的來源是 Blueprint 的訂單狀態機與 4 個例外，不是元件的樣子。

## 六、一個容易算錯的地方：人工 vs 自動

計算「後台動作覆蓋率」時，**不能把所有後台動作都算成需要頁面**。要先分兩類：

| 類型 | 定義 | 落點 |
|---|---|---|
| **人工作業** | 需要有人判斷或輸入 | 必須有 `SCR` 承接（覆蓋率 100%） |
| **系統自動** | 由某項決策指定自動執行 | 記在「系統行為」清單，交 `spec.md` |
| **無介面** | SOP、實體流程 | 不在 UX 範圍（但要說明） |

本案實例：

| Blueprint 動作 | 類型 | 落點 |
|---|---|---|
| 店員通知廚師製作 | **系統自動**（決策 2：KDS 路由） | spec |
| 店員通知顧客進度 | 系統自動（推播）＋人工觸發 | SCR-06 按鈕 → spec |
| 生成取餐號碼 | 系統自動 | spec |
| 老闆記錄銷售 | 系統自動（POS） | spec |
| 店員維護環境清潔 | 無介面（SOP） | 不在範圍 |

> 不這樣分，學生會為了湊 100% 而**替自動化動作硬造頁面**——這是「AI 味介面」的來源之一。

## 七、四項指標（可 lint）

| 指標 | 公式 | 標準 | 抓什麼錯 |
|---|---|---|---|
| **人工動作覆蓋率** | 被 SCR 承接的人工動作 ÷ 人工動作總數 | 100% | 服務斷點 |
| **狀態覆蓋率** | 被頁面承接的訂單狀態 ÷ 狀態機狀態總數 | 100% | 有狀態但沒有畫面 |
| **頁面過載度** | 單頁承接的任務數 ／ 動作數 | ≤ 3 ／ ≤ 7 | 一頁塞太多，必漏狀態 |
| **斷點率** | 沒有明確進入條件的頁面數 | 0 | 「這頁從哪來？」 |

## 八、課堂練習（3 題，各 3 分鐘）

1. **合併題**：SCR-06（店員訂單台）與「出餐確認」為什麼可以合併？請指出它們共享的資料與狀態。
2. **拆分題**：「付款」與「下單確認」為什麼不能合併？請用 episode 邊界說明。
3. **容器題**：「客製化選項（去冰、蛋半熟）」應該是頁面、抽屜、還是分步？請走一次決策樹並說明代價。

---

## 九、一句話

> **任務是連續的意圖，介面是離散的容器。**
> 切得對，使用者覺得「順」；切得錯，就會出現「我剛填的資料不見了」。
> **頁面數量從來不是設計目標，切點位置才是。**
