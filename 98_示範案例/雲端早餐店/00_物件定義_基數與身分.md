# 00_物件定義｜只寫「餐點存在」等於沒定義餐點

> 名詞：快照（某個時間點的完整狀態；重連時先拿快照，再補後續變化）。

> 真實案例：我們的 `05_objects` 列了「OBJ-03 餐點」，類型、擁有者、生命週期、角色都寫了。
> 但到了 `plan.md` 卻落不了點——最後被 `order_items`（訂單的一行）頂替。
> 原因不是工程偷懶，是**業務層沒給「單位」**。

## 代號對照

| 代號 | 意思 | 代號 | 意思 |
|---|---|---|---|
| S0 | 尚未建立訂單（狀態機之前） | S4 | 製作中 |
| S1 | 草稿 | S5 | 製作完成（待店員確認） |
| S2 | 已下單 | S6 | 可取餐 |
| S3 | 已確認 | S7 | 已取餐 |
| SX1–SX4 | 例外：缺貨／付款失敗／通知未送達／修改待確認 | | |

## 一、物件卡缺了什麼：基數、身分、關係

| 欄位 | 問題 | 沒有它的後果 |
|---|---|---|
| **基數** | 一筆訂單有幾份餐點？ | 不知道餐點是集合還是單一 |
| **身分** | 哪一份？怎麼辨認？ | 同品項 2 份無法區分 |
| **關係** | 餐點屬於訂單？取消時跟著作廢嗎？ | 生命週期說不清 |
| **狀態粒度** | 每份各自完成，還是整單一起？ | KDS 無法表達「一份先好」 |

原本的物件表有「類型／擁有者／生命週期／角色」，**這四項都在描述「它是什麼」，卻沒有描述「它有幾個、怎麼認、跟誰綁」。**

## 二、三個具體後果（都是業務缺口造成的）

| # | 後果 | 證據 |
|---|---|---|
| 1 | 狀態表只有訂單，沒有餐點 | `18_spec` §5 是 S1–S7（訂單），餐點的「製作中／完成」沒有位置 |
| 2 | 任務句語意錯位 | `12_role-tasks` T-05 說「製作**餐點**」，但狀態轉換寫「S3（已確認）→S4（製作中）→S5（製作完成，待店員確認）」（那是訂單的） |
| 3 | plan 用 `order_items` 頂替 | 它是「下單的一行、含價格快照」，不是「要做的份」 |

## 三、這是一個必須由業務決定的選擇

| 切法 | 定義 | 好處 | 代價 |
|---|---|---|---|
| **A. 餐點＝訂單明細** | 同品項 2 份算 1 個（quantity=2） | 最省 | **一份先好、一份還沒 → 無法表達** |
| **B. 餐點＝每份（portion）** | 蛋餅×2＝2 個餐點 | 可獨立完成、可個別交付 | 卡片變多 |
| **C. 餐點＝整張訂單** | 一單一個製作單位 | 最簡單 | 無法部分完成 |

**本案例選擇 B（每份一個）**，理由：

- 早餐店實務是「一份一份做」（蛋餅、漢堡分開），但同品項 2 份通常一起做。
- 因此：**資料層分開（每份一個）、顯示層合併（KDS 一張卡顯示「蛋餅 ×2」）**。
- 這樣「一份先好」能表達（顯示 1/2 完成），店員也不用面對兩張卡。

> 注意：這是**業務決策**，不是技術決策。技術決策（獨立表還是 `order_items` 拆份）留給 OOD。

## 四、修正後的四個連動（缺一個就會漂移）

| 位置 | 寫什麼 |
|---|---|
| `05_objects` | 基數「1 訂單 → N 份」、身分「訂單號＋品項＋份序號」、關係「屬於訂單，可單獨完成但不可脫離訂單存在」 |
| `06_infoflow` | 規則 6：「每份可各自完成；**訂單 S5（製作完成，待店員確認）＝全部餐點完成**」 |
| `12_role-tasks` | T-05 推進的是**餐點**的 S4→S5；訂單 S5（製作完成，待店員確認）是聚合結果 |
| `18_spec` | §4.1 註明基數與身分；§5 註明「上表是訂單狀態，餐點另有製作狀態」 |
| `plan.md` | 落點：形式（獨立表或 `order_items` 拆份）由 W11 OOD 決定，決定前以 quantity 表示 |

## 五、判準：什麼樣的物件才算「講清楚」

| 檢查 | 通過的樣子 | 反例 |
|---|---|---|
| 基數 | 「1 訂單 → N 份」 | 「餐點」兩個字就結束 |
| 身分 | 「訂單號＋品項＋份序號」 | 「就是餐點」 |
| 關係 | 「屬於訂單，取消時作廢」 | 沒提 |
| 狀態粒度 | 「每份獨立完成；訂單 S5（製作完成，待店員確認）＝全部完成」 | 只寫「待製作／完成」 |
| 聚合規則 | 「顧客看訂單進度，不逐份顯示」 | 兩邊各顯示一套 |

## 六、這跟 OOD 的關係（先後不能顛倒）

```text
業務層（現在）：餐點 = 每份一個、有自己的身分 → 這是「事實」
        ↓
OOD（W11）：要獨立表？還是 order_items 拆份？ → 這是「選擇」
        ↓
plan：資料表、約束、狀態聚合
```

**業務層給「事實」，OOD 才能給「選擇」。** 順序顛倒的話，OOD 只能猜——而它會猜成 `order_items`。

## 七、自查三問（你的專案有沒有同樣問題）

1. 你的物件清單裡，有沒有一個物件**從來沒出現在任何資料表**？（那就是落不了點）
2. 你的「一對多」關係寫在哪裡？如果只寫在 plan，代表業務層沒說。
3. 你的狀態表裡，有沒有一個狀態**無法由任何角色推進**？（那是聚合結果，不是狀態）

## 學生練習

1. 用「基數／身分／關係」三欄，補完你專案裡**最模糊的那個物件**。
2. 找一個「一份訂單有多個 X」的情境，說明 X 的三種切法各會造成什麼問題。
3. 檢查你的狀態表：有沒有哪個狀態是「聚合結果」被誤寫成狀態？
