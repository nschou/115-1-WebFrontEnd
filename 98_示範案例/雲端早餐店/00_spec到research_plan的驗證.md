# 00_spec 到 research 與 plan 的驗證｜spec 到底有什麼用

> 名詞：快照（某個時間點的完整狀態；重連時先拿快照，再補後續變化）／降級（主要管道失效時改用替代管道，例：通知送不出去就改看店內看板；不是把功能關掉）／競態（兩個人同時改同一筆資料，誰先誰後？會不會互相覆蓋？）。

> 目的：證明 `18_spec.md` 不是「寫完放著」的文件，而是**逼出研究題目、約束技術取捨**的來源。
> 方法：三問檢驗。每一問都有實際證據與對照位置。

## 三問檢驗

| # | 問題 | 通過代表 |
|---|---|---|
| Q1 | 這條 spec 會逼出什麼**研究題目**？ | spec 有「無法直接實作、必須先研究」的含量 |
| Q2 | 研究結論回填成**什麼取捨**？ | 研究不是讀論文，是選方案 |
| Q3 | plan／tasks 的決策能**回指 spec** 嗎？ | 改一條需求時，追得到該改哪裡 |

## 一、Q1：三條 spec 逼出的研究題目

### 題目 A｜「1 秒內四端一致」→ 狀態同步機制

| 項目 | 內容 |
|---|---|
| spec 依據 | `18_spec.md` §8「狀態變更後 1 秒內顧客端可見」；§4 四端 |
| 為什麼不能直接做 | 「1 秒一致」在瀏覽器裡**不是必然**：輪詢會延遲、長連線會斷、多寫入會互蓋 |
| 研究題目 | 四個觀看位置要怎麼拿到同一個狀態？輪詢／SSE／WebSocket 各自的延遲與復原成本？ |
| research 對應 | `research.md` §3.3「狀態同步：輪詢 vs SSE vs WebSocket」→ 結論 §4-3「採用 SSE；命令仍走一般請求」 |
| plan 對應 | `plan.md` §4.3 事件與重連、§5 一致性策略 |
| tasks 對應 | `tasks.md` TASK-009「事件串流、快照與重連降級」 |

### 題目 B｜「不可重複扣款」→ 冪等（同一個操作重送多次，只生效一次）與付款嘗試狀態

| 項目 | 內容 |
|---|---|
| spec 依據 | `18_spec.md` §D `REQ-008`（銀行確認中不重複扣款）、`AC-08`／`AC-09` |
| 為什麼不能直接做 | 付款是**外部系統＋網路重試**；「按兩次」與「重送回」在業務上看起來一樣 |
| 研究題目 | 怎麼讓同一筆付款只成立一次？冪等鍵放哪？「銀行確認中」這種中間狀態怎麼表示？ |
| research 對應 | §2 條件列「付款失敗與銀行確認中不可重複扣款 → 付款命令必須有可追蹤的嘗試狀態與冪等識別」；§4-6「事件帶版本／序號」 |
| plan 對應 | §5 交易與一致性策略 |
| tasks 對應 | TASK-006「完成付款冪等與付款狀態邊界」 |

### 題目 C｜「號碼與櫃位不可重複」→ 唯一約束與競態

| 項目 | 內容 |
|---|---|
| spec 依據 | `18_spec.md` §D `REQ-012`、§4.1 `OBJ-05`（憑證物，可回收）；`06_infoflow.md`「競爭熱點：多店員同時發號」 |
| 為什麼不能直接做 | 號碼**一天內會回收再發**，且「發出」與「回收」可能同時發生 |
| 研究題目 | 怎麼保證同一號碼／櫃位不會同時給兩張單？用唯一約束、鎖、還是佇列？ |
| research 對應 | §2 條件列「同單、取餐號碼、最後一份庫存不可重複或互相覆蓋」；§3.5「關聯式資料模型與交易／唯一約束」 |
| plan 對應 | §3 資料模型、§5 一致性策略 |
| tasks 對應 | TASK-003「核心資料模型與唯一約束」、TASK-008「取餐號碼、櫃位與取餐命令」 |

### 小結

> **spec 的價值不是把答案寫好，而是把「非研究不可的地方」標出來。**
> 上表三條，如果 spec 只寫「要快、要正確」，研究就會變成自由發揮；寫成「1 秒／不可重複／不可重複扣款」，研究才有靶。

## 三、實測缺口（用數字說話）

統計各檔案引用 spec 元素的次數：

| 檔案 | REQ | AC | SD | OBJ | T |
|---|---:|---:|---:|---:|---:|
| `18_spec.md` | 22 | 90 | 26 | 28 | 50 |
| `research.md` | **0** | 3 | **0** | 0 | 0 |
| `plan.md` | **0** | 47 | **0** | 7 | 7 |
| `tasks.md` | 2 | 54 | **0** | 2 | 3 |

**判讀**：

1. ✅ **spec → research 的連結是「條件」而非「編號」**：research §2 用來源描述（「§4、§8」「AC-08、AC-09」），所以人看得懂，但機器追不到。
2. ⚠️ **REQ 與 SD 在 plan／tasks 幾乎消失**：一旦某條需求改變，追到的是「哪條 AC」，追不到「哪條需求、哪條決策」。
3. ✅ 這是可修的：在 research §2 加 REQ／SD 欄、plan 每個決策加「對應 REQ」、tasks 每張卡加「完成哪條 REQ」。

## 四、spec 推不出來的部分（也是它的價值）

`research.md` §5 列了五個**不能由 spec 推測**的問題：

| ID | 問題 | 為什麼 spec 答不了 |
|---|---|---|
| RQ-01 | 店員／廚師／老闆如何辨識與授權？ | spec 只寫「誰可以推進」，沒寫「怎麼確認他是誰」 |
| RQ-02 | 付款供應商與銀行回呼方式？ | 這是外部契約，不是業務需求 |
| RQ-03 | 資料保存期限與刪除規則？ | 涉及法規與營運政策 |
| RQ-04 | 斷線後補事件還是重取快照？ | 這是實作策略，不是業務規則 |
| RQ-05 | 第一階段是否多實例？ | 部署決策 |

> **一份好的 spec，會清楚標出「我答不了什麼」。**
> 這不是缺陷，是把「猜」與「決定」分開——RQ 清單就是「必須有人負責決定」的清單。

## 五、驗收方式（可重複）

| 檢查 | 通過標準 |
|---|---|
| 每條 NFR 都有研究題目 | 在 research §2 找得到對應列 |
| 每條 REQ 都有 plan 落點 | 對照表覆蓋率 100% |
| plan 的每個技術選擇都有 spec 理由 | 沒有「因為流行」的選擇 |
| RQ 清單非空且被標記 | 至少 3 條（本案例 5 條） |

## 學生練習

1. 從 `18_spec.md` 挑一條 **§8 的非功能需求**，寫出它逼出的研究題目，並在 `plan.md` 找到落點。
2. 找出一条「plan 有、spec 沒有」的技術選擇，判斷它是**研究結論**（合理）還是**擅自決定**（越界）。
3. 用 `research.md` §5 的 RQ 清單，檢查你的專案：哪幾個問題你還沒決定？
