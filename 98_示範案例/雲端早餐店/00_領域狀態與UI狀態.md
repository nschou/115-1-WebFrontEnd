# 00_領域狀態與 UI 狀態｜別把「畫面」當成「事實」

> 狀態代號：S0 尚未建立訂單／S1 草稿／S2 已下單／S3 已確認／S4 製作中／S5 製作完成（待店員確認）／S6 可取餐／S7 已取餐；SX1–SX4 為例外（缺貨／付款失敗／通知未送達／修改待確認）。完整定義見 `18_spec.md` §5。

> 常見的設計錯誤：把「載入中」「送出中」「錯誤」寫成訂單的狀態。
> 結果是報表出現「載入中」的訂單、後端要處理一個不存在的業務狀態、狀態機爆成 42 種。
> 這份文件用三個案例把界線畫清楚。

## 一、一句話定義

| | 領域狀態 | UI 狀態（畫面狀態） |
|---|---|---|
| 回答的問題 | **世界發生了什麼事** | **我現在看到什麼、還能做什麼** |
| 例子 | S1 草稿 → S2 已下單 → … → S7 已取餐 | loading／submitting／error／selected／expanded |
| 誰推動 | **業務事件**（店員確認、廚師完成、入櫃） | **資源與互動**（請求回來、使用者點了、網路斷了） |
| 存在哪裡 | 後端／共享（可被多方讀取） | 只存在某個畫面（離開就消失） |
| 生命週期 | 長（要對帳、要審計） | 短（秒級，甚至毫秒） |
| 可以被重設嗎 | 不行（只能靠業務事件改變） | 可以（重新整理就回到初始） |

## 二、依賴是單向的

```text
┌──────────────────────────────┐
│ 領域狀態（事實）              │  S1–S7、SX1–SX4
│ 推動：業務事件                │  存：後端／共享
└──────────────┬───────────────┘
               │ 讀取（單向）
┌──────────────▼───────────────┐
│ UI 狀態（呈現與過渡）          │  loading／submitting／error／
│ 推動：資源與互動              │  selected／expanded
│ 存：只存在某個畫面            │
└──────────────────────────────┘
```

**關鍵**：領域狀態可以在**沒有 UI** 的情況下存在（報表、看板、對帳照樣跑）；UI 狀態離開畫面就不存在。

所以是 **UI 依賴領域**，不是互相依賴。反過來做，等於讓「有沒有畫面」決定「業務事實」。

## 三、三個案例

### 案例 1｜付款：同一個「處理中」，兩個不同的東西

| | 領域狀態 | UI 狀態 |
|---|---|---|
| 名稱 | `payment.status = 處理中` | `isSubmitting = true` |
| 意思 | **錢可能已經被扣了**，正在等銀行回覆 | 我正在等這個請求回來 |
| 誰推動 | 銀行回呼／付款結果 | 使用者按下付款 |
| 存哪裡 | 後端（要能對帳） | 瀏覽器記憶體 |
| 誰看得見 | 顧客、店員、對帳 | 只有這個畫面 |
| 判斷依據 | 能不能重送？會不會重複扣款？ | 按鈕要不要變灰？ |

> 「銀行確認中」**是領域狀態**，因為它決定「能不能重送、會不會重複扣款」；
> 「按鈕轉圈」**是 UI 狀態**，它不影響任何業務判斷。
> 兩者都寫成 `OrderState.Processing` 的話，對帳程式就得處理一個不存在的狀態。

### 案例 2｜KDS 按完成：按鈕變灰不是狀態

| | 領域 | UI |
|---|---|---|
| 事實 | 訂單 `S5 製作完成（待店員確認）` | 「已按完成」→ 按鈕變灰 |
| 判斷依據 | 廚師按了完成（業務事件） | 這次點擊已經送出（互動） |
| 寫錯的樣子 | `Order.status = '按下完成'` | — |

**後果**：隔天報表顯示「3 筆訂單停在『按下完成』」——那根本不是業務狀態，也沒有人能推進它。

### 案例 3｜取餐櫃數字鍵盤：UI 有狀態，領域沒有

| 層 | 內容 |
|---|---|
| UI 狀態 | 已輸入 2 位、游標位置、掃碼／鍵盤切換、錯誤閃紅 |
| 領域狀態 | **完全沒有變化**（還沒確認） |
| 只有在「確認」成功後 | 才產生領域事件：取餐號碼 → `已使用` |

把「已輸入 2 位」寫成 `PickupCodeState.Partial`，就得到一個**沒有任何人需要知道**的狀態。

## 四、把 UI 狀態塞進領域狀態的五個後果

| # | 後果 | 長相 |
|---|---|---|
| 1 | **狀態爆炸** | 7 個領域狀態 × 6 個畫面態 ≈ 42 種組合，還要處理交叉 |
| 2 | **語意污染** | 後端、報表、看板都要處理 `Loading` 這種不存在的業務狀態 |
| 3 | **不可審計** | loading 只存在 300ms 卻被持久化 → 報表出現「載入中」的訂單 |
| 4 | **權限錯亂** | 「誰能推進 loading？」沒有角色能回答 → 出現 `if (state === loading) return;` |
| 5 | **測試錯位** | 該用「資源延遲」驗的東西，被寫成領域單元測試 → 真正的風險沒測到 |

**最小徵兆**：你的領域狀態表裡出現 `loading`、`error`、`submitting`、`empty` —— 幾乎可以斷定放錯了。

## 五、判準：四問決定它住哪裡

| 問 | 是 | 否 |
|---|---|---|
| 其他角色（店員／看板／老闆）需要看到嗎？ | 領域 | |
| 需要被保存、對帳、審計嗎？ | 領域 | |
| 會改變「能不能取餐／能不能重送／誰能推進」嗎？ | 領域 | |
| 只在某個畫面短暫存在、離開就消失嗎？ | | UI |

四問全「否」＝純 UI；任一「是」＝領域。

## 六、UX 的「暫時狀態」是政策，不是狀態

你說「UI 狀態有時是為了 UX 而設計的暫時狀態」——對，但**它們要寫成政策（可驗收的行為約定），不是資料**。

| UX 政策 | 寫法 | 不要寫成 |
|---|---|---|
| 骨架最小顯示 300ms（避免閃爍） | 「載入畫面至少顯示 300 毫秒」 | `Order.state = loading` |
| 樂觀更新（先顯示成功） | 「送出後立即顯示成功，失敗時回滾並提示」 | 把「成功」寫進資料庫 |
| 重試倒數 | 「失敗後 3 秒可重試」 | 新增 `RetryState` |

> **政策是行為約定（可驗收）；狀態是資料（可保存）。** 混在一起就會出現「每秒寫一次資料庫來顯示倒數」。

## 七、對照你的六態

| 你的六態 | 它其實是 | 對應領域狀態 |
|---|---|---|
| default（正常） | 頁面的資源狀態 | 投影自 Sx（依頁面而不同） |
| loading（處理中） | **資源取得中** | 不變 |
| empty（沒有資料） | **查詢結果為空** | 不變（例如今天沒有訂單） |
| error（失敗） | **請求失敗** | 不變（訂單沒有因此改變） |
| success（完成） | **本次操作完成** | 由業務事件推進 |
| interrupted（被打斷） | **外部事件**（售完、逾時） | 可能是 SX 例外，也可能是純 UI |

**結論**：六態是**頁面層**，不是訂單層。在文件裡請寫「畫面呈現態」，不要寫成「訂單狀態」。

## 八、兩條紅線（可寫成檢查）

| 紅線 | 檢查方式 |
|---|---|
| 領域狀態表**不得**出現 loading／error／submitting／empty | 掃狀態表名稱 |
| UI 狀態**不得**被持久化 | 資料模型裡不得有 `is_loading`、`is_submitting` 欄位 |

## 九、五個常見誤解

| # | 誤解 | 事實 |
|---|---|---|
| 1 | 「loading 也是一種狀態，放進狀態機比較整齊」 | 放進去會讓狀態機變成畫面狀態機 |
| 2 | 「先把 loading 存起來，重新整理才不會消失」 | 重新整理就該重新載入；存起來反而製造假事實 |
| 3 | 「State pattern 什麼狀態都能管」 | 它管的是**業務狀態**；畫面狀態用一般的條件渲染就好 |
| 4 | 「六態就是訂單的六種狀態」 | 六態是頁面的呈現態，訂單只有 S1–S7 |
| 5 | 「UX 要的暫時狀態也是需求，所以也是領域」 | 它是**政策**，寫進行為約定，不是寫進資料 |
