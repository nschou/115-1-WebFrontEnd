# 00_因果鏈回推｜三個 spec 條文是怎麼長出來的

> 目的：讓你看見 `18_spec.md` 裡的每一句話，背後都有一條**可以被查證的推導鏈**。
> 方法：從 spec 條文往回走，每一層都標出「證據在哪個檔案的哪一節」，最後回到市場與 Persona。
> 判準：**一個條文如果回推不到人（Persona 的痛點）與物（物件的本質），它就不該存在。**

## 代號對照

| 前綴 | 意思 | 例子 |
|---|---|---|
| **S1–S7** | 訂單的正常狀態（S1 草稿／S2 已下單／S3 已確認／S4 製作中／S5 製作完成（待店員確認）／S6 可取餐／S7 已取餐） | S5 |
| **SX1–SX4** | 例外狀態：缺貨／付款失敗／通知未送達／修改待確認 | SX2 |
| **T-xx** | 角色任務句（七格）的編號 | T-05 廚師製作餐點 |
| **E-xx** | 介面元素編號 | E-09 訂單進度 |
| **AC-xx** | 驗收條件編號 | AC-12 廚師完成不得通知 |
| **OBJ-xx** | 業務物件編號 | OBJ-05 取餐號碼 |
| **REQ-xxx** | 規格需求編號 | REQ-012 可取餐顯示號碼 |
| **SD-xx** | 服務決策編號 | SD-03 進度更新與通知 |

## 回推的六層

| 層 | 問題 | 在哪裡 |
|---|---|---|
| L1 條文 | 它規定了什麼 | `18_spec.md` §D 需求清單 |
| L2 驗收 | 怎樣算做到 | `17_UserStory-I_AC.md` |
| L3 結構 | 哪個畫面／哪個狀態／哪個元素 | `15_UX.md`、`14_elements.md` |
| L4 任務 | 誰在什麼狀態下做什麼、交給誰 | `12_role-tasks.md`（七格） |
| L5 約束 | 物件能不能這樣動、時效容不容許 | `05_objects.md`、`06_infoflow.md` |
| L6 理由 | 為什麼選這個、代價是什麼、否決了什麼 | `07_decisions.md`、`04_blueprint.md` |
| L7 人 | 這是誰的痛點 | `03_cjm.md`、`02_persona.md`、`01_market.md` |

## 案例 A｜「廚師完成不得通知顧客」（性質：業務規則／角色邊界）

### A0 條文

> `18_spec.md` §D：`REQ-011 | 廚師完成後不得通知顧客 | T-05／T-06 | SD-03 | AC-12`
> §5 狀態表：S5（製作完成，待店員確認）→ **誰可以推進＝店長**；S6（可取餐）才是可取餐。

### A1 回推過程

| 層 | 證據 | 原文／內容 | 這一步推出什麼 |
|---|---|---|---|
| L2 | `17_UserStory-I_AC.md` AC-12 | 「When 廚師標記完成，仍顯示『製作中』，且不得發送取餐通知」 | 規定的是**通知時機**，不是畫面 |
| L3 | `15_UX.md` §3.3、`14_elements.md` E-09 | SCR-05 六態；SCR-07 完成卡「待店員確認」 | 兩端狀態不同步就會出現矛盾 |
| L4 | `12_role-tasks.md` T-05 / T-06 | T-05 廚師→店員「可以交付了嗎」；T-06 店員→顧客「去哪裡拿」，時效 **1 秒** | 「完成」與「可取」是**兩個人的兩個事件** |
| L5 | `06_infoflow.md` §2 規則 1 | 「廚師標記完成，不代表顧客可取餐；需經店員確認與入櫃」 | 這是**不變量**，不是偏好 |
| L5 | `05_objects.md` OBJ-02 | 訂單生命週期 S1–S7＋例外 | S5 必須是一個獨立狀態，不能併進 S4 |
| L6 | `07_decisions.md` SD-02 | 「店員確認後進入廚房工作佇列」；代價：需要店員多一次確認 | 寧可多一次人工，也不讓未確認的單進廚房 |
| L6 | `07_decisions.md` SD-03 | 「狀態機＋店內看板＋顧客查詢」；代價：例外處理較複雜 | 接受複雜度，換取「四端一致」 |
| L6 | `04_blueprint.md` §2 交接（廚師→店員） | 接收者要知道「哪張單完成，但**尚未必然可取**」；失敗風險「顧客提前來取」 | 這就是條文要防的事 |
| L6 | `04_blueprint.md` §4 R-4 | 被否決的候選：「廚師按完成即通知顧客」→ 否決理由「完成不等於備妥入櫃」→ **不應翻案（不變量）** | 六個月後有人想改，這裡有話可說 |
| L7 | `03_cjm.md` 等待取餐 | 情緒 **−2**（全旅程最低點）：「不知道餐點做到哪、何時可取」 | 這是痛點的本體 |
| L7 | `02_persona.md` 張家豪 | 痛點「等待時間不確定」；目標「快速拿到、不遲到」 | 誰在痛 |
| L7 | `01_market.md` §3 服務承諾 | 「依明確進度與取餐號碼快速取餐」 | 為什麼這件事值得做 |

### A2 一句話的推論

> 如果「完成即通知」，顧客會在店員確認**之前**走到櫃前 → 櫃前擠滿人、店員要分神處理 → 等待反而變長 → 直接違反市場承諾。
> 所以這條不是「流程囉唆」，而是**用一個人工確認，換掉整條等待曲線**。

### A3 影響範圍（用 `impact.mjs` 實測）

| 指標 | 值 |
|---|---|
| 受影響頁面 | 2（`scr-07-kds`、`scr-05-order-status`） |
| 會動到的資料欄位 | 5 |
| 提到它的文件 | 12 份 |

## 案例 B｜「取餐號碼是憑證物，不是訂單欄位」（性質：資料模型）

### B0 條文

> `18_spec.md` §4.1：`OBJ-05 取餐號碼｜類型＝憑證物｜生命週期＝未發／已發／已使用／回收`
> §D：`REQ-012 | 可取餐時顯示號碼、櫃位、開櫃碼 | T-06／OBJ-05 | SD-04 | AC-13`

### B1 回推過程

| 層 | 證據 | 原文／內容 | 這一步推出什麼 |
|---|---|---|---|
| L2 | `17_UserStory-I_AC.md` AC-13 | 「當店員確認備妥入櫃，顯示取餐號碼與櫃位，並發送通知」 | 號碼的**出現時機**被綁在 S6（可取餐） |
| L3 | `14_elements.md` E-09…、SCR-05 | 訂單進度、號碼、櫃位是不同元素 | 號碼不是「訂單的一部分」，是另一個東西 |
| L4 | `12_role-tasks.md` T-06 | 店員「備妥入櫃」→ 物件是 **OBJ-05 取餐號碼**，不是 OBJ-02 訂單 | 動作動到的是號碼，不是訂單 |
| L5 | `05_objects.md` 首段判準 | 列入物件必須：跨角色、影響決策、有生命週期、可持有／傳遞／更新 | 四條全部成立 → 它必須是物件 |
| L5 | `05_objects.md` OBJ-05 | 類型＝**憑證物**；擁有者＝服務；生命週期＝未發／已發／已使用／**回收** | 回收＝一天之內會重複使用 |
| L5 | `06_infoflow.md` 取餐號碼列 | 「不可重複；≤1 秒；競爭熱點：多店員同時發號；動態原型：競爭」（白話：號碼不能撞；發出後 1 秒內四個地方都要看到；多個店員可能同時發號） | 這是**會被同時搶用的資源**（多個店員可能同時發號，必須保證不撞號） |
| L6 | `07_decisions.md` SD-04 | 「顧客號碼＋櫃位，看板同步」；代價：「需管理號碼與櫃位的**回收**」 | 決策者已經預見回收成本並接受 |
| L6 | `04_blueprint.md` §2 交接（店員→顧客） | 接收者要知道「取餐號碼、櫃位、可取狀態」；失敗風險「顧客找不到餐」 | 交接的內容是號碼＋位置 |
| L7 | `03_cjm.md` 取餐 | 情緒 +1，但痛點「到店後不知道去哪裡拿」 | 號碼要解的是「定位」 |
| L7 | `02_persona.md` / `01_market.md` | 「不遲到」／「快速取餐」 | 為什麼值得 |

### B2 一句話的推論

> 如果只把它做成 `order.pickup_no` 一個欄位，就表達不了三件事：**會被回收再發**、**不能重複分配**、**要跟櫃位綁定**。
> 這三個性質都屬於「憑證」，不屬於「訂單」。**資料模型的形狀，是被業務性質逼出來的。**

## 案例 C｜「狀態變更 1 秒內四端一致」（性質：非功能／時效）

### C0 條文

> `18_spec.md` §8：`時效｜狀態變更後 1 秒內顧客端可見｜誰在等：站在櫃前的顧客`
> 同節：`時效｜新單 3 秒內出現在廚房顯示｜廚師`；`時效｜營收可落後 1 小時，但金額必須正確｜老闆`

### C1 回推過程

| 層 | 證據 | 原文／內容 | 這一步推出什麼 |
|---|---|---|---|
| L2 | `17_UserStory-I_AC.md` AC-13 | 入櫃後顯示號碼、櫃位並通知 | 驗收對象是「顧客看到的時間」 |
| L3 | `15_UX.md` §3.2 跨端狀態同步 | FLOW-02：顧客／店員／廚房／看板 | 「四端」是四個實際的觀看位置 |
| L4 | `12_role-tasks.md` T-06 | 時效欄＝**1 秒** | 時效是任務的一部分，不是後來補的 |
| L5 | `06_infoflow.md` 訂單列 | 「單一狀態來源；≤1 秒；競爭熱點：店員與廚房同時改同一單」（白話：四個地方讀同一份狀態；1 秒內看到新狀態；店員與廚房可能同時改動） | 1 秒不是隨便寫的：它是在「店員與廚房可能同時改同一張單」的情況下，仍然要在 1 秒內看到最新狀態 |
| L5 | `06_infoflow.md` 營收列 | 「可延遲 1 小時」 | **不同物件有不同的容忍** |
| L6 | `07_decisions.md` SD-03 | 「訂單狀態機＋店內看板＋顧客查詢」；代價：例外處理複雜 | 為了 1 秒一致，接受複雜度 |
| L6 | `04_blueprint.md` §2 交接（店員→顧客） | 失敗風險「顧客找不到餐」 | 延遲＝找不到餐 |
| L7 | `03_cjm.md` 等待取餐 | 情緒 −2，最低點 | 秒級焦慮的來源 |
| L7 | `02_persona.md` 張家豪 | 「不遲到」 | 誰在等 |
| L7 | `01_market.md` §2 市場機會 | 「可預期等待」是顧客願意付溢價的原因 | 這是商業價值，不只是體驗 |

### C2 一句話的推論

> **「1 秒」不是技術指標，是體驗參數**：它來自「站在櫃前的人」的容忍度。
> 同一份文件裡，營收可以落後 1 小時——這證明**時效是分角色、分物件定的**，不是「全部都越快越好」。

## 三例的共同結構（你可以拿這個檢查每一條 spec）

| # | 問題 | 答不出來代表 |
|---|---|---|
| 1 | 這條是誰的痛點？（Persona＋CJM） | 需求是憑空想的 |
| 2 | 它動到哪個物件、那個物件的性質允許嗎？ | 資料模型是猜的 |
| 3 | 它對應哪個狀態轉換、誰有權推進？ | 規則會被實作繞過 |
| 4 | 當初否決了什麼、代價是什麼？ | 六個月後會重新發明 |
| 5 | 改了它，哪幾頁／哪些資料／哪些文件要動？ | 改動會漏 |
