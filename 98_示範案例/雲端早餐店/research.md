# research.md｜雲端早餐店訂餐管理系統

> 名詞：冪等（同一個操作重送多次，只會生效一次，例：付款按兩次只扣一次）／降級（主要管道失效時改用替代管道，例：通知送不出去就改看店內看板；不是把功能關掉）／快照（某個時間點的完整狀態；重連時先拿快照，再補後續變化）。

## 3. 架構選項比較

### 3.1 UI 組織：原生頁面 vs React

| 選項 | 優點 | 代價 | 判定 |
|---|---|---|---|
| 原生 HTML／CSS／JavaScript | 依賴少，適合目前 Prototype | 11 個介面與多角色狀態共享困難，容易重複狀態邏輯 | 保留作 Prototype，不作整合實作主架構 |
| React + TypeScript | 元件、狀態與表單可局部組合；適合多介面共享狀態 | 需要明確區分 UI state、server state 與事件訂閱 | **採用** |

React 官方文件將互動、狀態管理與外部系統同步列為核心使用情境；這符合訂單狀態、付款處理與事件訂閱的需求。

來源：

- [React Learn](https://react.dev/learn)
- [Managing State](https://react.dev/learn/managing-state)
- [Synchronizing with Effects](https://react.dev/learn/synchronizing-with-effects)

### 3.2 瀏覽器與服務交換：REST/JSON vs gRPC

| 選項 | 優點 | 代價 | 判定 |
|---|---|---|---|
| REST/JSON | 瀏覽器直接支援；請求、錯誤與資源邊界容易由前端檢查；適合本案命令與查詢 | 需要自行約定資源與錯誤格式 | **採用** |
| gRPC | 契約與型別明確，適合服務對服務的高效呼叫 | 瀏覽器需額外轉接；本案規模不足以抵銷邊界複雜度 | 不採用於第一切片 |

HTTP 方法的語意可直接表達查詢與命令；gRPC 官方文件則以 HTTP/2 與 Protocol Buffers 為核心，較適合已有多服務邊界的情境。本案先維持單一應用邊界，避免提前引入服務間協定。

來源：

- [MDN HTTP request methods](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods)
- [Introduction to gRPC](https://grpc.io/docs/what-is-grpc/introduction/)
- [gRPC over HTTP/2](https://grpc.io/docs/guides/wire/)

### 3.3 狀態同步：輪詢 vs SSE vs WebSocket

| 選項 | 優點 | 代價 | 判定 |
|---|---|---|---|
| 固定間隔輪詢 | 最容易理解與除錯；不需長連線 | 延遲與請求數受輪詢週期限制；多端尖峰時浪費查詢 | 作為降級與開發期 fallback |
| SSE | 伺服器可單向廣播狀態；瀏覽器有 `EventSource`；比雙向通道簡單 | 客戶端命令仍需另一條請求；需要重連與事件序號 | **採用：事件下行，命令走 REST** |
| WebSocket | 雙向即時；可同一通道傳命令與事件 | 連線生命週期、權限、重連與代理設定較複雜 | 第一切片不採用 |

本案的命令方向是顧客、店員或廚師送出操作；同步方向主要是服務將訂單狀態廣播給多個觀察者。因此使用一般命令請求加 SSE 下行事件，符合需求且少於全雙向通道。

來源：

- [MDN Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events)
- [Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

### 3.4 資料驗證：分散手寫檢查 vs 共用 schema

| 選項 | 優點 | 代價 | 判定 |
|---|---|---|---|
| 各端手寫檢查 | 初期快速 | 前後端規則容易漂移；錯誤格式不一致 | 不採用 |
| 共用 Zod schema | 可在 TypeScript 中定義、推導與執行檢查；適合命令與事件契約 | 需要維護 schema 版本與錯誤映射 | **採用** |

Zod 官方文件定位為 TypeScript-first schema validation，支援由 schema 推導型別，符合前後端共享資料契約的研究條件。

來源：

- [Zod](https://zod.dev/)
- [Zod Basics](https://zod.dev/basics)

### 3.5 資料保存：關聯式資料庫 vs 文件型資料庫

| 選項 | 優點 | 代價 | 判定 |
|---|---|---|---|
| 關聯式資料庫 | 訂單、品項、庫存、號碼與櫃位有明確關係；交易與唯一約束適合競爭寫入 | 需要設計 migration 與交易邊界 | **採用：託管 PostgreSQL 相容資料庫，供應商待定** |
| 文件型資料庫 | 原型欄位彈性高 | 跨物件一致性、唯一號碼與報表彙總需要額外規則 | 不採用於第一切片 |
| Serverless database | 部署與擴展負擔低 | 交易、延遲、鎖定、成本與供應商限制必須實測 | 作為供應商選擇，不是資料模型決策 |

PostgreSQL 官方文件提供交易隔離層級與交易特性的明確語意；本案的同單、號碼與庫存競爭需要先建立交易與唯一約束，再比較託管供應商。

來源：

- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
- [PostgreSQL SET TRANSACTION](https://www.postgresql.org/docs/current/sql-set-transaction.html)

## 4. 研究結論

1. 採用 React + TypeScript 作為整合介面層；Prototype 仍保留原有原生頁面作為驗證證據。
2. 採用 REST/JSON 作為命令與查詢邊界；第一切片不引入 gRPC。
3. 採用 SSE 傳遞訂單、取餐號碼、庫存與付款狀態事件；命令仍透過一般請求送出。
4. 採用共用 Zod schema 驗證命令、回應、事件與錯誤格式。
5. 採用關聯式資料模型與交易／唯一約束處理訂單、號碼、庫存與付款競爭；資料庫供應商留到部署研究決定。
6. 所有狀態事件都必須帶有物件 ID、狀態、版本或事件序號，避免舊事件覆蓋新狀態。
