# 00_工程推進紀錄｜學生作業範本

> 每週交一則。不是交「我做了什麼」，是交**「我怎麼發現、怎麼想、怎麼修、怎麼防」**。
> 一則 300–600 字，七欄都要填；沒有「我原本以為錯」的那一欄，這份作業就不算完成。

## 一、為什麼要寫這個

| 不寫的後果 | 寫了的好處 |
|---|---|
| 半年後只記得「改了一個東西就好了」 | 記得**為什麼一開始判斷錯** |
| 同類 bug 修第二次 | 每次留一道防護，錯誤不會回頭 |
| 別人接手要重問一次 | 文件裡有「當時的取捨」 |

## 二、格式（直接複製，逐欄填）

| 欄位 | 要寫什麼 | 反例 |
|---|---|---|
| **症狀** | 別人（或你）看到什麼現象。要具體到「畫面停在哪、數字是多少」 | 「壞掉了」 |
| **第一個想法** | 你**當下**的猜測，**即使是錯的也要寫** | （跳過不寫） |
| **真正原因** | 造成現象的機制，不是「哪一行改了就好」 | 「改個變數就好了」 |
| **怎麼確認** | 你做了什麼**證據動作**（看 console／對照版本／量數字／跑一次） | 「我覺得是這樣」 |
| **怎麼修** | 修的是根因還是症狀 | 「先這樣試試」 |
| **留下什麼防護** | 下次同類錯會紅的機制（檢查、測試、文件規則） | 「下次小心」 |
| **可搬走的原則** | 一句可以套用到別的地方的話 | 「學到了很多」 |

## 三、短範例（照這樣寫）

| 欄位 | 內容 |
|---|---|
| 症狀 | 交付物頁的內容只有手機那麼窄（約 280px），右邊一片空白 |
| 第一個想法 | 「CSS 寫錯了吧？」 |
| 真正原因 | 頁面借用了首頁的兩欄格線（側欄 280px ＋ 內容），但這頁只有一個子元素，所以被塞進第一欄 |
| 怎麼確認 | 打開樣式表看 `.app-shell` 的定義，再數這一頁的子元素只有一個 |
| 怎麼修 | 新增單欄版面 `.doc-shell`（最大 1100px），頁面改用它 |
| 留下什麼防護 | 寫進樣式表的註解：這個版面假設「有兩個子元素」；另加手機斷點 |
| 可搬走的原則 | 借樣式之前先看它的假設——「排版」類別可能內建了結構假設 |

## 四、評分（每則 100）

| 項目 | 比重 | 判準 |
|---|---:|---|
| 症狀具體 | 20 | 別人看描述能重現 |
| **錯誤的初始判斷** | 20 | 有寫，而且寫得出來（沒寫＝0） |
| 證據動作 | 25 | 至少一個可重複的確認步驟 |
| 防護 | 25 | 是機制，不是「小心一點」 |
| 原則 | 10 | 能套用到別的場景 |

## 五、交之前的四問

1. 這則紀錄，**沒有參與的人**看得懂嗎？
2. 「真正原因」能不能解釋「為什麼症狀長那樣」？
3. 防護**會不會紅**？（不會紅的防護＝沒有防護）
4. 如果把這則給 AI 讀，它會不會做出跟你一樣的推論？

## 六、五個常見失敗

| # | 失敗 | 為什麼扣分 |
|---|---|---|
| 1 | 只寫「修好了」 | 沒有過程，等於沒有學習 |
| 2 | 把「第一個想法」寫成正確答案 | 掩蓋了錯誤，就學不到 |
| 3 | 防護寫「以後注意」 | 不可執行 |
| 4 | 原因寫「某個變數錯」 | 這是現象，不是機制 |
| 5 | 一則寫三個問題 | 太淺；一則一個問題 |

## 七、繳交

- 檔名：`工程紀錄_第NN週_姓名.md`
- 位置：你自己的專案資料夾，**不要**改動教材
- 每則開頭寫：日期、遇到的畫面／檔案、花了多久
