# plan.md｜雲端早餐店訂餐管理系統

> 名詞：快照（某個時間點的完整狀態；重連時先拿快照，再補後續變化）／降級（主要管道失效時改用替代管道，例：通知送不出去就改看店內看板；不是把功能關掉）。

> 名詞：冪等（同一個操作重送多次，只會生效一次，例：付款按兩次只扣一次）。

> 本文件承接 `18_spec.md` v1.3 與 `research.md`。它決定第一階段的共同架構、資料模型、資料契約、驗證策略與風險；不重新定義業務需求。
>
> 版本：v0.1｜2026-11-13

> **狀態代號**：S0 尚未建立訂單（狀態機之前）／S1 草稿／S2 已下單／S3 已確認／S4 製作中／S5 製作完成（待店員確認）／S6 可取餐／S7 已取餐；SX1 缺貨／SX2 付款失敗／SX3 通知未送達／SX4 修改待確認。

## 1. 計畫目標

第一個垂直切片完成以下端到端路徑：

```text
顧客選餐
→ 建立訂單
→ 付款結果確認
→ 店員接單
→ 廚師開始／完成
→ 店員備妥入櫃
→ 顧客看到取餐號碼與櫃位
```

對應：`US-B-01`、`US-B-02`、`US-B-03`、`US-B-04`、`US-B-05`、`US-B-07`、`US-B-09`；主要驗收為 `AC-01`～`AC-17`、`AC-19`、`AC-22`。

## 2. 共同架構

```text
React + TypeScript UI
        │ REST/JSON 命令與查詢
        │ SSE 狀態事件
        ▼
單一應用服務
        │ 交易、唯一性、冪等與狀態轉換
        ▼
PostgreSQL 相容關聯式資料庫
```

### 2.1 邊界責任

| 邊界 | 責任 | 不負責 |
|---|---|---|
| UI | 顯示 11 個 SCR、六態、表單錯誤、重試與事件更新 | 決定業務狀態是否合法 |
| 應用服務 | 權限檢查、命令驗證、狀態轉換、交易、事件發佈與錯誤格式 | 直接讓 UI 修改資料庫 |
| 資料庫 | 物件保存、關聯、唯一約束、交易與查詢 | 推送畫面事件 |
| 付款 adapter | 封裝外部付款供應商、回傳付款狀態與冪等結果 | 改變訂單製作或取餐狀態 |
| 事件通道 | 將已提交的狀態變更傳給觀察者 | 成為唯一資料來源 |

### 2.2 第一階段部署假設

- 先以單一應用服務實例完成第一個垂直切片。
- 事件通道與資料庫都在同一個部署邊界內；多實例廣播列入後續容量研究。
- 付款供應商以 adapter 邊界隔離；未決定供應商前，不把供應商欄位寫進業務 UI。
- 角色切換只作為示範環境的明確 actor context；正式身份驗證與授權需先完成 `RQ-01`。

### 2.3 TASK-001 決策邊界

| RQ | 採用決策 | 對第一切片的約束 |
|---|---|---|
| RQ-01 | 示範 actor context；正式身份驗證與授權保留 | 不宣稱正式安全完成；命令仍檢查 actor scope |
| RQ-02 | 供應商中立付款 adapter；外部供應商與 callback 保留 | 只驗證付款狀態、冪等與 adapter 契約 |
| RQ-03 | 保留必要稽核資料；保存期限與刪除作業保留 | 不建立刪除作業，不宣稱隱私政策完成 |
| RQ-04 | 序號拒絕舊事件；斷線或缺號時重取完整快照 | 不做事件歷史補送 |
| RQ-05 | 單一應用服務實例 | 多實例廣播列入後續容量研究 |


## 3. 資料模型

### 3.1 核心資料

| 資料集合 | 主要欄位 | 約束／用途 | 對應規格 |
|---|---|---|---|
| `menu_items` | `id`, `name`, `price`, `availability` | 品項 ID 唯一；供應狀態可變更 | OBJ-01、T-01、T-10 |
| `orders` | `id`, `status`, `pickup_slot`, `customer_name`, `version` | 狀態只能依允許轉換前進；版本避免舊更新覆蓋 | OBJ-02、S1–S7 |
| `order_items` | `order_id`, `menu_item_id`, `quantity`, `unit_price` | 保存下單時價格快照 | OBJ-02、AC-01 |
| `payment_attempts` | `id`, `order_id`, `idempotency_key`, `status`, `provider_ref` | 同一冪等鍵不得產生兩次扣款結果 | OBJ-02（付款嘗試，技術實體）、SX2、AC-07～AC-09 |
| `inventory_items` | `menu_item_id`, `available_quantity`, `version` | 最後一份庫存不可被重複扣減 | OBJ-04、SX1 |
| `pickup_numbers` | `id`, `order_id`, `number`, `status` | 取餐號碼唯一；使用後不可再次分配 | OBJ-05、AC-13 |
| `lockers` | `id`, `locker_no`, `status`, `order_id` | 一個櫃位同時只能承接一筆可取餐訂單 | OBJ-06、T-06 |
| `order_events` | `id`, `order_id`, `type`, `from_status`, `to_status`, `sequence`, `created_at` | 保存狀態變更與事件序號；不取代目前狀態 | 非業務（審計／重連） |
| `revenue_entries` | `id`, `order_id`, `amount`, `created_at` | 一筆已完成訂單只產生一筆彙總來源 | OBJ-07、T-11、AC-25 |

> **OBJ-03 餐點的落點**：業務已定為「1 訂單 → N 份，每份一個」（見 `05_objects`），但**實作形式（獨立表或 `order_items` 拆份）留給 W11 的 OOD 決定**。
> 決定前：以 `order_items.quantity` 表示份數，餐點狀態聚合到訂單 S5，不另立欄位。
> `order_events` 屬**非業務物件**（審計與重連用），不需對應 OBJ。

### 3.2 狀態責任

- `orders.status` 是訂單目前狀態的唯一來源。
- `order_events` 只記錄合法狀態轉換與對外事件。
- S5 → S6 只能由店員命令完成；廚師完成命令只能將訂單留在 S5。
- 付款狀態與訂單製作狀態分開保存；付款「確認中」不可重送付款命令。
- 所有改變狀態的命令在同一交易中完成：驗證前置狀態、修改資料、寫入事件，再提交。

## 4. 契約

### 4.1 命令與查詢

| 方法 | 路徑 | 用途 | 主要驗收 |
|---|---|---|---|
| `GET` | `/menu` | 取得可供應品項 | AC-01、AC-05 |
| `POST` | `/orders` | 建立訂單草稿／送出訂單 | AC-01～AC-04 |
| `GET` | `/orders/:orderId` | 取得訂單快照 | AC-10、AC-11、AC-13 |
| `POST` | `/orders/:orderId/payment-attempts` | 建立一次付款嘗試 | AC-06～AC-09 |
| `GET` | `/staff/orders` | 取得店員待處理訂單 | AC-16、AC-18 |
| `POST` | `/orders/:orderId/confirm` | 店員接單，S2 → S3 | T-04 |
| `POST` | `/orders/:orderId/start` | 廚師開始製作，S3 → S4 | T-05、AC-20 |
| `POST` | `/orders/:orderId/complete` | 廚師完成，S4 → S5 | AC-12、AC-22 |
| `POST` | `/orders/:orderId/pickup-ready` | 店員入櫃，S5 → S6 | AC-13、AC-17 |
| `POST` | `/orders/:orderId/picked-up` | 顧客取餐，S6 → S7 | T-07 |
| `POST` | `/orders/:orderId/shortage` | 廚師回報缺貨 | AC-23 |
| `GET` | `/events` | 接收目前 actor 可見的狀態事件 | AC-10、AC-13、AC-16、AC-22 |

### 4.2 共用資料格式

所有命令、回應與事件使用共用 schema：

```text
CommandResult<T> =
  { ok: true, data: T, requestId: string }
  | { ok: false, error: { code, message, retryable, field? }, requestId: string }
```

事件至少包含：`eventId`、`sequence`、`type`、`entityId`、`status`、`occurredAt`。事件只在交易提交成功後發佈。

### 4.3 事件與重連

1. UI 開啟 `/events` 後先取得目前資料快照。
2. 服務只發佈已提交的狀態變更。
3. UI 收到事件時，只有事件序號較新才更新畫面。
4. SSE 斷線或序號不連續時，重新取得完整快照；不得猜測中間狀態。
5. 通知事件失敗不阻止看板透過查詢取得目前可取餐資料。

## 5. 交易與一致性策略

| 風險 | 策略 | 驗證 |
|---|---|---|
| 付款重複提交 | `idempotency_key` 唯一；相同鍵回傳原結果 | AC-07～AC-09 整合測試 |
| 同單競爭更新 | 以目前狀態與版本作條件更新；失敗回傳可重試衝突 | AC-12、AC-17、負向測試 |
| 取餐號碼撞號 | 資料庫唯一約束加交易內分配 | AC-13、競爭測試 |
| 最後一份庫存被超賣 | 在同一交易中檢查並扣減；不足則產生 SX1 | AC-05、AC-23 |
| 舊事件覆蓋新狀態 | 事件序號單調遞增；UI 拒絕舊序號 | AC-10、AC-11、AC-22 |
| 通知不可用 | 查詢看板與訂單快照作為替代路徑 | AC-14、NFR 降級 |

### 6.2 第一切片新增檢查

- schema contract：每個命令、回應、事件與錯誤範例都能通過共用 schema。
- state transition：非法 S5 → S6 廚師命令必須拒絕；店員命令必須成功。
- idempotency：同一付款冪等鍵重送只產生一個付款結果。
- concurrency：兩個取餐號碼分配與兩個最後庫存扣減不可得到相同資源。
- reconnect：事件中斷後重新取得快照，畫面不得回到舊狀態。
- acceptance：AC-01～AC-17、AC-19、AC-22 的每條結果回指 `18_spec.md`。
