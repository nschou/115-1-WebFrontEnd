# 00_工程推進紀錄｜七個「發現問題 → 想清楚 → 修好 → 留下防護」

> 這份不是成果報告，是**過程紀錄**。每一則都照同一個格式寫，因為工程能力就是這個格式：
> **症狀 → 第一個想法（可能是錯的）→ 真正原因 → 用什麼證據確認 → 怎麼修 → 留下什麼防護 → 可搬走的原則**。
>
> 為什麼要留這個？因為半年後你只會記得「那時候改了一個東西就好了」，而不記得「為什麼一開始判斷錯」。

---

## 案例 1｜畫面只停在「正在載入文件⋯」

| 欄位 | 內容 |
|---|---|
| **症狀** | 教材網站的閱讀器打開後一直顯示「正在載入文件…」，沒有任何錯誤畫面 |
| **第一個想法** | 「應該是網路或 CDN 掛了」——**錯** |
| **真正原因** | `reader.js` 裡 `extraFiles` 的變數宣告被刪掉，但下面的 `allowed` 還在用它 → 一載入就 `ReferenceError` → 整個初始化中止 |
| **怎麼確認** | ①打開 console 看到 `ReferenceError: extraFiles is not defined` ②用 `git show HEAD:<file>` 對照，確認舊版有這個宣告 |
| **怎麼修** | 補回宣告（並保留後來新增的 `demoLinks`） |
| **留下什麼防護** | `check-site.mjs`：用假 DOM 跑一次閱讀器管線，壞掉會變紅 |
| **可搬走的原則** | **「沒反應」不是訊息，是訊息被吞掉了。** 先看 console，不要先怪網路 |

## 案例 2｜「修好了」但使用者還是打不開

| 欄位 | 內容 |
|---|---|
| **症狀** | 修好案例 1 之後，使用者點交付物頁的連結，仍然只看到原始 Markdown |
| **第一個想法** | 「是不是快取？」——**又錯** |
| **真正原因** | **兩層問題**：①`deliverables.html` 的連結直接指向 `.md`（瀏覽器只會顯示純文字）②閱讀器的白名單只認 `guide-data` 列出的檔案，`D_交付物` 不在名單裡 |
| **怎麼確認** | ①檢查 HTML 的 `href` ②用假 DOM 模擬 `file=..%2FD_交付物%2FD1_決策書.md`，得到「不在允許清單」 |
| **怎麼修** | ①6 個連結改走 `reader.html?file=…` ②白名單放寬為「同源 ＋ `.md`／`.txt`／`.css`」 |
| **留下什麼防護** | `check-site` 增加兩個案例：①非名單檔案（`D_交付物`）要能開 ②閱讀器連結的**目標檔必須存在** |
| **可搬走的原則** | **「渲染器修好」≠「使用者能打開」。** 要驗的是**使用者走的那條路**，不是模組自己的單元 |

## 案例 3｜交付物頁只有手機那麼寬

| 欄位 | 內容 |
|---|---|
| **症狀** | `deliverables.html` 內容被擠在約 280px 的窄欄 |
| **第一個想法** | 「CSS 寫錯了吧？」 |
| **真正原因** | 頁面沿用了首頁的 `.app-shell`：它是「側欄 280px ＋ 內容」的兩欄格線；這個頁面**只有一個子元素**，所以被放進第一欄 |
| **怎麼確認** | 讀 `site.css` 的 `.app-shell` 定義，數一下子元素 |
| **怎麼修** | 新增 `.doc-shell`（單欄、最大 1100px、760px 以下轉單欄），頁面改用它 |
| **留下什麼防護** | 手機斷點與表格橫向捲動規則一併寫進 `site.css` |
| **可搬走的原則** | **借樣式之前先看它的假設。** 一個「看起來只是排版」的類別，可能內建了「你會有兩個子元素」 |

## 案例 4｜記憶資料庫讀寫全部失敗（disk I/O error）

| 欄位 | 內容 |
|---|---|
| **症狀** | 所有記憶查詢／寫入都回 `disk I/O error` |
| **第一個想法** | 「資料庫壞了」 |
| **真正原因** | 資料庫本身**沒壞**：複製到本機後 `integrity_check = ok`，12 張表都在；問題出在同步碟上的 `-wal`／`-shm` 與仍握著舊控制代碼的程序 |
| **怎麼確認** | ①備份 `db／-wal／-shm` ②複製到本機暫存開一次，跑 `PRAGMA integrity_check` 與 `wal_checkpoint(TRUNCATE)` |
| **怎麼修** | 在複本上把 WAL 併回主檔，覆蓋回原位置，刪掉殘留 `-wal`／`-shm` |
| **留下什麼防護** | 備份目錄 `backup-20261114/`；重要資料「先備份再動」 |
| **可搬走的原則** | **先確認「資料有沒有壞」，再決定「要不要修」。** 很多時候壞的是連線，不是資料 |

## 案例 5｜追溯鏈斷在「沒人檢查的地方」

| 欄位 | 內容 |
|---|---|
| **症狀** | 規格寫得很完整，但研究與計畫文件幾乎不回指需求 |
| **第一個想法** | 「大家都有讀 spec，應該沒問題」 |
| **真正原因** | 追溯是用「條件描述」接起來的（例如「1 秒四端一致」），不是用編號；所以**人看得懂、機器追不到** |
| **怎麼確認** | 統計 `REQ／AC／SD` 在各檔的出現次數：`research` 的 REQ 是 0、`plan` 的 REQ 也是 0 |
| **怎麼修** | ①`research` §2 加「REQ／SD」欄 ②`plan` 新增需求回指表 ③`tasks` 13 張卡加「完成需求」④`impact.mjs` 加 `--req` 模式 |
| **留下什麼防護** | 改一條需求時跑 `node impact.mjs --req REQ-012`，會列出要同步的所有文件 |
| **可搬走的原則** | **鏈條會斷在「沒有檢查器」的地方。** 只要某段交接沒有自動驗證，它遲早會鬆掉 |

## 案例 6｜「1 秒四端一致」——濃縮到看不懂

| 欄位 | 內容 |
|---|---|
| **症狀** | 學生（與 AI）對這句話各有解讀：有人做成「四張畫面長得一樣」 |
| **第一個想法** | 「寫得夠短，專業的人都懂」 |
| **真正原因** | 濃縮詞省略了**主體**（哪四端）與**判準**（什麼叫一致） |
| **怎麼確認** | 拿句子去問：「如果只照這句話做，你會做出什麼？」——答案不一致就是寫壞了 |
| **怎麼修** | 在 `18_spec` §8 開頭直接定義：四端＝顧客手機／店長訂單台／廚房顯示器／店內看板；一致＝同一個狀態＋相同號碼櫃位。另建 `00_名詞展開` 表（18 條） |
| **留下什麼防護** | 寫作三問：①第一次出現有展開嗎？②展開的是行為還是形容詞？③換人讀會做出不同的事嗎？ |
| **可搬走的原則** | **濃縮是給懂的人用的；文件是給不懂的人看的。** 第一次出現一定要展開 |

## 案例 7｜批次更新誤覆蓋了兩筆記憶

| 欄位 | 內容 |
|---|---|
| **症狀** | 想更新「閱讀器」相關記憶，結果兩筆不同記憶被寫成同一段 |
| **第一個想法** | 「用關鍵字比對一次改掉就好」 |
| **真正原因** | 用 `LIKE '%閱讀器%'` 一次選到兩列，然後套同一段內容 |
| **怎麼確認** | 改完立刻 `SELECT` 檢查受影響的列 |
| **怎麼修** | 用 id 精準改寫兩筆，刪掉重複的第三筆 |
| **留下什麼防護** | 批次更新前**先 SELECT 看會命中幾筆**；改完再 SELECT 驗證 |
| **可搬走的原則** | **批次操作前先看「會影響幾筆」。** 這和資料庫、和文件改名都一樣 |

## 方法總結：五步，順序不能反

| 步 | 動作 | 這七個案例的對應 |
|---|---|---|
| 1 | **重現**（把症狀變成可觀察的） | 看到「正在載入」、看到 280px |
| 2 | **縮小**（懷疑的範圍一次砍一半） | 先看 console，而不是先改 CDN |
| 3 | **找證據**（不是找靈感） | `git show HEAD`、`integrity_check`、統計 REQ 次數 |
| 4 | **修根因**（不是修症狀） | 補宣告、放寬白名單、加 REQ 欄 |
| 5 | **留防護**（讓同類錯誤下次會紅） | `check-site`、`--req`、名詞展開表 |

> **沒有第 5 步，就只是「這次剛好修好了」。**

## 什麼時候該停下來寫檢查

| 訊號 | 動作 |
|---|---|
| 同一個錯誤你修了第二次 | 立刻寫檢查 |
| 這個錯誤「表面看不出來」（例如只停在載入中） | 讓它變可見：狀態文字、console、檢查器 |
| 有人（含 AI）對同一句話做出不同解讀 | 展開名詞，並在第一次出現處定義 |
| 一個改動要同步三個以上地方 | 建索引或產生器，不要靠記憶 |

## 學生練習

1. 挑一個你最近修好的 bug，照這個格式寫一則（七欄都要填）。
2. 找出你專案裡「只有你懂」的三個詞，寫成一句話的展開。
3. 對你最常改的那份文件，問：如果明天有人改了一條需求，他怎麼知道要動哪些檔案？
