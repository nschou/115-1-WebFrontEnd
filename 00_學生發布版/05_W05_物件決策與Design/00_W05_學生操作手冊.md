# 第 5 週學生操作指南：物件、資訊流、決策與 Design

> 本週不是直接做漂亮畫面，而是先把 Blueprint 的候選方案定案，再把唯一服務基準交給 Design 與 W6 UX。
> 四個 AI Prompt 的完整可貼用版本在 `00_W05_PROMPTS.md`；本手冊說明每一步何時使用、如何人工檢查，以及如何從輸入產出下一份文件。

## 2. 開始前輸入檢查

逐項確認：

- [ ] `04_blueprint.md` 有角色、交接、例外、SD-01～SD-11 候選。
- [ ] `04_blueprint.md` 的候選沒有被標成採用方案。
- [ ] `03_cjm.md` 有最低點、痛點、機會與數位接觸點。
- [ ] `02_persona.md` 有主要使用者與支持角色。
- [ ] `01_market.md` 有市場限制與營運方向。

若缺少任何一項，先在 `00_open-questions.md` 記錄並回退補件；不要讓 AI 猜答案。

## 3. Step 1：建立 `05_objects.md`

### 3.1 從 Blueprint 盤點候選

逐列查看 `04_blueprint.md` 的角色任務與「對象」欄，先列出 5–8 個候選物件。物件必須四條都成立：

1. 至少兩個角色會碰它。
2. 它會影響某個角色的決策。
3. 它有生命週期或狀態會改變。
4. 它可以被持有、傳遞或更新。

不符合的內容改列為欄位、情緒、規則或一般描述，不要硬列成 OBJ。

### 3.2 填寫物件表

使用 `05_objects/05_objects_template.md`：

| OBJ | 物件 | 類型 | 擁有者 | 生命週期 | 涉及角色／端 |
|---|---|---|---|---|---|
| OBJ-01 | | 實體／紀錄／憑證／內容 | | | |

ID 一旦建立不要重編。若刪除物件，標記淘汰原因並保留原 ID。

### 3.3 補角色 × 物件 × 資訊需求

對每個重要物件至少列兩個角色：

| 角色 | 物件 | 要看到什麼 | 要做什麼決策 | 缺少會怎樣 |
|---|---|---|---|---|
| | | | | |

最後做可觀測性檢查：每個狀態轉換至少有一個角色需要知道；若角色需要知道卻沒有入口，列為服務斷點。

## 4. Step 2：建立 `06_infoflow.md`

對 `05_objects.md` 的每個主要物件回答「怎麼動、誰在等、會不會撞」。

使用 `06_infoflow/06_infoflow_template.md`：

| 物件 | 變更事件 | 尖峰量 | 誰要知道 | 一致性 | 競爭熱點 | 延遲容忍 | 動態原型 |
|---|---|---|---|---|---|---|---|
| OBJ-xx | | 業務量 | | 單一來源／可延遲 | | 秒／分／時 | 廣播／競爭／狀態機／彙總 |

填寫順序：

1. 寫會造成狀態改變的業務事件，例如「店員確認備妥」。
2. 寫尖峰業務量，例如「尖峰 3 分鐘約 40 單」，不寫 QPS。
3. 列出變更後誰必須知道，以及誰只是稍後查看。
4. 判斷同一物件是否只能有一個真相。
5. 列出可能同時搶同一物件的角色。
6. 由「誰在等」推導延遲容忍：≤1 秒、≤3 秒或≤1 小時。
7. 分類為廣播、競爭、狀態機或彙總型。

規則：只寫業務需求，不寫 Redis、訊息佇列、資料庫或 API。

## 5. Step 3：完成 `07_decisions.md`

### 5.1 逐條盤點 11 項決策

開啟 `04_blueprint.md` 的 SD-01～SD-11 候選，逐條確認有：

- 服務需求
- A／B／C 候選
- 候選優缺點
- 物件或資訊流依據
- 受影響的角色與交接

若某個 SD 沒有候選，先回到 Blueprint 補齊，不得直接選一個。

### 5.2 做三層方案分類

每個採用方案標記層次：

- 基本方案：人工操作或基礎數位工具。
- 規則自動化：依固定規則執行，不等於 AI。
- AI 增強：需要歷史資料才能預測或最佳化。

### 5.3 填寫決策定案表

每條 SD 必須填：

| 決策代碼 | 採用方案 | 理由 | AI 增強方向 | 導入條件 | 負責角色 | 代價與限制 |
|---|---|---|---|---|---|---|
| SD-01 | | | | | | |

理由必須同時回指：

- 人的需求：Persona、CJM 痛點或角色任務。
- 物的約束：物件屬性、生命週期或資訊流。

不能只寫「比較方便」「使用者喜歡」。

### 5.4 補操作流程與因果鏈

至少補：

- KDS 操作與訂單狀態流。
- 預估取餐時間的基本／規則／AI 三層。
- 缺貨同步的發現、停止、恢復、已下單處理。
- POS 與庫存的導入時序。

再填因果鏈：

| SD | 決策 | 依據 | 回溯來源 | 來源性質 | 驗證狀態 |
|---|---|---|---|---|---|
| | | | | 使用者指定／研究依據／案例假設／設計推導 | 未驗證／已檢查／已核准 |

## 6. Step 4：執行 Prompt 1，產出 Baseline 草稿

使用 `00_W05_PROMPTS.md` 的 Prompt 1，讀取：

人工檢查：

- [ ] 所有重要內容有來源或「待補證據」。
- [ ] Blueprint 候選仍標為候選。
- [ ] SD-01～SD-11 尚未被 AI 自行選定。
- [ ] 物件、角色、等待者、例外與交接都有進入草稿。
- [ ] 沒有混入按鈕、頁面、API 或技術架構。

## 8. Step 6：執行 Prompt 3 與 Prompt 4

### Prompt 3

讀取：

```text
08_service-design-baseline.md
09_DESIGN/09_DESIGN_prompts.md
09_DESIGN/09_DESIGN_template.md
```

輸出：`stitch-prompt-draft.md`。

檢查：三組風格候選的頁數、資訊架構、區塊順序與文案必須一致；只有色彩、字體、間距、圓角、動效等風格參數不同。

### Prompt 4

讀取：

```text
stitch-prompt-draft.md
09_DESIGN/stitch-prompt-checklist.md
08_service-design-baseline.md
```

輸出：`stitch-prompt-final.md`。

逐項執行 13 項清單。審查表保留在對話或另存紀錄；最後的 `stitch-prompt-final.md` 只保留可貼入 Stitch 的 Prompt，不要把審查表貼進去。

## 9. Step 7：Stitch、匯出與整併 Design

1. 把 `stitch-prompt-final.md` 貼入 Google Stitch。
2. 生成三組 IA 一致的樣張。
3. 比較並選定一組；記下選定理由與未採用風格。
4. 匯出 7 章原料為 `09_DESIGN_export.md`。
5. 依 `09_DESIGN/09_DESIGN_README.md` 與 `09_DESIGN_template.md` 整併。
6. 保留工具原文第 2–8 章，不自行潤飾原文。
7. 從 baseline 補第 1、9、10 章：DS-RATIONALE、DS-MOTION、DS-TRACE。
8. 產出 `09_DESIGN_audit.md`，記錄來源命中、矛盾、覆蓋率與待驗證項目。
9. 完成 `09_DESIGN.md` 後才建立 `10_tokens.css`。

如果 Stitch 不可用，使用 README 的 omp 無樣張模式，並將 token 與第 10 章標記為「待驗證」，不得宣稱已由樣張驗證。

## 10. `10_tokens.css` 檢查

Token 必須能回指 `09_DESIGN.md` 的設計契約。檢查：

- [ ] 顏色、字體、間距、圓角與動效都有來源。
- [ ] 沒有只改原始 token 卻沒有改到被引用的語意 token。
- [ ] 尚未由工具或實測確認的項目標記待驗證。
- [ ] `09_DESIGN_audit.md` 記錄 token 與來源的對照。

## 11. 本週交付檢查

- [ ] `05_objects.md` 的每個物件都通過四條物件判準。
- [ ] `06_infoflow.md` 每個主要物件都有事件、等待者、一致性、競爭與延遲。
- [ ] `07_decisions.md` SD-01～SD-11 為 11／11，開放選項為 0。
- [ ] `08_service-design-baseline.md` 是唯一服務基準。
- [ ] Prompt 1～4 的四個工作檔都存在且順序正確。
- [ ] `09_DESIGN.md` 有 10 章，工具原文 7 章未被改寫。
- [ ] `09_DESIGN_audit.md` 有三項指標與待驗證項目。
- [ ] `10_tokens.css` 能回指 Design 契約。
- [ ] 沒有用 Design 或 tokens 反過來改寫服務決策。
