# 04 UX README

## 目標

先把 Blueprint 的角色任務與 CJM 痛點整合成服務需求與 **US-B**，再由 US-B 推導資訊、狀態、線框與 SCR；完成 UX 後再產生有路徑的 **US-I** 與 **AC**。最後交給第 7 週的 `spec.md` 彙整，不在 spec 第一次設計。

> 記住一句話：**CJM 告訴你顧客在哪裡痛；Blueprint 告訴你誰要動手；US-B 說明值得做的價值；UX 把價值變成可操作的結構；US-I／AC 證明它能走、能驗。**

## 六步調研方法（先整合需求，再做 UX）

1. **服務需求索引**：先讀已凍結的 baseline，再把角色任務、交接、失敗點與 CJM 的痛點／機會放在同一列，補上物件。
2. **US-B**：用「作為〔角色〕，我想要〔任務成果〕，以便〔價值〕」寫業務版故事；此時不得出現頁面或按鈕。
3. **資訊與端別**：從任務句 B 的決策、baseline 物件屬性與資訊流推導元素、端別、任務流與狀態。
4. **UX 與線框**：建立 SCR、六態／例外、文案、互動與 Wireframe；每個元素都要有用途、來源與去處。
5. **US-I／AC**：將 US-B 對上實際路徑；再由狀態與業務規則寫 EARS AC，不由畫面外觀猜。
6. **走查與交接**：跑規則層／體驗層檢查，將 `10_tasks` 至 `15_review` 交給 W7 彙整成 `spec.md`。

> 為什麼不只從 CJM 開始？CJM 只有顧客一條線；Blueprint 才包含店員、廚師與設施等所有服務角色。

## AI 協作（四階段）

### 階段 1：建立服務需求索引與 US-B

```
請讀取已凍結的 @service-design-baseline.md、CJM 的痛點／機會、Blueprint 的角色任務／交接／例外，以及 W5 的物件清單。
不要產生任何 SCR 或畫面：
1. 每列整理：角色任務｜角色｜交接對象｜物件｜狀態轉換｜CJM 痛點／機會。
2. 標出顧客、店員、廚師、設施四端；指出哪些角色是設施。
3. 對每列寫 1 條 US-B：
   作為〔角色〕，我想要〔任務成果〕，以便〔價值〕。
4. 檢查：每列都有來源；US-B 沒有頁面、按鈕、API 或資料表詞。
5. 指出資料不足、交接不明或沒有價值理由的列。
```

### 階段 2：產生資訊與線框清單（附覆蓋率自檢）

```
依服務需求索引與 US-B，並引用物件／資訊流產生元素與線框清單。
每個元素一列：ID｜用途｜資料來源｜功能類型｜建議型態｜歸屬角色／任務。
每個線框一列：ID｜端｜承接任務｜承接狀態｜進入點｜離開點｜深度。
規則：
- 一個任務可以落在多個 SCR，但每個服務需求至少要有承接。
- 設施角色（取餐櫃、看板）必須有 SCR，端別寫「設施」。
- 每個操作元素補狀態改變／去處／回饋／失敗去處。
- 產生後附上：服務需求總數 N、已承接 M、覆蓋率、未承接清單。
```

### 階段 3：狀態機與文案

```
針對線框清單建立任務流、狀態表與文案。
狀態表（每頁 6 欄，缺一欄視為未完成）：
default／loading／empty／error／success／interrupted
每格寫：畫面顯示什麼、主要動作是什麼、給哪個 MSG 編號。
文案表（MSG）：ID｜類型（錯誤/空/成功/按鈕/載入）｜文字｜語氣依據。
規則：
- 錯誤文案要「指出怎麼修」，不是「你錯了」。
- 按鈕用動詞，不用「確定」這種無資訊的詞。
- 字數上限：按鈕 6 字、錯誤 30 字、空狀態 40 字。
```

### 階段 4：US-I 與 AC

```
先將 US-B 對應到實際故事路徑，再寫 AC：
1. 每條 US-I 列出會走過的 SCR（可多個）。
2. 每條 US-I 指回一條 US-B 與來源痛點。
3. 把狀態表、例外與業務規則翻成 EARS：
   When／While／Where／If…then ＋ the system shall…
4. 一條 AC 對應一個狀態轉換或禁止規則。
5. 不得出現 API、資料表、元件名稱。
```

## 驗收標準（8 條）

| # | 項目 | 標準 |
|---|---|---|
| 1 | 人工動作覆蓋率 | **100%**（少一條＝服務斷點；自動化動作另列） |
| 2 | 端別覆蓋 | 顧客／店員／廚房／設施 **四端都出現** |
| 3 | 設施角色 | 至少 1 個 SCR 端別為「設施」 |
| 4 | 狀態完整 | L3 的每一頁都有 6 欄狀態表 |
| 5 | 例外落點 | 4 個例外全部指定到 SCR |
| 6 | 文案 | 每個錯誤與空狀態都有 MSG；按鈕全是動詞 |
| 7 | Story 語言 | 通過「系統→店員」替換測試 |
| 8 | AC 覆蓋 | 每個狀態至少 1 條 AC |

### 可計算的四個指標

| 指標 | 公式 | 標準 | 抓什麼錯 |
|---|---|---|---|
| **人工動作覆蓋率** | 被 SCR 承接的**人工**動作 ÷ 人工動作總數 | 100% | 服務斷點 |
| **狀態覆蓋率** | 被頁面承接的訂單狀態 ÷ 狀態機狀態總數 | 100% | 有狀態沒有畫面 |
| **頁面過載度** | 單頁承接任務數 ／ 動作數 | ≤ 3 ／ ≤ 7 | 一頁塞太多 |
| **斷點率** | 沒有進入條件的頁面數 | 0 | 「這頁從哪來？」 |

> **注意**：覆蓋率只算「人工作業」。由決策指定自動化的動作（如 KDS 路由、推播、POS 記錄）應記入 `spec` 的系統行為，不得為了湊 100% 而硬造頁面。

## 常見錯誤

| 錯誤 | 症狀 | 修正 |
|---|---|---|
| 從 CJM 起手 | 只有 5 個顧客端頁面 | 回去盤點 Blueprint 後台動作 |
| 忘了設施角色 | 沒有看板／取餐櫃 | 端別必須有「設施」 |
| 只有 happy path | 狀態表只填 default | 6 欄缺一不可 |
| AC 寫成元件行為 | 「點擊後出現彈窗」 | 改寫成狀態轉換 |
| 文案寫成責罵 | 「錯誤！請輸入正確資料」 | 指出怎麼修 |
| 把 Story 當任務 | 「作為顧客我想要一個按鈕」 | 把「以便」寫成價值，不是動作 |
