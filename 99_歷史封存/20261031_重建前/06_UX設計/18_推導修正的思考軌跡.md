# 18 推導修正的思考軌跡：我們怎麼走到這裡

> 這份文件記錄的不是結論，是**過程**。
> 學生要學的其中一個核心技能是：**當某個東西推導不出來時，怎麼找到是哪一層的表述錯了。**
> 讀法：先看 §1 的八個回合，再看 §3「為什麼回滾是正常的」，最後做 §7 的練習。

---

## 一、八個回合：每一次都是「推不下去」逼出來的

### 回合 1｜只有「人」，沒有「物」

| | |
|---|---|
| 原本的想法 | Blueprint 寫角色、工作事項、對象，這樣就夠了 |
| 撞到什麼 | 要回答「菜單該長什麼樣」時，發現**沒有任何一份文件在管「物件」**——菜單、庫存、取餐號碼都只在「對象」欄出現過一次 |
| 修正 | 把「對象」升級成**物件（OBJ）**：類型、擁有者、生命週期、跨哪幾端；再加「角色 × 物件 × 資訊需求」 |
| 留下的規範 | 物件四判準（跨角色／影響決策／有生命週期／可傳遞）；可觀測性原則 |

**得到的教訓**：狀態機其實就是物件的生命週期。我們只做了一個物件（訂單），就以為做完了。

---

### 回合 2｜物件是靜態的，但有人在等

| | |
|---|---|
| 原本的想法 | 有了物件與屬性，資訊架構就完成了 |
| 撞到什麼 | 物件模型答不出三件事：**時序、傳播、競爭**——而系統架構要解的正是這三件 |
| 修正 | 補「資訊流」：動態原型（廣播／競爭／彙總／記錄）＋ 時效需求＋競爭熱點 |
| 留下的規範 | **延遲容忍是體驗參數，不是技術參數**（顧客 1 秒、廚房 3 秒、報表 1 小時）；只寫需求不寫方案 |

**得到的教訓**：把「誰在等」寫出來，技術問題才會自己浮現；先寫 Redis 的人，是在猜答案。

---

### 回合 3｜決策的依據只有「人」

| | |
|---|---|
| 原本的想法 | 每一項決策都能指回 Persona 痛點或 CJM 情緒，就夠了 |
| 撞到什麼 | 「為什麼要支援圖片上傳」「為什麼取餐號碼不能重複」——這兩題答不出來，因為依據不在人身上 |
| 修正 | 決策記**兩個方向**：受哪些物件影響（約束，進因果鏈）、影響哪些物件（產出，做變更分析）；依據＝**人的需求 ＋ 物的本質** |
| 留下的規範 | 寫法要指到屬性：「菜單品項.照片必填且會過期」，不能只寫「受菜單影響」 |

---

### 回合 4｜線框能看，但不能驗

| | |
|---|---|
| 原本的想法 | 畫出六態的線框，能切換狀態就夠了 |
| 撞到什麼 | 使用者問：「打開來看，驗證在哪裡？」——**能點不等於能驗** |
| 修正 | 三層：可點（流程通）→ 可查（動作對得到 AC）→ **可驗（做錯會紅）**；加入斷言、負向測試 |
| 留下的規範 | 不會失敗的檢查是說明書；會失敗的才是規格 |

---

### 回合 5｜全部綠燈，但沒人用過

| | |
|---|---|
| 原本的想法 | 23 條 AC 全部自動化、全部 PASS，就是做完了 |
| 撞到什麼 | 「規則全綠」證明的是規則被實作，**不證明好用** |
| 修正 | 兩層證據：規則層（機器，會紅）＋ 體驗層（人，會不通過）；入口頁同時顯示兩個數字 |
| 留下的規範 | 體驗層要有方法、owner、**數字型證據**；不得只寫「看起來不錯」 |

---

### 回合 6｜任務句裡混進了 UI

| | |
|---|---|
| 原本的想法 | 任務寫成「顧客在菜單頁按下送出，把訂單交給店員」 |
| 撞到什麼 | 使用者指出：**「在菜單頁按下送出」是 UX 的結果，不是需求**——不一定要這樣設計 |
| 修正 | 任務句改成 7 格，且**禁用介面詞**；「觸發」改成「前置業務狀態」 |
| 留下的規範 | 店長測試（他若反問「哪個畫面」就不合格）；任務只產生**問題**，不產生答案 |

**得到的教訓**：在需求文件裡寫「按鈕」，等於在需求階段就先做了設計決定。

---

### 回合 7｜設施被當成憑空出現的執行者

| | |
|---|---|
| 原本的想法 | 看板、取餐櫃是「支援層的執行者」，它們沒有 Persona、沒有情緒、沒有旅程，所以 CJM 生不出來 |
| 撞到什麼 | 使用者指出：**設施是給人用的**。自助繳款機取代收費員，顧客在它面前一樣會緊張（後面有人排隊）、一樣會困惑（投幣口在哪、優惠碼刷哪裡） |
| 修正 | 設施是**角色替代**：它替代了某個人的那段交接；旅程在顧客身上，只是交接對象換了 |
| 留下的規範 | 設施要標 `serves`（服務誰）／`substitutes`（替代誰）／`via`（透過誰）；**驗收基準＝被替代掉的那段人際互動** |

**推出來的三件事**：設施有三個設計義務（自我說明、錯誤自癒、佇列友善）；指標是「困惑自癒率 10 秒」；設施是**雙面**的（對顧客是前台、對員工是後台）。

---

### 回合 8｜US 該放在線框之前還是之後

| | |
|---|---|
| 原本的想法 | 一種順序：任務 → US → AC → 線框 |
| 撞到什麼 | 先寫 US 會寫出對不上畫面的故事；先畫線框會畫出沒有任務支撐的畫面 |
| 修正 | **US 出現兩次**：US-B（業務版，線框之前，用來確認「值得做」）＋ US-I（介面版，線框之後，可走、有 AC）；同時把 SCR 定義成**三件套**（資訊規格＋線框＋tokens） |
| 留下的規範 | 資訊流與頁面清單都排在線框**之前**；元素表要有「型態依據」 |

## 二、修正只有三種類型

| 類型 | 症狀 | 這次的例子 |
|---|---|---|
| **補漏** | 某個要素完全沒有住的地方 | 物件、資訊流、體驗層 |
| **換層** | 東西放錯樓層（把結果當需求） | 任務句混進 UI、決策只有人的依據 |
| **改序** | 順序錯，導致後面的推導對不上 | US 只出現一次、線框排在資訊流之前 |

**如果不是這三種，就不要改。** 這條能擋掉「凭感覺想改」。

## 三、為什麼「回滾修正」是現實專案的正常現象

### 3.1 三個現實理由

| 理由 | 說明 |
|---|---|
| **表述精度會隨理解提高** | 一開始只知道「要做點餐」，做到一半才知道「菜單需要照片」——這不是需求變更，是**需求具體化** |
| **下游會暴露上游的錯** | 畫線框時才發現任務寫不出狀態轉換；做驗證時才發現 AC 沒有來源 |
| **不改的代價比改更大** | 硬著頭皮做完，上線才發現「這一頁沒有人需要」 |

### 3.2 業界的對照

| 業界作法 | 對應我們的做法 |
|---|---|
| ADR（架構決策紀錄） | 每次修正寫「背景／選項／決定／代價／影響範圍」 |
| Sprint 內的需求澄清 | 任務句從三欄升級成七格 |
| 版本治理（語意化版本） | v6.4 → v7.0，並保留凍結舊版 |
| Retrospective | 「這次為什麼沒早點發現」寫進 lesson |

### 3.3 反例：不改會怎樣

```
任務句寫「顧客在菜單頁按下送出」
  → 線框照著畫（有按鈕）
    → 決策表沒機會討論「如果改成語音點餐呢」
      → AC 寫成「送出中不得再出現按鈕」（介面 AC 冒充業務 AC）
        → 換一種互動方式時，全部 AC 失效
```

**錯誤不會自己消失，只會被後面的層包起來。**

## 四、回滾的紀律（不是想改就改）

| 規則 | 內容 |
|---|---|
| **觸發條件** | 只有「某個要素推導不出來」才回滾——不是「覺得不好」 |
| **最小單位** | 只回滾出問題的**那一層**（這次是「表述層」），不動上游與無關下游 |
| **必留紀錄** | 每次修正寫 ADR：背景／選項／決定／代價／影響範圍／怎麼回滾 |
| **舊版凍結** | 不刪舊版，標記為凍結，讓人看得到演化 |
| **可檢查** | 修正後要能被 lint（否則只是換了說法） |

## 五、學生要學的三個技能

| # | 技能 | 具體做法 |
|---|---|---|
| 1 | **追問「這條規則從哪來」** | 每一條 AC、每一個元素，都要能指回任務句或物件屬性；指不回去就是憑空想的 |
| 2 | **用「推不出來」當偵測器** | 不要用「感覺不對」當理由；要說出「這裡缺一格，所以推不下去」 |
| 3 | **把修正留下紀錄** | 寫 ADR，讓下一個人（或三個月後的自己）不必重推一次 |

## 七、練習（三題）

1. **找斷點**：拿你的 Blueprint，挑一個設施，寫出它 `serves` 誰、`substitutes` 誰。寫不出來 → 這個設施沒有出處。
2. **換層**：把你的任務句中的介面詞全部畫掉，改寫成業務語言；改不動 → 這個任務其實還沒定義。
3. **留紀錄**：挑一個你改過的決定，寫一則 ADR（背景／選項／決定／代價／影響範圍）。

## 八、一句話

> **改，不是因為之前的錯；是因為我們現在有能力看見它錯在哪。**
> 一套不能被抓錯的方法，比抓錯一百次更危險。
