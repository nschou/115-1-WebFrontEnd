## 一、為什麼：設計階段的完整管線

第一性原理：為什麼設計階段要到規格書才算完成

核心事實：

軟體開發的本質是溝通：寫程式碼之前，必須先讓所有人對「要做什麼」有相同理解。理解不一致是返工的最大來源。

三個角色需要同一份文件：

需求端（老闆/使用者）：要確認「這就是我要的」

開發端（工程師）：要知道「要實作什麼、驗收標準是什麼」

AI（程式生成工具）：要有明確的指令與結構化輸入，才能穩定生成

如果只有旅程圖沒有規格書：旅程圖是體驗視角，但開發端不知道「每個功能叫什麼、使用者故事是什麼、驗收標準是什麼、畫面長什麼樣」。AI 更無法從一張旅程圖直接生成程式碼。

規格書是設計階段的終點，實作階段的起點：它把服務設計的所有成果（Persona、CJM、服務藍圖、UX/UI 分析、線框圖）濃縮成一份結構化文件。

因果鏈：

理解使用者 → 描述體驗旅程 → 連結前台後台 → 分析介面需求 → 畫線框圖 → 寫規格書
→ 三端共用同一份文件 → 溝通成本最低 → 返工最少 → AI 能穩定實作

完整管線：6 個步驟

Persona → CJM → Service Blueprint → UX/UI Analysis → Wireframes → Requirements.md
 角色人物誌  使用者旅程圖   服務藍圖        介面分析       線框圖      規格書

每一步的產出是下一步的輸入。缺任何一步，後面就會有盲點。

## 二、6 個步驟詳解

步驟 1：Persona（角色人物誌）

是什麼：一個虛構但真實的角色，代表一類使用者。不是統計數字，是一個有名字、有故事的人。

為什麼：

如果只說「使用者要點餐」，每個人腦中浮現的使用者不同

Persona 讓所有人討論時指著同一個人：「小王會怎麼做？」

有了具體的人，才能推導出真實的情境、目標與痛點

做什麼：為早餐店系統建立 3 個 Persona（顧客、店員、老闆）

怎麼做：每個 Persona 包含以下欄位：

| 欄位 | 說明 | 範例 |
|---|---|---|
| 姓名 | 虛構但真實的名字 | 王同學 |
| 基本資料 | 年齡、職業、生活狀態 | 20 歲，大二生，住宿舍 |
| 使用情境 | 什麼時候、為什麼會用 | 早上 7:30 趕 8:00 上課 |
| 目標 | 想達成什麼 | 快速拿到早餐不遲到 |
| 痛點 | 現在遇到什麼困難 | 排隊太久、不確定做好了沒 |
| 期望感受 | 希望感受到什麼 | 快、清楚、可信任 |
| 不期望感受 | 不希望感受到什麼 | 焦慮、混亂、被忽視 |

範例：顧客 Persona

王同學，20 歲，聯合大學大二生，住學校宿舍。
每天早上 7:30 起床，8:00 有課，中間只有 30 分鐘。
目標：在 30 分鐘內拿到早餐、趕到教室。
痛點：打電話點餐常佔線、到現場要排隊、不確定做好了沒。
期望感受：快速、清楚、可信任。
不期望感受：焦慮（怕遲到）、混亂（不知道進度）。

範例：店員 Persona

阿美，35 歲，早餐店正職員工，負責接單與出餐。
尖峰時段同時有 10 幾張單在跑。
目標：不漏單、不出錯、讓客人準時拿到。
痛點：口頭點餐容易聽錯、紙本單子找不到、不知道哪張先做。
期望感受：清楚、有序、有效率。
不期望感受：混亂、壓力、出錯。

範例：老闆 Persona

陳姐，45 歲，早餐店老闆，每天打烊後看數字。
目標：知道今天賺多少、什麼好賣、什麼該調整。
痛點：手算營收要 30 分鐘、不知道哪個品項利潤最好。
期望感受：數字清楚、能做決策。
不期望感受：一堆數字看不懂、不知道該怎麼改。

步驟 2：CJM（Customer Journey Map，使用者旅程圖）

是什麼：一個角色從開始到結束的完整體驗地圖，記錄每個階段的行動、接觸點、情緒、痛點與機會。

為什麼：

服務不是一個瞬間，是一段時間軸上的體驗

旅程圖讓你看見「整段體驗」，而不只看單一畫面

情緒曲線讓你發現「哪裡最痛」——那就是最該被數位化的地方

做什麼：為主要角色（建議顧客）繪製完整旅程圖

怎麼做：旅程圖包含以下欄位：

| 欄位 | 說明 |
|---|---|
| 階段 | 把旅程分成大階段（前、中、後） |
| 行動 | 使用者在做什麼 |
| 接觸點 | 透過什麼互動（網頁、通知、店員） |
| 情緒 | 當下的感受（用曲線或表情標示高低） |
| 痛點 | 哪裡可能出問題 |
| 機會 | 數位化能改善什麼 |

範例：顧客 CJM（雲端早餐店）

| 階段 | 行動 | �觸點 | 情緒 | 痛點 | 機會 |
|---|---|---|---|---|---|
| 點餐前 | 打開網站 | 首頁 | 期待 😊 | 載入慢 | 快速載入 |
| 點餐前 | 瀏覽菜單 | 菜單頁 | 專注 🤔 | 品項太多找不到 | 分群顯示 |
| 點餐中 | 選餐點 | 餐點卡片 | 滿足 😋 | 不確定總金額 | 即時金額 |
| 點餐中 | 加入購物車 | 購物車按鈕 | 確認 ✅ | 怕點錯 | 可修改數量 |
| 點餐中 | 送出訂單 | 確認頁 | 確認 ✅ | 怕填錯取餐時間 | 清楚確認 |
| 點餐後 | 等待取餐 | 通知 | 焦慮 😰 | 不知道進度 | 訂單狀態更新 |
| 點餐後 | 取餐 | 店面 | 釋懷 😊 | 找不到單號 | 取餐號碼 |

情緒曲線：期待 → 專注 → 滿足 → 確認 → 焦慮（最低點）→ 釋懷
→ 焦慮是最低點，所以「訂單狀態更新」是最該被數位化的功能。

步驟 3：Service Blueprint（服務藍圖）

是什麼：在 CJM 下方加上後台層，連結「顧客看到的」與「顧客看不到但系統在做的」。

為什麼：

CJM 只看前台，但每個前台接觸點背後都有後台行為支撐

如果只設計前台不管後台，就會出現「畫面很漂亮但資料沒記到」的情況

服務藍圖確保每個接觸點都有對應的系統行為

做什麼：把 CJM 的接觸點往下連到後台行為與支援系統

怎麼做：服務藍圖有 3 層 + 2 條線：

┌─────────────────────────────────────┐
│  前台（顧客看到的）                      		           │  ← 顧客直接體驗
├─────── 可見線（Line of Visibility）		      ──┤  ← 這條線上方顧客看得到
│  後台（顧客看不到但系統在做的）           		           │  ← 顧客不直接看到
├─────── 內部互動線（Line of Interaction）	          ┤
│  支援系統（基礎設施）                   		           │  ← 支撐後台的底層
└─────────────────────────────────────┘

範例：服務藍圖（顧客送出訂單這個接觸點）

| 前台（顧客看到） | 後台（系統在做） | 支援系統 |
|---|---|---|
| 顧客點「送出訂單」按鈕 | 系統記錄訂單資料 | 資料庫 |
| 畫面顯示「訂單已送出」 | 系統通知店員有新訂單 | 推播服務 |
| 顧客收到取餐號碼 | 系統生成取餐號碼 | 序號生成器 |
| —（顧客看不到） | 系統把訂單排入佇列 | 訂單佇列 |
| —（顧客看不到） | 店員端顯示新訂單 | 店員端介面 |

範例：服務藍圖（店員出餐這個接觸點）

| 前台（店員看到） | 後台（系統在做） | 支援系統 |
|---|---|---|
| 店員看到新訂單列表 | 系統按時間排序訂單 | 排序邏輯 |
| 店員點「開始備餐」 | 系統更新訂單狀態為「備餐中」 | 狀態機 |
| 店員點「出餐完成」 | 系統通知顧客可取餐 | 推播服務 |
| 顧客收到「可取餐」通知 | 系統更新訂單狀態為「已出餐」 | 狀態機 |

步驟 4：UX/UI Analysis（介面分析）（https://ns-wfe115-1.pplx.app ）

是什麼：從服務藍圖中找出「需要哪些畫面、每個畫面要有哪些元素」，把服務設計轉成介面需求。

為什麼：

服務藍圖告訴你「系統要做什麼」，但不告訴你「畫面長什麼樣」

UX/UI 分析是「服務設計」到「介面設計」的橋樑

先分析再畫線框圖，才知道每個畫面要放什麼、資訊層次如何安排

做什麼：列出系統需要的所有頁面，分析每個頁面的元素與資訊層次

怎麼做：

從服務藍圖的接觸點列出頁面：

| 接觸點（來自藍圖） | 對應頁面 | 角色 |
|---|---|---|
| 瀏覽菜單 | 菜單頁 | 顧客 |
| 加入購物車 | 購物車頁 | 顧客 |
| 送出訂單 | 訂單確認頁 | 顧客 |
| 等待取餐 | 訂單狀態頁 | 顧客 |
| 接單 | 店員訂單列表頁 | 店員 |
| 出餐 | 店員訂單詳情頁 | 店員 |
| 看營收 | 報表頁 | 老闆 |

分析每個頁面的元素：

| 頁面 | 主要元素 | 次要元素 | 資訊層次 |
|---|---|---|---|
| 菜單頁 | 餐點卡片（品名、價格、圖、加購按鈕） | 分群標題、搜尋框 | 分群 > 卡片 > 詳情 |
| 購物車頁 | 品項列表、數量加減、總金額 | 清空按鈕、繼續點餐連結 | 總金額 > 品項 > 操作 |
| 訂單確認頁 | 取餐時間、姓名、訂單摘要 | 送出按鈕、返回修改 | 取餐資訊 > 摘要 > 操作 |
| 訂單狀態頁 | 訂單狀態、取餐號碼 | 預計時間、明細 | 號碼 > 狀態 > 明細 |
| 店員訂單列表 | 訂單卡片（號碼、時間、品項） | 狀態篩選、排序 | 待處理 > 進行中 > 完成 |
| 報表頁 | 今日營收、熱門品項 | 時間篩選、趨勢圖 | 營收 > 品項 > 趨勢 |

步驟 5：Wireframes（線框圖）

是什麼：每個頁面的低精度佈局草圖，用方塊、線條、文字標示畫面結構與元素位置。不是最終設計，是結構藍圖。

為什麼：

直接寫程式碼會浪費時間在「位置不對、元素不對」的返工上

線框圖讓你在 5 分鐘內試一種佈局，而不是 5 小時寫完程式碼才發現不對

線框圖可以給需求端確認「畫面是這樣的」，確認後再實作

AI 也能從線框圖描述生成更準確的程式碼

做什麼：為每個頁面畫一張線框圖（手繪或數位工具皆可）

怎麼做：

根據 UX/UI 分析的元素清單，畫每個頁面

用方塊代表區塊，用文字標示內容

標注資訊層次（什麼最大、什麼最重要）

不需要配色、不需要美觀——只要結構清楚

步驟 6：Requirements.md（規格書）

是什麼：把前面所有成果濃縮成一份結構化文件，每個功能包含 4 個部分，讓需求端、開發端、AI 都能據此溝通與實作。

為什麼：

旅程圖是體驗視角，規格書是實作視角

規格書是設計階段的終點、實作階段的起點

有了規格書，AI 才能穩定生成程式碼（結構化輸入 → 穩定輸出）

有了規格書，開發端才知道驗收標準是什麼

做什麼：為每個功能寫一組規格，包含 4 個部分

怎麼做：每個功能包含以下結構：

## Feature: [功能名稱]

### User Story
作為 [角色]，我想要 [動作]，以便 [目標]。

### Acceptance Criteria（EARS 格式）
- When [觸發條件]，the system shall [系統回應]。
- While [狀態]，the system shall [系統行為]。
- If [異常情況]，then the system shall [錯誤處理]。

### Wireframes
- 菜單頁：見 wireframe_menu.png
- 購物車頁：見 wireframe_cart.png

EARS 格式說明

EARS（Easy Approach to Requirements Syntax）是一種結構化寫驗收標準的方法，用關鍵字把條件與回應分清楚：

| 類型 | 關鍵字 | 結構 | 適用場景 |
|---|---|---|---|
| 無條件 | shall | The system shall [回應] | 永遠要做的 |
| 事件驅動 | When | When [觸發], the system shall [回應] | 某事件發生時 |
| 狀態驅動 | While | While [狀態], the system shall [回應] | 某狀態持續時 |
| 可選 | Where | Where [條件], the system shall [回應] | 有此功能時 |
| 異常 | If...then | If [異常], then the system shall [回應] | 出錯時處理 |

範例：菜單瀏覽功能

## Feature: 菜單瀏覽

### User Story
作為顧客，我想要瀏覽分群的菜單，以便快速找到想吃的餐點。

### Acceptance Criteria
- When 顧客進入菜單頁，the system shall 顯示所有餐點，按「主餐、套餐、飲品、加購」分群。
- When 顧客點擊餐點卡片的「＋」按鈕，the system shall 將該餐點加入購物車並更新購物車數量。
- While 購物車有商品，the system shall 在頁首顯示購物車數量徽章。
- If 菜單載入失敗，then the system shall 顯示「菜單載入中，請稍候」的友善提示。

範例：送出訂單功能

## Feature: 送出訂單

### User Story
作為顧客，我想要確認訂單內容並送出，以便讓店員開始備餐。

### Acceptance Criteria
- When 顧客點擊「送出訂單」，the system shall 驗證取餐時間已選擇且姓名已填寫。
- When 驗證通過，the system shall 記錄訂單、生成取餐號碼、通知店員。
- When 驗證失敗，the system shall 在未填欄位旁顯示友善提示「請選取一個取餐時間」。
- While 訂單送出中，the system shall 顯示 loading 狀態並禁用按鈕。
- If 送出失敗，then the system shall 顯示「訂單尚未送出，請確認以下欄位」。

### Wireframes

## Feature: 店員接單與出餐

### User Story
作為店員，我想要看到新訂單並標記出餐狀態，以便不漏單且讓顧客知道進度。

### Acceptance Criteria
- When 有新訂單送出，the system shall 在店員端訂單列表頂部顯示該訂單。
- When 店員點擊「開始備餐」，the system shall 更新訂單狀態為「備餐中」。
- When 店員點擊「出餐完成」，the system shall 更新狀態為「已出餐」並通知顧客。
- While 訂單狀態為「備餐中」，the system shall 在列表中以黃色標示。
- If 店員端載入失敗，then the system shall 顯示「連線中，請稍候」。
