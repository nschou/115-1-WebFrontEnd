# 05 服務方案決策定案範本（第 5 週）

> 學生根據本範本產生兩個檔案：
> - `05_decisions.md` — 結論（11項決策定案 + 操作流程 + 因果鏈 + 設計交接，固定格式）
> - `05_decisions_rd.md` — 研究推導過程（每項決策的選擇理由 + 代價分析 + 三層分類論述）
>
> 輸入：`04_blueprint.md`（選項版，SD-01~SD-NN 的選項已列出，採用方案留空）
> 本範本把選項版轉為定案版——填入採用方案、理由、代價。

### 4. 操作流程（按需補充）

某些決策需要補充操作流程。以下為本案例需要的：

#### KDS 操作流程與訂單狀態流

```
訂單狀態流：接收(Received) → 製作中(Preparing) → 完成(Ready)
```

1. 訂單從數位點餐系統/POS 自動傳送到 KDS 螢幕
2. KDS 依路由規則將品項分派到對應工作站
3. 廚師在 KDS 上點擊確認接收 → 開始製作 → 完成
4. 計時器顏色變化提醒 urgency（綠→黃→紅）
5. KDS 自動通知店員「訂單完成」
6. **店員確認餐點備妥** → 放置取餐櫃 → **取餐櫃通知顧客取餐號碼**

關鍵區分：「廚師完成製作」≠「店員確認餐點可領取」——兩個不同狀態。

#### 預估取餐時間三層次

| 層次 | 機制 | 準確度 | 導入條件 |
|---|---|---|---|
| 基本版 | 固定值，店員可調整 | 依賴人工 | 無 |
| 規則版 | 品項標準時間 + 佇列計算 | 中等 | 需設定標準時間 |
| AI 版 | ML 模型動態預估 | 較高 | 需 KDS 歷史數據 |

#### 缺貨同步機制

| 環節 | 誰做 | 怎麼做 |
|---|---|---|
| 發現缺貨 | 廚師或店員 | 通知老闆 |
| 停止供應 | 老闆（或POS庫存連動） | 數位菜單標記缺貨 |
| 恢復供應 | 老闆 | 確認補貨後恢復 |
| 已下單缺貨 | 店員 | 通知顧客更換品項 |

#### POS 與庫存時序

```
階段1：POS 上線記錄銷售
階段2：設定食譜配方(recipe)自動扣庫存
階段3：低庫存門檻提醒
階段4(未來)：AI 庫存預測
```

## 05_decisions_rd.md 需包含的內容

### A. 每項決策的選擇推導

對每項決策（SD-01 到 SD-11），記錄：
- 列出的選項（從 04_blueprint.md 選項版）
- 每個選項的優缺點分析
- 為什麼選定這個方案（具體理由）
- 代價與限制是什麼
- 為什麼不是其他方案

### B. 三層分類的論述

對每項決策，說明：
- 基本方案是什麼
- 規則自動化是什麼（如適用）
- AI 增強方向是什麼（如適用）
- 為什麼初期採用某個層級，未來再升級

### C. 操作流程的推導

- KDS 操作流程為什麼需要（從哪個決策推導）
- 預估取餐時間為什麼分三層（從哪個需求推導）
- 缺貨同步機制從哪個決策推導
- POS 與庫存時序為什麼這樣安排

### D. 因果鏈推導

每條因果鏈記錄的推導過程：
- 決策依據從哪裡來
- 為什麼回溯到那個上游
- 來源性質為什麼是這個分類
- 驗證狀態為什麼是「未驗證」或「已檢查」

### E. 設計交接摘要的推導

- 品牌人格如何從 Persona 推導
- 情緒需求如何從 CJM 推導
- 為什麼風格預設標記「待提出候選」而非直接定義
