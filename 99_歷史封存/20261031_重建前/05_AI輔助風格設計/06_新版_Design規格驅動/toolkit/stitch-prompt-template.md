# Stitch Prompt 產生範本

> 本範本用於讓 AI（omp 或 Claude Artifacts）讀取服務設計 baseline 後，自動產生完整的 Stitch Prompt。
> 固定部分已預填，可變部分標注來源，AI 在資料不足時會提問。

---

## 給 AI 的作業指令

```
你是服務設計師的 AI 助手。請依照以下步驟產生餵給 Google Stitch 的 Prompt。

工作順序：
1. 讀取使用者提供的服務設計文件（檔名、內容）。不能只因看見檔名就宣稱已讀取——必須確認實際讀到內容。
2. 對照「必要欄位」清單，逐項檢查是否有對應資料。列出已找到和缺漏的項目。
3. 如果必要欄位有缺漏，提出 1-4 個關鍵問題，不輸出假裝完整的 Prompt。
4. 非必要欄位可使用範本預設值，或提出具名候選，但須標記為「設計推導，待討論」。
5. 資料足夠後，依固定結構組裝 Prompt，並分兩部分輸出：
   - A：可直接貼進 Stitch 的 Prompt（不含審查資料）
   - B：供學生審查的來源對照（每段的來源章節、假設、待確認事項）

規則：
- 不得捏造研究結果、使用者測試結論或老闆核准狀態。
- 可根據 baseline 資料提出設計候選（如風格預設、頁面安排），但必須標記「設計推導，待討論」。
- 三組候選樣張必須使用**相同的資訊架構與相同頁數**，只更換風格參數——否則無法比較。
- **不得自行新增或刪除畫面**；畫面清單以「需要生成的畫面」為準。
- 所有介面文案和說明使用繁體中文。
- 固定規則（標示「【固定】」的段落）不可修改。
- 可變欄位（標示「【從 baseline 填入】」的段落）從服務設計文件提取。
- 候選欄位（標示「【AI 提出候選】」的段落）由你根據資料推導。
```

## Prompt 固定結構

以下是需要產生的 Prompt 範本。標示 `【固定】` 的段落直接使用，標示 `【從 baseline 填入】` 的從服務設計文件提取，標示 `【AI 提出候選】` 的由 AI 推導並標記。

### A. 可直接貼入 Stitch 的 Prompt

```
為「【從 baseline 填入：專案名稱】」設計【從 baseline 填入：目標端（顧客端/店員端/廚房端）】系統。全部介面文案使用繁體中文。

【品牌背景】
【從 baseline 填入：市場名稱、老闆/買單者 Persona 的年齡/經驗/資金/目標、品牌人格。
 來源：baseline 第二章市場選擇 + 第四章 Persona】

【主要使用者】
【從 baseline 填入：主要使用者 Persona 的年齡/職業/使用情境、期望感受/不期望感受。
 來源：baseline 第四章 Persona】
如果有多個使用者角色，列出主要使用者即可，其他角色在後續階段延伸。

【服務流程】
【從 baseline 填入：CJM 的各階段名稱和顧客行為，標注情緒最低點。
 來源：baseline 第七章 CJM】

【需要生成的畫面】
【從 baseline 填入：從 CJM 接觸點和 Blueprint 前台行為推導 3-5 個代表畫面。
 每個畫面標注：名稱、包含的內容、對應的 CJM 階段。
 來源：baseline 第七章 CJM 接觸點 + 第八章 Blueprint 前台行為】
注意：畫面數量和內容是探索階段的初步配置，不是最終頁面規格。後續階段會延伸和調整。

【關鍵服務規則】
【從 baseline 填入：服務流程中必須遵守的業務規則。
 如：KDS 操作的狀態流、角色間的交接規則、設施角色的行為。
 來源：baseline 第五章角色表 + 第六章決策表中的操作流程 + 第八章 Blueprint】
如果 baseline 中沒有明確的服務規則，此段可省略。

【風格要求】
【AI 提出候選：根據 baseline 的品牌人格和情緒需求，提出 3 組風格預設。
 每組包含：名稱、情緒方向、色彩方向、字體方向、間距密度、圓角大小、動效速度。
 每組標注回溯來源（哪個 Persona 期望或 CJM 情緒需求）。
 標記為「設計推導，待討論」。
 如果 baseline 中有老闆指定的風格偏好或企業 CIS，優先使用，標記來源。】

【固定：UX 原則與無障礙要求】
以下為本課程所有專案共通的設計要求，不可修改：
- 確保 WCAG AA 對比度（內文 4.5:1，大字 3:1）
- 不僅靠顏色傳達狀態（搭配圖示或文字標籤）
- 鍵盤焦點可見
- 錯誤提示要幫助不是責備（友善文案 + 柔和色彩）
- 支援減少動效（prefers-reduced-motion）
- 中文可讀性（最小 12px，內文 16px）

【固定：禁止事項（本課程探索限制）】
以下為本課程的 AI 風格探索限制，避免生成千篇一律的 AI 風格：
- 不要紫藍漸層背景
- 不要過度 SaaS 感（千篇一律的儀表板配色）
- 不要抽象幾何背景裝飾
- 不要用 emoji 當圖示
- 不要全部圓角 16px
- 不要 Inter 字體加漸層文字標題

【裝置】
【從 baseline 填入：主要使用情境和裝置優先序。
 來源：baseline 第七章 CJM 使用情境。
 如：手機優先設計（通勤路上使用）。】
```

### B. 供學生審查的來源對照

AI 產生 Prompt 後，必須同時輸出以下審查資料（不貼入 Stitch）：

```
【來源對照表】
| Prompt 段落 | 來源（baseline 章節） | 資料性質 | 驗證狀態 |
|---|---|---|---|
| 品牌背景 | 第X章 | 使用者指定/研究資料/案例假設 | 已驗證/待驗證 |
| 主要使用者 | 第X章 | ... | ... |
| ... | ... | ... | ... |

【AI 提出的候選】
| 候選項目 | 推導依據 | 標記 |
|---|---|---|
| 風格預設A | 顧客Persona期望→情緒方向→參數值 | 設計推導，待討論 |
| ... | ... | ... |

【待確認事項】
- 風格預設參數值需經樣張比較確認
- 頁面清單是探索配置，第6週定最終規格
- ...
```

## 必要欄位檢查清單

AI 在產生 Prompt 前，必須逐項檢查以下欄位是否在 baseline 中有對應資料：

| # | 必要欄位 | baseline 來源 | 缺漏時 AI 應提問 |
|---|---|---|---|
| 1 | 專案名稱 | 文件標題 | 「專案名稱是什麼？」 |
| 2 | 市場選擇 | 第二章 | 「選定了哪個細分市場？」 |
| 3 | 老闆/買單者 Persona | 第四章 | 「買單決策者的 Persona 是什麼？」 |
| 4 | 主要使用者 Persona | 第四章 | 「主要使用者是誰？期望什麼感受？」 |
| 5 | 服務流程（CJM） | 第七章 | 「CJM 有幾個階段？情緒最低點在哪裡？」 |
| 6 | 畫面推導來源 | 第七章+第八章 | 「CJM 接觸點和 Blueprint 前台行為是什麼？」 |
| 7 | 服務規則 | 第五章+第六章+第八章 | 「有沒有必須遵守的服務規則（如角色交接、KDS 操作）？」 |
| 8 | 使用情境/裝置 | 第七章 CJM | 「主要使用情境是什麼？手機還是桌面優先？」 |

| # | 選填欄位 | 缺漏時處理 |
|---|---|---|
| 9 | 企業 CIS/風格偏好 | AI 提問：「有企業 CIS嗎？或老闆有指定風格偏好嗎？若無，AI 可提出候選。」 |
| 10 | 三組風格預設 | 如果 baseline 無風格預設，AI 根據品牌人格和情緒需求提出 3 組候選，標記「設計推導，待討論」 |
| 11 | 負面約束 | 使用範本固定值 |
| 12 | UX 原則 | 使用範本固定值 |
