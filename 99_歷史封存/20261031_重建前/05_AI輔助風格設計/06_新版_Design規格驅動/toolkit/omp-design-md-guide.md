# oh-my-pi (omp) 操作指南：無樣張模式（備援路徑）

> **定位：備援，不是主線。** 主線是 Google Stitch（有樣張佐證）。
> 本指南適用於：Stitch 連不上、額度用完、校園網路被封、或想在沒有工具的情況下先驗證 baseline 是否完整。
>
> **代價要先講清楚**：這條路產生的 token 是「從 baseline 推導出來的」，**沒有畫面佐證**。
> 所以第 10 章回溯表的驗證狀態**一律標「待驗證」**，不得標「已驗證」。

---

## 一、什麼時候用哪條路

| 情況 | 用哪條 | 產出標記 |
|---|---|---|
| 能連上 Stitch、有額度 | **正常模式**（`stitch-prompts.md`） | 前言寫「正常模式」 |
| 連不上／額度用完／要快速驗證 baseline | **無樣張模式**（本檔） | 前言寫「無樣張模式」 |
| 交作業 | 正常模式優先；用備援要在審計紀錄說明原因 | — |

> **兩個模式不可混用**：一份 Design.md 只能有一種來源。混用會讓第 10 章的回溯失真（有些 token 有樣張依據、有些沒有，卻標成一樣）。

## 二、事前準備

### 必要檔案

```
專案目錄/
  service-design-baseline.md    ← 第 2–5 週累積的決定版
  style-preset.md               ← 本次要用的風格預設參數（單一組）
  DESIGN.md                     ← 即將產生
```

### 關於 `style-preset.md`（很重要）

**不要在 Prompt 裡硬寫 hex。** 之前的版本把 `#1B6E8C`／`#E8743C` 寫死在指令裡，結果專案裡出現了**第三組色值**（對照表是 `#0B3C49`、匯出 token 是 `#134E4A`、指令卻是 `#1B6E8C`），三份互相矛盾。

正確做法：把參數集中在一個小檔，只寫一組，並註明來源。

```markdown
# style-preset.md
預設名稱：平衡現代
來源：baseline §3.4 三組風格預設（設計推導，待樣張驗證）
色彩：冷色基底 ＋ 暖色點綴（暖色只用於推薦標記與今日特餐）
字體：無襯線中性
間距：4px 基準，緊湊偏中
圓角：中（8–12px）
動效：中（200ms 為主）
限制：見 baseline §10 不可違反的限制
```

> 刻意**不寫 hex**。讓 omp 從「情緒方向」推導 token，再由人檢查是否與品牌人格一致；若你確實要指定 hex，只寫一組，並在第 10 章記錄它與工具值（或對照表）的落差。

### omp 設定

```bash
cd your-breakfast-shop-project
omp
/login openai-codex        # 或用 Groq / Gemini 免費方案
```

## 三、舊版 8 章 → v6 的 10 章對照

如果你沿用舊的 omp 指令，會產出「8 章」的檔案，**與課程的 10 章對不上**。請照下表轉換：

| 舊（8 章） | v6（10 章） | 說明 |
|---|---|---|
| Overview | **DS-RATIONALE（第 1 章）** | 品牌人格、體驗目標、服務承諾、情緒需求 |
| Colors | DS-COLOR（第 3 章） | |
| Typography | DS-TYPE（第 4 章） | |
| Layout | DS-SPACE（第 5 章） | |
| Elevation & Depth | DS-DEPTH（第 6 章） | |
| Shapes | DS-SHAPE（第 7 章） | |
| Components | DS-COMP（第 8 章） | |

| （舊版沒有） | **DS-TRACE（第 10 章）** | 回溯＋可替換性，必須新寫 |

## 四、產生 DESIGN.md（四步，不要一步到位）

### 第一步：盤點（**不要寫檔**）

```
請讀取 @service-design-baseline.md 與 @style-preset.md。
先做盤點，不要產生內容、不要寫檔：
1. baseline 的品牌人格、核心體驗目標、服務承諾、情緒需求各是什麼？列出來並附章節。
2. 有哪些「不可違反的限制」？列成清單。
3. baseline 的 11 項決策（SD-01~SD-11）中，哪些會影響 UI 元件？
4. 若要產生第 9 章（動效），從 baseline 的哪裡可以推出「節奏檔位」？
5. 你認為資料不足的地方有哪些？列 1–4 個問題等我回答。
```

### 第二步：產生 10 章（寫入檔案）

```
依 @06_designmd_template.md 的 10 章結構，產生 @DESIGN.md。

規則：
1. 第 1 章：每個形容詞都要標「定律／慣例」，慣例必附反面案例，每列附 baseline 來源（章節＋原文片段）。
2. 第 2–8 章：YAML frontmatter 要有完整 tokens（色彩／字體／間距／圓角），body 7 章齊全。
3. 第 9 章：時長只能取 150／200／250／300ms；目的填「裝飾」的一律在降級欄寫「全關」。
4. 第 10 章：回溯表每列標「驗證狀態」與「可替換性」；因為本模式無樣張，**驗證狀態一律「待驗證」**，不得寫「已驗證」。
5. 每章標上穩定 ID（DS-RATIONALE … DS-TRACE）。
6. 第 2–8 章外層加凍結標記註解。
7. 最後列出：N（token 總數）、M（已回溯數）、覆蓋率。
```

### 第三步：自審（強制輸出）

```
請檢查你剛才產生的 @DESIGN.md，輸出：
1. 你最不確定的 3 條設計決策，並說明原因。
2. 第 1 章的每個形容詞，在第 2–8 章有沒有對應的值？沒有的列出來。
3. 第 1 章說「緊湊」，第 9 章的時長是多少？兩者一致嗎？
4. 第 10 章的驗證狀態有沒有任何一條寫成「已驗證」？如果有，改成「待驗證」。
5. 覆蓋率是多少？未覆蓋的 token 有哪些？
```

### 第四步：寫入並回報

```
請把結果寫入 DESIGN.md，然後回報：
- 檔案路徑
- 10 章是否齊全
- 採用的風格預設
- 標為「待驗證」的項目清單
```

## 五、驗證 DESIGN.md 有沒有生效（實作階段）

這一步不屬於「產生規格」，屬於「驗證規格」。但強烈建議當天做完，否則你不知道自己寫的東西能不能用。

### 5.1 生成測試頁

```
請讀取 @DESIGN.md，生成「等待取餐進度頁」的 HTML/CSS。
所有色彩、字體、間距、圓角都使用 DESIGN.md 的 tokens（CSS 變數）。
等待頁的留白要比其他頁多（用 lg/xl 間距）——因為這是 CJM 情緒最低點。
按鈕要有 normal/hover/active/focus/disabled 五種狀態。
寫入 progress.html。
完成後列出你用了哪些 CSS 變數與值。
```

### 5.2 改一個 token，看有沒有連動

```
我把 DESIGN.md 的 primary 改成 #FF0000，請重新讀取 @DESIGN.md 並更新 progress.html。
完成後告訴我 primary 的新值是什麼。
```

若回報 `#FF0000` → 規格生效；若仍是原值 → 沒有讀到檔案，檢查 `@DESIGN.md` 引用或 skill 設定。**驗證完記得改回。**

> 這一步順便驗證了第 10 章的「可替換性」：如果改一個 token 就讓版面崩掉，表示某個「可換」項其實被寫成了「連動」，要回去修正契約。

## 六、常見問題

**Q：omp 產生的 DESIGN.md 格式不對怎麼辦？**
A：先確認有沒有餵 `06_designmd_template.md`。格式問題九成是「沒給格式範本」。另外可貼官方規格的 YAML 範例當參考。

**Q：無樣張模式可以交作業嗎？**
A：可以，但要在審計紀錄寫明原因，且第 10 章全部標「待驗證」。評分時「有樣張」的組別在 A1 會有優勢——因為我們的判準是「可回溯到樣張」。

**Q：Stitch 和 omp 產生的 DESIGN.md 差在哪？**
A：
- **Stitch**：依 Prompt 生成畫面，同時生成該專案的設計系統 → 匯出 7 章。**有畫面佐證**，是主線。
- **omp**：讀 baseline 的文字描述直接寫規格。**沒有畫面**，token 是推導值，只適合當備援或快速驗證 baseline 完整性。

**Q：兩個都跑，然後挑好的合併？**
A：不行。混用會讓第 10 章的回溯失真。要嘛全部用 Stitch、要嘛全部用 omp；若要換來源，等於換版，要走 `06_designmd_template.md` 的換版程序並更新版本指紋。

**Q：Groq 免費額度夠嗎？**
A：產生一份 10 章 DESIGN.md 約需 3–5 輪對話，在每日 1,000 次請求／200k tokens 內。但大量生成多頁前端程式碼會耗盡，實作階段建議換 ChatGPT Plus 或 DeepSeek API。
