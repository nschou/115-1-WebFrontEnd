## 一、為什麼要先做決定版

**【固定——以下內容由課程提供，不需修改】**

### 第一性原理推導

```
服務藍圖是「業務描述」轉向「工程描述」的轉換點
→ 轉換點之前，可以列選項、討論可能性
→ 轉換點之後，要進入風格、介面、程式碼
→ 工程化需要明確的輸入，不能帶著開放問題
→ 所以在服務藍圖階段，必須把所有服務設計的決定都做完
→ 從「選項版」變成「決定版」
→ 這份決定版就是後續所有工程化工作的需求來源
```

### 什麼是「決定版」

| | 選項版（第 2-4 週） | 決定版（本週） |
|---|---|---|
| 支援需求 | 列出多種可能（App/電話/現場） | 選定一個方案，附理由 |
| 角色配置 | 「老闆兼任或另聘」 | 明確決定誰擔任什麼 |
| 服務方案 | 比較選項和考量 | 最終選擇 + 代價與限制 |
| 用途 | 討論和思考 | 工程化的輸入 |

**【固定內容結束】**

## 二、市場選擇是投資方向的決定

| 欄位 | 填什麼 | 資料性質 | 範例 |
|---|---|---|---|
| 選定市場 | 細分市場名稱 | 使用者指定（教授/老闆） | 新型數位複合式連鎖 |
| 選擇理由 | 為什麼選這個市場 | 研究依據+使用者指定 | 數位化高、系統需求豐富、適合教學 |
| 約束鏈 | 市場選擇如何約束後續 | 設計推導 | →目標客群→Persona→CJM→Blueprint→風格 |

資料性質標記：`使用者指定` = 教授或老闆指定；`研究依據` = 來自行業研究資料；`案例假設` = 教學假設；`設計推導` = 從上游推導

## 十、設計交接摘要

此章節是 baseline 到 Design.md 的橋樑。只記錄已確定的設計相關資訊，不含完整 Design.md。

| 項目 | 填什麼 | 範例 |
|---|---|---|
| 品牌人格 | 從 Persona 推導的品牌形容 | 俐落、現代、可信賴 |
| 核心體驗目標 | 從顧客 Persona 推導 | 高效、清楚、安心 |
| 服務承諾 | 從 Blueprint 前台推導 | 決定→快速找到；等待→隨時知道 |
| 情緒需求 | 從 CJM 推導 | 放大科技感；避免混亂焦慮 |
| 企業 CIS | 如有，記錄品牌色和標準字 | 無（新創，無 CIS） |
| 老闆風格偏好 | 如有 | 無明確指定 |
| 禁用事項 | 本課程探索限制 | 不要紫藍漸層、不要 SaaS 感等 |
| 待提出候選 | 尚未決定的設計項目 | 三組風格預設（待設計師提出） |
| 不可違反的限制 | 無障礙和基本要求 | WCAG AA、中文可讀、手機優先 |

**注意**：三組風格預設不在 baseline 中定義——它們在 Design.md 流程中由設計師提出、AI 生成樣張、老闆比較選定。baseline 只記錄「待提出候選」。
