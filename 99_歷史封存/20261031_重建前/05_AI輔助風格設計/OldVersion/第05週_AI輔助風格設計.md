# Part A：服務設計完整成果——決定版

## 一、為什麼要先做決定版

### 第一性原理推導

```
服務藍圖是「業務描述」轉向「工程描述」的轉換點
→ 轉換點之前，可以列選項、討論可能性
→ 轉換點之後，要進入風格、介面、程式碼
→ 工程化需要明確的輸入，不能帶著開放問題
→ 所以在服務藍圖階段，必須把所有服務設計的決定都做完
→ 從「選項版」變成「決定版」
→ 這份決定版就是後續所有工程化工作的需求來源
```

### 什麼是「決定版」

| | 選項版（第 2-4 週） | 決定版（本週） |
|---|---|---|
| 支援需求 | 列出多種可能（App/電話/現場） | 選定一個方案，附理由 |
| 角色配置 | 「老闆兼任或另聘」 | 明確決定誰擔任什麼 |
| 服務方案 | 比較選項和考量 | 最終選擇 + 代價與限制 |
| 用途 | 討論和思考 | 工程化的輸入 |

## 二、市場選擇是投資方向的決定

### 選擇的邏輯

第 2 週分析了 6 種早餐業細分市場。選擇哪一個細分市場，就是老闆的投資方向決定——它決定了目標客群、價值主張、經營目標、資源限制，進而決定 Persona、角色配置、CJM、服務藍圖、風格、功能、系統。

**在現實中**：這由企業老闆根據自己的資源、能力和市場判斷來決定。

**在本課程中**：由教授指定，選定「新型數位複合式連鎖」。

### 為什麼選「新型數位複合式連鎖」

| 選擇理由 | 說明 |
|---|---|
| 數位化程度高 | 數位點餐占比高，系統需求豐富，適合資工系學生實作 |
| 客單價適中 | $110-180，有足夠的服務設計空間（不是純粹拼低價） |
| 系統需求豐富 | 預約、取餐、狀態追蹤、會員——功能多樣 |
| 有明確痛點 | 等待焦慮、品項太多、進度不明——可設計解決方案 |
| 角色分工清楚 | 店員、廚師、店長——角色結構適合教學 |

### 選擇如何約束後續一切

```
選定「新型數位複合式連鎖」
→ 目標客群：彈性工時者、年輕上班族（如張家豪）
→ 老闆傾向：推動數位化，App 點餐占比目標 50%+
→ 企業風格：現代、高效、科技感
→ 顧客期望：高效科技感、舒適
→ CJM 情緒需求：放大科技感、避免混亂
→ Blueprint 服務方案：偏向數位化方案
→ 風格方向：冷色、無襯線、俐落（風格假設，需比較驗證）
→ 功能需求：數位點餐、進度追蹤、取餐通知
→ spec.md → 前端實作
```

**注意**：市場選擇約束了方向，但不唯一決定每個方案。例如「數位複合式」約束了「偏向數位方案」，但「用 App 還是網頁」仍需比較決定。

## 六、服務方案決策表

### 市場定位帶來的需求

「新型數位複合式連鎖」包含三個關鍵詞，每個都帶來特定需求：

| 關鍵詞 | 帶來什麼需求 | 影響的決策 |
|---|---|---|
| 數位 | 顧客接觸點和營運環節以數位化為主——但不是每個環節都必須數位化 | 訂單接收、廚房顯示、進度通知、取餐看板、支付、菜單、銷售記錄 |
| 複合式 | 品項多樣化，需要分群、分類呈現 | 菜單系統、點餐流程 |
| 連鎖 | 需要數據累積支援展店決策——但初期 1 店可分階段導入 | 銷售記錄、庫存、顧客經營、數據分析 |

「順理成章」不代表某個方案是唯一選擇——而是市場定位提高了某些方案的優先度，服務設計師仍需從營運需求、成本與限制做決定。

以 KDS 為例，完整推導是：

```
數位點餐為主（決策1）+ 尖峰不漏單需求
→ 廚房需統一接收訂單、辨識製作順序、回報進度
→ 比較紙單、口頭、顯示器
→ 選擇 KDS，保留故障備援
```

### 方案分類原則

每項決策的候選方案分為三個層次：

| 層次 | 說明 | 舉例 |
|---|---|---|
| 基本方案 | 靠人工操作或基礎數位工具 | 紙本訂單、人工喊號、人工盤點 |
| 規則自動化 | 系統按設定規則自動執行，不需要 AI | POS 銷售扣庫存、低庫存門檻提醒、售完自動下架 |
| AI 增強 | 機器學習模型根據歷史數據預測或優化 | AI 預估取餐時間、AI 需求預測、AI 製作排程建議 |

重要區分：規則自動化是現代 POS/KDS 的標準功能，不需要 AI。例如 POS 根據食譜配方自動扣減庫存、品項售完自動從菜單下架，都是規則自動化。AI 增強需要累積歷史數據才能發揮價值——初期 1 店數據量可能不足，因此多數 AI 選項列為「未來導入方向」，不是初期採用方案。

以下每項從選項中做出最終決定，不再留下「A 或 B」作為答案。

### 決策 1：訂單接收方式

| 項目 | 內容 |
|---|---|
| 需求 | 讓顧客能方便地下單，同時達成老闆數位點餐 50%+ 目標 |
| 市場定位帶來的需求 | 「數位」→數位點餐是主要管道，現場點餐是輔助 |
| 候選方案 | **基本：** A. 數位點餐為主 + 現場口頭輔助　B. 現場口頭為主　C. 混合並重　**AI 增強：** D. 數位點餐 + AI 推薦（根據歷史訂單、時段推薦品項） |
| 比較依據 | 顧客便利性、數位化目標、尖峰效率、實施成本、AI 推薦準確度 |
| 採用方案 | **A. 數位點餐為主**（數位首頁/數位菜單），保留現場點餐作輔助 |
| 理由 | 選定「數位複合式」市場，數位化是核心競爭力；老闆目標 App 占比 50%+；張家豪期望高效科技感 |
| AI 增強方向 | 累積會員資料後可導入 D。與決策 6（菜單）、決策 10（會員）的推薦能力共享同一底層，非三套獨立 AI |
| 導入條件 | AI 推薦需會員系統 + 歷史訂單資料 |
| 負責角色 | 顧客下單；店員協助現場點餐 |
| 代價與限制 | 初期數位點餐占比可能不到 50%，需推廣；不熟悉數位的顧客需現場協助 |

### 決策 2：廚房接收訂單方式

| 項目 | 內容 |
|---|---|
| 需求 | 廚師能及時收到訂單，尖峰不漏單 |
| 市場定位帶來的需求 | 數位點餐為主後，廚房需統一接收多管道訂單——KDS 是高優先候選 |
| 候選方案 | **基本：** A. KDS（數位廚房顯示器）　B. 紙本訂單　C. 口頭叫號　**規則自動化：** KDS 自動路由品項到對應工作站、計時器顏色變化提醒（標準 KDS 功能）　**AI 增強：** D. KDS + AI 製作排程建議（根據品項製作時間、佇列長度建議順序，保留廚師覆核） |
| 比較依據 | 即時性、視覺排序、漏單風險、成本、AI 排程效益 |
| 採用方案 | **A. KDS** |
| 理由 | 尖峰不漏單是店長最大痛點；KDS 可視覺化排序、計時提醒，降低漏單風險 |
| AI 增強方向 | 尖峰量大時可導入 D：AI 建議製作順序——但保留廚師覆核與調整權，AI 不替代廚師判斷 |
| 導入條件 | AI 排程需累積品項製作時間數據 |
| 負責角色 | 廚師操作 KDS 狀態；店員確認備妥與交付 |
| 代價與限制 | 設備費 1-2 萬；停電時需紙本備案 |

#### KDS 操作流程與訂單狀態流

KDS 的標準操作流程（參考 [RestaurantManage](https://restaurantmanage.com/en/help/kitchen-display/)、[Fresh KDS](https://www.fresh.technology/blog/what-is-a-kds)、[Tcang](https://www.tcang.net/kds-full-form-kitchen-display-system.html)）：

```
訂單狀態流：接收(Received) → 製作中(Preparing) → 完成(Ready)
```

1. 訂單從數位點餐系統/POS 自動傳送到 KDS 螢幕（< 1 秒）
2. KDS 依路由規則將品項分派到對應工作站
3. 廚師在 KDS 上點擊確認接收 → 點擊開始製作（計時器啟動）→ 點擊完成
4. 計時器顏色變化提醒 urgency（綠→黃→紅）
5. KDS 自動通知店員「訂單完成」
6. **店員確認餐點備妥** → 放置取餐櫃 → **取餐櫃通知顧客取餐號碼**

**關鍵區分**：「廚師完成製作」和「店員確認餐點可領取」是兩個不同狀態——廚師在 KDS 標記 Ready 後，店員需確認餐點確實備妥、放置取餐櫃，才通知顧客。不要把這兩步合併。

### 決策 3：進度更新與通知方式

| 項目 | 內容 |
|---|---|
| 需求 | 顧客能即時知道訂單進度，降低等待焦慮（CJM 最低點） |
| 市場定位帶來的需求 | 「數位」→數位通知是基本；CJM 最低點在這裡，值得投入最多心力 |
| 候選方案 | **基本：** A. 數位推播 + 店內看板　B. 店員喊號　C. 僅店內看板　**規則自動化：** KDS 狀態變更自動觸發推播　**AI 增強：** D. 數位通知 + AI 預估取餐時間（ML 模型根據佇列、品項、歷史製作時間動態預估） |
| 比較依據 | 即時性、顧客安心感、科技感、成本、預估準確度 |
| 採用方案 | **A. 數位進度通知 + 店內看板**，搭配基本版預估時間 |
| 理由 | CJM 最低點是「等待取餐」焦慮；張家豪期望「高效科技感」；數位通知讓顧客在通勤路上也能看到進度 |
| AI 增強方向 | CJM 痛點是「不知道要等多久」。AI 預估取餐時間直接回答顧客最焦慮的問題 |
| 導入條件 | AI 預估需 KDS 累積歷史製作時間數據 |
| 負責角色 | KDS 自動觸發通知；店員在例外時手動調整預估時間 |
| 代價與限制 | 需開發推播功能；通知可能被忽略；AI 預估需累積數據才能準確 |

#### 預估取餐時間的三個層次

| 層次 | 機制 | 準確度 | 導入條件 |
|---|---|---|---|
| 基本版 | 下單時告知固定值「預計 X 分鐘」，店員可目測調整 | 依賴人工判斷 | 無 |
| 規則版 | 品項標準製作時間 + 佇列數量 × 平均製作時間 | 中等，不考慮品項組合變異 | 需設定品項標準製作時間 |
| AI 版 | ML 模型學習歷史製作時間，考慮品項組合、佇列、時段、人員配置 | 較高，動態調整 | 需 KDS 歷史數據 |

參考：[Fresh KDS](https://www.fresh.technology/blog/why-fresh-kds-is-building-an-ai-powered-order-prediction-system) 的 AI 預估模型使用 KDS 的實際訂單完成時間數據訓練，在 5 分鐘誤差內的準確率從一般平台的約 35% 提升到 85%。但本案例初期 1 店數據量有限，建議先採基本版，KDS 上線後升級規則版，累積數據後再評估 AI 版。

### 決策 4：取餐號碼顯示

| 項目 | 內容 |
|---|---|
| 需求 | 顧客能清楚看到自己的取餐號碼（CJM 痛點：號碼字太小） |
| 市場定位帶來的需求 | 「數位」→電子看板是基本 |
| 候選方案 | **基本：** A. 店內電子看板（大字體）　B. 紙本號碼牌　**規則自動化：** KDS 完成時自動更新電子看板　**數位增強（非 AI）：** C. 電子看板 + QR 碼取餐確認（掃碼核對訂單，防止拿錯） |
| 比較依據 | 可見性、科技感、成本、防呆能力 |
| 採用方案 | **A. 店內電子看板（大字體顯示）** |
| 理由 | 解決「號碼字太小」痛點；數位化方向；大字體可從遠處看到 |
| 數位增強方向 | 可加入 C：QR 碼取餐確認——顧客掃碼後系統比對訂單，防止拿錯餐。這是數位方案，不是 AI |
| 導入條件 | QR 碼確認需開發掃碼功能 |
| 負責角色 | KDS 自動更新看板；取餐櫃通知顧客取餐號碼 |
| 代價與限制 | 需購買看板設備；看板位置需在顧客等待區視線範圍內 |

### 決策 5：支付方式

| 項目 | 內容 |
|---|---|
| 需求 | 讓顧客方便付款，同時支援數位化記錄 |
| 市場定位帶來的需求 | 「數位」→線上支付為主；「連鎖」→支付記錄是數據來源 |
| 候選方案 | **基本：** A. 線上支付為主 + 現場付現　B. 僅現場付現　**規則自動化：** 支付完成自動更新訂單狀態　**AI 增強：** C. + AI 異常訂單偵測 |
| 比較依據 | 顧客便利性、數位化記錄、信任感、實施成本、風控需求 |
| 採用方案 | **A. 線上支付為主 + 保留現場付現** |
| 理由 | 數位化記錄支援老闆「數據驅動」目標；線上支付降低現場排隊；保留付現照顧不使用數位支付的顧客 |
| AI 增強方向 | 展店後訂單量大再考慮；優先評估支付服務商已有的風控能力，而非自建 |
| 導入條件 | AI 風控需大量交易數據 |
| 負責角色 | 系統處理線上支付；店員處理現場付現 |
| 代價與限制 | 線上支付有手續費（約 1.5-2%）；需處理退款流程 |

### 決策 6：菜單資訊維護

| 項目 | 內容 |
|---|---|
| 需求 | 確保顧客看到的菜單是最新的（品項、價格、供應狀態） |
| 市場定位帶來的需求 | 「數位」→數位菜單；「複合式」→品項多需分群分類 |
| 候選方案 | **基本：** A. 數位菜單系統（老闆手動更新）　B. 紙本菜單　**規則自動化：** POS 庫存連動——品項售完自動標記缺貨、自動下架　**AI 增強：** C. + AI 動態排序（根據銷量、時段自動調整品項排序） |
| 比較依據 | 更新即時性、品項供應狀態同步、成本、推薦精準度 |
| 採用方案 | **A. 數位菜單系統**（老闆負責更新），POS 上線後加入規則自動化 |
| 理由 | 數位化核心；品項供應狀態需即時同步；老闆掌握菜單決策權 |
| AI 增強方向 | 累積銷售數據後可導入 C。與決策 1（點餐推薦）、決策 10（會員推薦）共享推薦能力 |
| 導入條件 | AI 排序需累積銷售數據 |
| 負責角色 | 老闆更新菜單內容；系統自動標記缺貨 |
| 代價與限制 | 老闆需花時間維護；停電時需有紙本備案 |

#### 缺貨同步機制

| 環節 | 誰做 | 怎麼做 |
|---|---|---|
| 發現缺貨 | 廚師或店員 | 發現食材不足時通知老闆 |
| 停止供應 | 老闆（或 POS 庫存連動自動） | 在數位菜單標記缺貨；POS 上線後，庫存歸零自動下架 |
| 恢復供應 | 老闆 | 確認補貨後恢復供應狀態 |
| 已下單缺貨處理 | 店員 | 通知顧客更換品項（見藍圖例外情況） |

### 決策 7：銷售記錄方式

| 項目 | 內容 |
|---|---|
| 需求 | 記錄銷售資料，支援老闆「數據驅動成長感」 |
| 市場定位帶來的需求 | 「數位」+「連鎖」→POS 是基本配備；數據分析是展店決策的基礎 |
| 候選方案 | **基本：** A. POS 系統　B. 紙本記帳　**規則自動化：** POS 自動記錄客單價、品項銷量、時段統計、日報週報　**AI 增強：** C. POS + AI 銷售預測（ML 根據歷史數據、天氣、節假日預測品項銷量） |
| 比較依據 | 數據分析能力、自動化程度、成本、預測精準度 |
| 採用方案 | **A. POS 系統** |
| 理由 | 老闆目標包括「數據驅動」；POS 自動記錄客單價、數位點餐占比、品項銷量；支援展店決策 |
| AI 增強方向 | 累積數據後可導入 C。參考 [Wingstop Smart Kitchen](https://www.techdogs.com/td-articles/trending-stories/how-ai-and-automation-are-reshaping-fast-food-chains) 用 100+ 數據點預測 15 分鐘區間需求；[產業研究](https://www.pygmalios.com/insights/drive-thru-analytics-qsr)指出 ML 需求預測可降低預測誤差達 52% |
| 導入條件 | AI 預測需多個月銷售數據，含天氣、節假日等外部因素 |
| 負責角色 | POS 自動記錄；老闆查看報表 |
| 代價與限制 | POS 月費或買斷；需培訓員工使用 |

### 決策 8：庫存盤點方式

| 項目 | 內容 |
|---|---|
| 需求 | 掌握品項供應狀態，避免顧客點了沒有的 |
| 市場定位帶來的需求 | 「數位」→初期人工可接受；「連鎖」→半自動化是目標 |
| 候選方案 | **基本：** B. 人工每日盤點　**規則自動化：** C. POS 上線後，銷售自動扣庫存（recipe-based deduction），低庫存門檻提醒　**AI 增強：** D. + AI 庫存預測（根據銷售速度、歷史數據、季節預警低庫存） |
| 比較依據 | 精確度、即時性、成本、實施難度、預警即時性 |
| 採用方案 | **B → C（分階段）：初期人工每日盤點，POS 穩定後啟用庫存串接** |
| 理由 | 初期控制成本；人工盤點建立基線數據；POS 穩定後設定食譜配方串接庫存 |
| AI 增強方向 | 半自動穩定後可評估 D。注意：POS 銷售扣庫存和低庫存提醒是規則自動化（[標準 POS 功能](https://merchants.doordash.com/en-us/blog/pos-systems-for-restaurants)），不是 AI |
| 導入條件 | AI 預測需累積銷售 + 庫存數據 |
| 負責角色 | 店員每日盤點；系統自動扣庫存（POS 上線後）；老闆審核差異 |
| 代價與限制 | 初期精確度依賴人工；庫存串接需設定食譜配方 |

#### POS 與庫存的時序釐清

決策 7 採用 POS，決策 8 寫「導入 POS 後半自動」——這不是延後 POS 上線，而是**延後庫存串接**：

```
階段 1：POS 上線，記錄銷售（決策 7）
階段 2：設定食譜配方（recipe），每筆銷售自動扣減食材（決策 8 規則自動化）
階段 3：低庫存門檻提醒（規則自動化）
階段 4（未來）：AI 庫存預測（AI 增強）
```

POS 的 recipe-based 扣庫存是[業界標準功能](https://merchants.doordash.com/en-us/blog/pos-systems-for-restaurants)：每道菜對應食譜配方中的食材數量，銷售時自動扣減。品項售完時可[自動從菜單下架](https://www.therestauranthq.com/technology/restaurant-inventory-management-software/)（稱為「auto-86'ing」）。

### 決策 9：環境清潔流程

| 項目 | 內容 |
|---|---|
| 需求 | 維護店內環境，讓顧客用餐感受舒適 |
| 市場定位帶來的需求 | 「數位」不強制清潔數位化——清潔是人工行為 |
| 候選方案 | **基本：** B. 人工 SOP（標準作業程序）　**規則自動化：** A. 數位排程提醒（定時提醒清潔、完成紀錄）　**AI 增強：** C. AI 排程建議（根據客流低峰時段建議清潔時間） |
| 比較依據 | 可靠度、成本、數位化效益、排程優化程度 |
| 採用方案 | **B. 人工 SOP** |
| 理由 | 清潔是人工行為，數位化效益低；SOP 確保一致性；省下系統成本投入更有價值的數位化 |
| AI 增強方向 | 低優先度。先比較固定排程的 SOP 是否足夠；AI 排程只能是輔助，不能延後必要清潔 |
| 導入條件 | AI 排程需 POS 客流數據 |
| 負責角色 | 店員執行清潔；店長查核 |
| 代價與限制 | 依賴員工遵守 SOP；需定期檢查和培訓 |

### 決策 10：顧客經營與會員系統（新增）

| 項目 | 內容 |
|---|---|
| 需求 | 累積顧客資料，支援回訪率與個人化服務 |
| 市場定位帶來的需求 | 「連鎖」→會員系統有助展店，但初期 1 店非必備 |
| 候選方案 | **基本：** C. 暫不導入獨立會員系統，用 POS 記錄顧客資料　**規則自動化：** A. 數位會員系統（會員資料、集點、消費記錄）　**AI 增強：** B. + AI 個人化推薦（根據歷史訂單推薦品項、預測回訪週期） |
| 比較依據 | 回訪率提升、個人化程度、實施成本、數據需求 |
| 採用方案 | **C. 暫不導入獨立會員系統**，初期用 POS 記錄顧客消費 |
| 理由 | 初期 1 店，會員系統效益尚未體現；先用 POS 累積顧客資料；展店前再導入 |
| AI 增強方向 | 展店後導入 A，穩定後升級 B。與決策 1（點餐）、決策 6（菜單）的推薦共享同一能力 |
| 導入條件 | 會員系統需確認顧客識別方式（手機號碼/會員卡號）和資料使用同意 |
| 負責角色 | 店員詢問手機號碼；系統記錄消費 |
| 代價與限制 | 初期無會員經營，回訪率依賴產品品質和位置 |

### 決策 11：經營數據分析（新增）

| 項目 | 內容 |
|---|---|
| 需求 | 將銷售數據轉化為經營洞察，支援老闆「數據驅動成長感」 |
| 市場定位帶來的需求 | 「數位」+「連鎖」→數據分析是核心能力，不是附加功能 |
| 候選方案 | **基本：** A. POS 報表（手動查看：日報、週報、品項銷量）　**規則自動化：** POS 自動生成報表、設定異常提醒（連續下降、客單價偏低）　**AI 增強：** B. AI 經營儀表板（自動洞察品項趨勢、時段熱區、生成式摘要） |
| 比較依據 | 洞察深度、自動化程度、成本、決策支援能力 |
| 採用方案 | **A. POS 報表（手動查看）** |
| 理由 | 初期數據量小，POS 基本報表足夠；老闆有數據分析能力，可自行解讀 |
| AI 增強方向 | 數據累積後可升級 B。注意區分三種能力：數字報表（規則自動化）、預測（AI）、生成式摘要（AI）。生成式摘要須能回到原始數據核對 |
| 導入條件 | AI 預測需歷史數據；生成式摘要需確保可追溯 |
| 負責角色 | 老闆查看報表；系統自動生成 |
| 代價與限制 | 初期需老闆手動分析；可能錯過數據中的早期趨勢 |

# Part B：從服務設計到 Design.md

## 十、為什麼：Design.md 的第一性原理

### AI 協同開發的趨勢

DESIGN.md 是 [Google Labs 於 2026 年 4 月開源](https://github.com/google-labs-code/design.md)的設計系統規範格式（Apache-2.0 授權，GitHub 23,000+ 星）。它放在專案根目錄，作為 AI 編碼助手讀取的**設計系統唯一來源**。格式為 YAML frontmatter（機器可讀 tokens）+ Markdown body（人類可讀理由），不只包含色碼和字體，還包含**每個設計決策的理由**——讓 AI 生成程式碼時有明確依據，而不是每次重新猜測。Google Stitch 原生支援 DESIGN.md 的生成、匯入和匯出。

### 第一性原理推導

```
服務設計決定版告訴我們「顧客要感受什麼」
→ 感受需要透過視覺語言來傳達
→ 視覺語言需要被系統化定義（否則不一致）
→ 系統化的視覺語言就是設計系統
→ 設計系統需要被文件化（否則無法傳達給開發者和AI）
→ 這份文件就是 Design.md
→ Design.md 包含：理由 + 色彩 + 字體 + 間距 + 元件 + 佈局 + 動效
→ 每個決策都要回溯到服務設計的依據
→ 這樣 AI 生成程式碼時才「有憑有據」
```

### style-brief.md 進化成 Design.md

之前的 style-brief.md 只是「為什麼」——從服務設計萃取的風格依據。design-tokens.css 只是「怎麼做」——CSS 變數實作。但學生缺少一個具體的方法論，把這兩者串起來，讓每一步都有憑有據。

**Design.md 是「為什麼 + 是什麼 + 怎麼做」的完整文件**——包含設計理由、規格定義、和實作指引，一份文件讓 AI 和人都能理解。style-brief.md 不是獨立文件，而是 Design.md 的「設計理由」章節。

### 轉譯公式

**服務設計決定版 → 設計理由 → 品牌人格 → 視覺語言系統 → Design.md**

**注意**：從「高效科技感」到「冷色」是一個風格假設，不是唯一正確的推導。需要比較多個方向，由 AI 生成提案，人工審查後決定。

### 1. 設計理由（Design Rationale）

**使用情境**：當需要向 AI、開發者或設計師解釋「為什麼做這個設計決策」時。

**是什麼**：從服務設計決定版萃取的風格依據，是 Design.md 的第一個章節。包含品牌人格、核心體驗目標、服務承諾、情緒需求。

**為什麼**：
- 如果 Design.md 只有色碼和字體，AI 知道「用什麼」但不知道「為什麼」
- 不知道「為什麼」就無法判斷「什麼時候可以變通」
- 例如：AI 知道主色是深青，但不知道「因為 CJM 最低點需要安心感」→ 它可能在付款頁用了亮色，破壞信任感
- 設計理由讓 AI 在生成程式碼時能理解「為什麼」，從而做出符合服務目標的判斷

**做什麼**：把服務設計決定版的關鍵資訊萃取出來，作為後續所有設計決策的上游依據。

**怎麼做**：
1. 拿服務設計決定版（Part A）
2. 萃取 4 項：品牌人格、核心體驗目標、服務承諾、情緒需求
3. 每項標注來源決策編號
4. 範例：品牌人格「俐落、現代、可信賴」（來源：老闆目標+顧客期望）

### 2. 色彩系統（Color System）

**使用情境**：所有視覺元素的情緒傳達——背景、文字、按鈕、卡片、通知。

**是什麼**：一組有**語義角色**的色彩定義。不只是色碼清單，而是每個色彩有明確的角色（背景、表面、主色、文字、語義色），以及使用規則。

**為什麼**：
- 色彩是情緒最直接的視覺載體
- 語義角色確保一致性（UX 原則一）——所有頁面用同一套角色，不會每頁不同
- 語義角色讓 AI 理解「這個色用在什麼情境」——不只是「這個色叫 primary」

**做什麼**：定義色彩語義角色 + 色碼值 + 使用規則。

**怎麼做**：
1. **從情緒需求推導色彩方向**（風格假設，非唯一推導）
   - 期望「高效科技感」→ 假設A：冷色系 / 假設B：暖色但克制
2. **用 AI 生成多個色彩提案**（Google Stitch 或 Claude Artifacts）
3. **人工審查**：每個色彩問「這傳達了什麼情緒？跟 CJM 的需求一致嗎？」
4. **定義語義角色**：
   ```css
   --color-primary: #1B6E8C    /* 深青——傳達安心感，用在 CTA 和重要操作 */
   --color-bg: #F5F7F8         /* 冷色基底——傳達高效科技感 */
   --color-error: #C0392B      /* 錯誤——不責備的紅，搭配友善文案 */
   ```
5. **定義使用規則**：主色只用在一個地方（CTA），不要到處都是

### 3. 字體系統（Typography System）

**使用情境**：所有文字內容的呈現——標題、內文、按鈕文字、標籤、通知。

**是什麼**：字體家族（用什麼字）、字級比例尺（多大）、字重（多粗）、行高（多鬆）的系統化定義。

**為什麼**：
- 字體傳達品牌人格——無襯線=現代俐落，有襯線=古典權威
- 字級比例尺建立視覺層次（UX 原則二）——標題大、內文中、標籤小
- 行高影響閱讀舒適度——緊湊服務行高小，質感服務行高大
- 如果不定義系統，每頁字級不一致→違反 UX 原則一

**做什麼**：定義標題字/內文字家族、字級比例尺（xs→2xl）、字重、行高。

**怎麼做**：
1. **從品牌人格推導字體方向**——俐落現代→無襯線、幾何感
2. **選定字體家族**（1-2 種，不超過）
3. **定義字級比例尺**（比例制，不是隨意數字）：
   ```css
   --text-xs: 12px   /* 標籤、說明 */
   --text-sm: 14px   /* 輔助文字 */
   --text-base: 16px /* 內文 */
   --text-lg: 20px   /* 小標 */
   --text-xl: 28px   /* 大標 */
   --text-2xl: 40px  /* Hero */
   ```
4. **定義行高**：內文 1.5-1.6，標題 1.15-1.25
5. **回溯**：為什麼用無襯線？→ 品牌人格「俐落現代」→ 來源：老闆目標+顧客期望

### 4. 間距系統（Spacing System）

**使用情境**：所有元素的空間關係——元素間距、區塊間距、頁面邊距。

**是什麼**：基於一個**基準單位**推導出的間距比例尺。所有間距都是基準單位的倍數。

**為什麼**：
- 間距決定服務節奏——緊湊=快速高效，寬鬆=質感舒適
- 基準單位確保一致性——所有間距都是 4px 的倍數，不會出現 7px 或 13px
- 間距系統是 UX 原則一（一致性）和 UX 原則三（Hick's Law 分群）的基礎

**做什麼**：定義基準單位和間距比例尺（xs/sm/md/lg/xl）。

**怎麼做**：
1. **從服務節奏推導密度方向**——尖峰快速點餐→緊湊但不擁擠
2. **選定基準單位**（通常 4px 或 8px）
3. **推導比例尺**：
   ```css
   --space-xs: 4px   /* 元素內緊密間距 */
   --space-sm: 8px   /* 元素間 */
   --space-md: 16px  /* 區塊內 */
   --space-lg: 24px  /* 區塊間 */
   --space-xl: 40px  /* 大區塊間 */
   ```
4. **特殊規則**：CJM 最低點頁面（等待取餐）留白用 lg/xl（降低焦慮）
5. **回溯**：為什麼緊湊？→ 服務節奏「尖峰快速」→ 來源：CJM 使用情境

### 5. 圓角系統（Border Radius）

**使用情境**：卡片、按鈕、輸入框、通知框的邊角。

**是什麼**：圓角值的系統化定義（sm/md/lg）。

**為什麼**：
- 圓角傳達品牌人格——小圓角=俐落銳利，大圓角=親切柔和
- 一致的圓角確保視覺統一（UX 原則一）
- 避免「AI 味」——全部 16px 圓角是常見的 AI 生成特徵

**做什麼**：定義 sm/md/lg 圓角值。

**怎麼做**：
1. **從品牌人格推導**——俐落現代→小圓角（4-8px）
2. **定義值**：
   ```css
   --radius-sm: 4px   /* 輸入框、小元件 */
   --radius-md: 8px   /* 按鈕、卡片 */
   --radius-lg: 12px  /* 大容器 */
   ```
3. **回溯**：為什麼小圓角？→ 品牌人格「俐落」→ 來源：老闆目標

### 6. 元件設計原則（Component Principles）

**使用情境**：重用元件的設計——按鈕、卡片、表單、通知。

**是什麼**：元件的視覺規範，包含樣式、狀態（normal/hover/active/error）、變體（primary/secondary）。

**為什麼**：
- 元件一致性是 UX 原則一（一致性）的具體實現
- 狀態定義確保互動回饋一致——所有按鈕的 hover 都用同一種方式
- 元件規範讓 AI 生成程式碼時知道「按鈕長什麼樣、有什麼狀態」

**做什麼**：定義每種元件的樣式、狀態、變體。

**怎麼做**：
1. **從 UX 原則推導元件規範**：
   - 一致性 → 所有按鈕同一套樣式
   - 視覺層次 → 主按鈕高對比色，次按鈕低調
   - 錯誤預防 → 錯誤狀態用柔和紅+友善文案
2. **定義按鈕**：
   ```
   主按鈕：背景 primary，文字 white，圓角 md，hover 變深
   次按鈕：背景 transparent，邊框 primary，文字 primary
   危險按鈕：背景 error，文字 white
   ```
3. **定義卡片**：背景 surface，圓角 md，邊框 border，陰影 subtle
4. **定義通知**：成功=綠色左邊框；錯誤=柔和紅左邊框+友善文案（UX 原則五）
5. **回溯**：為什麼主按鈕高對比？→ UX 原則二「視覺層次」→ 來源：CJM 痛點

### 7. 佈局原則（Layout Principles）

**使用情境**：頁面整體結構——網格、容器寬度、回應式。

**是什麼**：網格系統、最大容器寬度、回應式斷點的定義。

**為什麼**：
- 佈局決定資訊層次——最重要的放哪裡、次要在哪裡
- 服務節奏決定佈局密度——快速服務緊湊，質感服務留白
- 回應式確保手機和桌面都能用

**做什麼**：定義網格、容器寬度、斷點。

**怎麼做**：
1. **從使用情境推導**——通勤點餐→手機優先（張家豪在通勤路上用手機）
2. **定義斷點**：
   ```
   手機：< 640px（優先設計）
   平板：640-1024px
   桌面：> 1024px
   ```
3. **定義容器**：最大寬度 1200px，兩側 padding 用間距系統
4. **回溯**：為什麼手機優先？→ 使用情境「通勤路上」→ 來源：CJM

### 8. 動效原則（Motion Principles）

**使用情境**：頁面切換、元素出現、狀態變化。

**是什麼**：動效的時機、持續時間、緩動函數。

**為什麼**：
- 動效傳達服務節奏——快速服務用快動效，質感服務用慢動效
- 動效提供操作回饋——按鈕按下有回饋，讓使用者知道「系統有回應」
- 過度動效會拖慢快速服務——尖峰點餐不需要花俏動畫

**做什麼**：定義動效規範。

**怎麼做**：
1. **從服務節奏推導**——高效快速→動效短（150-250ms），不花俏
2. **定義**：
   ```
   按鈕回饋：150ms ease-out
   頁面切換：200ms ease-in-out
   進度更新：數字變化 300ms，不做花俏動畫
   ```
3. **回溯**：為什麼動效短？→ 核心體驗目標「高效」→ 來源：顧客 Persona

### 9. 回溯表（Traceability）

**使用情境**：當需要審查 Design.md 中某個設計決策「憑什麼這樣決定」時；當 AI 生成的前端程式碼與服務設計目標不一致，需要回頭找原因時；當團隊成員問「為什麼主色是深青而不是橙色」時。

**是什麼**：回溯表是 Design.md 的最後一章，記錄每個設計決策到服務設計上游的回溯連結。它回答的問題是：「這個色彩/字體/間距/圓角值，是從哪個服務設計決策推導出來的？依據是什麼？這個依據是已驗證的還是待驗證的假設？」

回溯表不是因果鏈追蹤表的副本——兩者追蹤的範圍不同：

| | 因果鏈追蹤表（第 5 週 Part A） | Design.md 回溯表（Part B） |
|---|---|---|
| 追蹤什麼 | 市場選擇→Persona→CJM→Blueprint→服務決策 | 服務決策→風格預設→Design.md 每個參數 |
| 在哪裡 | 講義/專案文件中獨立累積 | Design.md 第 9 章 |
| 粒度 | 服務層級的決策（如「採用 KDS」） | 設計層級的決策（如「主色 #1B6E8C」） |
| 作用 | 確保服務設計有推導鏈 | 確保每個設計值有上游依據 |

兩者是串接的：因果鏈追蹤表追蹤到「CJM 最低點需安心感」，回溯表接著追蹤「CJM 最低點需安心感→主色選深青（設計假設，待驗證）」。

**為什麼**：
- 如果沒有回溯表，Design.md 只是一份「好看的規格」——讀者知道用什麼值，但不知道為什麼
- 不知道為什麼就無法判斷「什麼時候可以變通」——例如：AI 看到主色是深青，但不知道是因為 CJM 最低點需要安心感→它可能在付款頁改用亮色，破壞信任感
- 回溯表讓設計系統成為「有推導鏈的規格」而非「憑感覺的清單」——這是 Design.md 與一般風格指南的根本差異
- 回溯表也讓 AI 在生成程式碼時能理解「為什麼」，從而做出符合服務目標的判斷——這正是 DESIGN.md 規格中 Markdown body 存在的理由
- 標注「待驗證」讓團隊知道哪些決策已經過測試確認、哪些還是設計假設——避免把假設當成結論

**做什麼**：在 Design.md 末尾編寫回溯表，涵蓋所有設計決策，每個決策標注依據來源和驗證狀態。

**怎麼做**：

1. 逐一列出 Design.md 中的每個設計決策（不是每個參數值，而是每個「選擇」）
2. 為每個決策填寫四個欄位：

| 欄位 | 填什麼 | 好的寫法 | 壞的寫法 |
|---|---|---|---|
| **決策** | 具體的設計選擇 | 「主色選深青 #1B6E8C」 | 「色彩」（太模糊） |
| **依據** | 這個選擇憑什麼 | 「CJM 最低點（等待取餐）需安心感，深青傳達穩重」 | 「看起來好看」（無推導） |
| **回溯到** | 上游來源 | 「第 3 週 CJM」 | 「服務設計」（太模糊） |
| **待驗證** | 這個依據是否已驗證 | 「設計假設，待樣張比較驗證」 | 留空（假裝已驗證） |

3. 區分三類依據：
   - **已驗證**：有使用者測試或明確數據支持（如「WCAG AA 對比度 4.5:1」）
   - **設計推導**：從服務設計邏輯推導，合理但未經測試（如「CJM 最低點→安心感→深青」）
   - **待驗證**：明確標注為假設，需透過樣張比較或使用者測試確認

4. 完整範例（張家豪案例）：

| 決策 | 依據 | 回溯到 | 待驗證 |
|---|---|---|---|
| 選定「平衡現代」預設 | 老闆需科技感+CJM需溫度，折衷方向 | 老闆Persona + CJM | 教學示範決策，待老闆核准 |
| 色彩冷色基底 | 顧客期望「高效科技感」 | 第 2 週 Persona | 設計假設，待樣張比較驗證 |

| 暖色點綴暖橙 #E8743C | 推薦標記、今日特餐標籤 | 「複合式」需食物食慾感 | 設計假設，待樣張驗證 |
| 字體無襯線 Inter | 品牌人格「俐落現代」→無襯線 | 設計理由 | — |

5. 審查回溯表的方法：
   - **逐行問「憑什麼？」**：如果依據寫不出來，表示這個決策是憑感覺的——需要回頭找推導鏈
   - **檢查「待驗證」比例**：如果整表都是「待驗證」，表示設計還在假設階段——需要生成樣張比較
   - **檢查回溯鏈是否斷裂**：如 果「決策→依據→回溯到」的中間有任何一環缺失，表示推導不完整

## 十二、UX 原則 × 風格決策

UX 原則不是獨立的設計知識，而是元件設計原則（技術樹第 6 點）的推導依據。以下 5 個 UX 原則直接對應到 Design.md 的具體決策。

### 一、一致性原則 × 品牌風格與信任感

**UX 原則的目的**：讓使用者在不同頁面都感覺自己在同一個產品裡，降低認知負荷、建立信任感。

**對應 Design.md**：色彩系統的語義角色 + 字體系統的統一家族 + 元件的統一樣式。

**錯誤範例**：顧客面暖米色圓角，菜單冷色銳角，店員面完全不同 → 信任感下降。

**正確範例**：所有頁面同一套主色、字體、圓角；店員面密度高但同色系。

### 二、視覺層次 × 哪裡先被注意到

**UX 原則的目的**：讓使用者一眼看到最重要的資訊和操作。

**對應 Design.md**：字體系統的字級比例尺 + 色彩系統的主色使用規則 + 元件的主按鈕高對比。

**錯誤範例**：品牌故事最大字，下單按鈕很小 → 顧客不知道可以點餐。

**正確範例**：主按鈕高對比色，菜名價格粗體大字，描述略小偏灰。

### 三、Hick's Law × 版面密度與分群

**UX 原則的目的**：選項越多決策越慢，分群減少負擔。

**對應 Design.md**：間距系統的區塊間留白 + 佈局的網格分區 + 元件的卡片群組化。

**錯誤範例**：長表格列全部品項，無分組 → 顧客逐行看，耗時。

**正確範例**：分 3-4 區塊（主餐/套餐/飲品/加購），區塊間留白。

### 四、審美可用性效應 × 初次信任

**UX 原則的目的**：美觀的介面被認為更好用。

**對應 Design.md**：佈局的統一網格 + 色彩的克制使用 + 元件的對齊規範。

**錯誤範例**：卡片大小不一、混用字體 → 顧客覺得不專業。

**正確範例**：統一網格，1-2 種字體，色彩克制，付款頁更穩重。

### 五、錯誤預防 × 錯誤狀態的風格與文案

**UX 原則的目的**：錯誤提示要幫助不是責備。

**對應 Design.md**：元件的錯誤通知規範（柔和紅+友善文案，非大紅警告）。

**錯誤範例**：小字紅色「錯誤」→ 顧客不知道哪裡錯。

**正確範例**：「請選取取餐時間，讓我們準時為你準備早餐」+ 柔和紅框。

## 十三、風格決定流程：品牌資產、預設選擇與參數調整

Design.md 的 9 個章節（第十一章技術樹）是規格查閱表——不是要求學生從零發明每個參數。本章說明如何從服務設計出發，有效率地產出 Design.md。

### 路徑判斷：有 CIS vs 無 CIS

風格決定的第一步是判斷企業是否有品牌資產可沿用。

#### 路徑 A：企業有 CIS

如果企業已有 CIS（企業識別系統）或品牌手冊，可以從中提取視覺規範，直接填入 Design.md 的部分章節。但 CIS 通常不涵蓋所有網頁設計需要的項目：

| CIS 常見包含 | Design.md 對應章節 | 處理方式 |
|---|---|---|
| 品牌色（主色、輔色、背景色） | 色彩系統 | 直接沿用，補語義角色定義 |
| 標準字（中文字體、英文字體） | 字體系統 | 直接沿用，補字級比例尺和字重 |
| LOGO 規範（安全距離、最小尺寸） | — | 參考，不直接轉入 Design.md |
| 圖像風格（攝影、插畫方向） | — | 參考色彩和情緒方向 |
| 數位介面規範（部分 CIS 包含） | 色彩+字體+元件 | 如有可直接沿用，仍需補網頁特有項目 |
| CIS 通常未定義 | 間距系統 | 需從服務節奏推導 |
| CIS 通常未定義 | 圓角系統 | 需從品牌人格推導 |
| CIS 通常未定義 | 動效原則 | 需從服務節奏推導 |
| CIS 通常未定義 | 元件設計原則 | 需從 UX 原則推導 |
| CIS 通常未定義 | 佈局原則 | 需從使用情境推導 |

有 CIS 時，色彩和字體有直接來源，但仍需推導間距、圓角、動效、元件、佈局等網頁特有項目。預設組合仍可用來補足 CIS 未規定的模組。

#### 路徑 B：企業沒有 CIS（本案例）

本案早餐店是新創，沒有 CIS。風格面對的是老闆的美學偏好加上設計師的專業建議。此時採用「模組化＋參數化」方法：

1. 從服務設計推導幾個情緒方向
2. 每個方向綁定一組 Design.md 參數值，用風格名稱代表
3. 用 AI 生成每組的視覺樣張
4. 老闆與設計師比較、選擇、微調

### 風格預設組合

風格預設是「可替換風格模組」的**具名起始組合**——每組綁定一組色彩、字體、間距、圓角、動效的參數值，用一個名稱代表整體方向。名稱只是溝通標籤；交給 AI 時仍須附上完整規格，不能只給名稱。

本案從服務設計推導三個情緒方向，對應三組預設：

| 預設名稱 | 情緒方向 | 色彩 | 字體 | 間距 | 圓角 | 動效 | 回溯到 |
|---|---|---|---|---|---|---|---|
| 科技俐落 | 高效科技感 | 冷色基底 | 無襯線、幾何感 | 緊湊 | 小（4-8px） | 快（150ms） | 張家豪期望「高效科技感」 |
| 溫暖信賴 | 安心舒適感 | 暖色但克制 | 無襯線、圓潤 | 寬鬆 | 大（12-16px） | 慢（300ms） | CJM 最低點需安心感 |
| 平衡現代 | 科技感+人情味 | 冷暖混搭 | 無襯線、中性 | 中等 | 中（8-12px） | 中（200ms） | 老闆目標「俐落、現代、可信賴」 |

**重要提醒**：以上參數方向是設計假設，不是必然推導。「溫暖=慢動效」「高效=緊湊間距」是常見的設計聯想，但需要透過 AI 生成樣張、人工比較後才能確認。模組化和參數化是工程化管理手段，不代表美學偏好已被科學證明。

### 模組化的三層結構

風格預設只替換「可替換」的部分。Design.md 的參數分為三層：

| 層次 | 包含什麼 | 能不能因風格改變 |
|---|---|---|
| 共同底座 | 資訊層次、可讀性、狀態語義、鍵盤焦點、錯誤修正、減少動效需求 | 不能——任何風格都必須遵守 |
| 可替換風格模組 | 配色、字體、圓角、邊框/陰影、動效速度 | 能——預設組合替換的就是這層 |
| 角色情境配置 | 顧客手機版密度、店員平板版密度、廚房顯示器版面 | 獨立調整——不同角色有不同的資訊密度需求 |

投影片主題可以用來溝通風格方向和呈現樣張，但不能直接把投影片版面當網頁版面——網頁仍需補互動狀態、回應式規則和操作規格。

### 執行流程：7 步

| 步驟 | 操作 | 產出 |
|---|---|---|
| 1 | 萃取服務目標、角色情境、品牌資產與老闆偏好 | 設計理由、不可違反的限制 |
| 2 | 有 CIS：映射並補缺；無 CIS：定義三組候選預設 | 候選規格及來源標記 |
| 3 | 用相同內容、資訊結構與任務製作三組候選樣張 | 可比較的風格樣張 |
| 4 | 先檢查可用性（對比、可讀），再由老闆與設計師比較取捨 | 選定方向與理由 |
| 5 | 調整參數，補齊網頁互動規格（元件狀態、表單、回應式） | Design.md 草稿 |
| 6 | 檢查對比、中文閱讀、手機呈現及操作狀態 | 修正與待驗證紀錄 |
| 7 | 整理規格、tokens、版本與回溯表 | 一致的交付文件 |

#### 步驟 1：萃取設計理由與限制

**操作**：從服務設計決定版萃取服務目標、角色情境、品牌資產、老闆偏好。同時列出不可違反的限制（如 WCAG 對比、中文可讀性、手機優先）。

**產出**：Design.md 第 1 章「設計理由」+ 限制清單

#### 步驟 2：品牌資產映射或定義預設

**操作**：
- 有 CIS：對照 CIS 映射表，直接填入色彩和字體，標記缺少的項目
- 無 CIS：從設計理由推導三個情緒方向，定義三組預設的參數值，每組標注回溯來源

**產出**：三組候選規格（含參數值和來源標記）

#### 步驟 3：製作候選樣張

**操作**：用 Google Stitch 或 Claude Artifacts，以相同內容、相同資訊結構、相同任務，分別生成三組預設的視覺樣張。關鍵：三組樣張的內容和佈局結構一致，只換風格參數，才能公平比較。

**產出**：三組可比較的風格樣張（HTML/CSS 或截圖）

#### 步驟 4：可用性檢查與方向選定

**操作**：
1. 先檢查可用性：對比度是否足夠？中文是否清晰？按鈕是否可辨識？
2. 再由老闆與設計師比較三組樣張的偏好和取捨
3. 記錄選定理由和捨棄其他方向的理由

**產出**：選定方向 + 選定理由 + 捨棄理由

#### 步驟 5：調整參數，補齊互動規格

**操作**：以選定預設為基礎，調整必要參數。補齊預設未涵蓋的網頁互動規格：元件狀態（normal/hover/active/focus/disabled）、表單規範、回應式斷點。

**產出**：Design.md 草稿（9 個章節齊全）

#### 步驟 6：驗證檢查

## 十四、範例：張家豪的風格預設選擇與 Design.md

### 三組預設比較

從服務設計決定版推導三個情緒方向，定義三組預設：

| 預設名稱 | 情緒方向 | 色彩基底 | 字體風格 | 間距密度 | 圓角 | 動效速度 | 回溯到 |
|---|---|---|---|---|---|---|---|
| 科技俐落 | 高效科技感 | 冷色（深青基底） | 無襯線、幾何 | 緊湊 | 小（4-8px） | 快（150ms） | 張家豪期望 |
| 溫暖信賴 | 安心舒適感 | 暖色克制（米色基底） | 無襯線、圓潤 | 寬鬆 | 大（12-16px） | 慢（300ms） | CJM 最低點 |
| 平衡現代 | 科技+人情味 | 冷暖混搭（冷底+暖點綴） | 無襯線、中性 | 中等 | 中（8-12px） | 中（200ms） | 老闆目標 |

### 選定理由（教學示範決策，待驗證）

本案選定「平衡現代」預設。理由：

- 老闆品牌人格「俐落、現代、可信賴」需要科技感 → 排除純暖色
- CJM 最低點（等待取餐）的安心感需要溫度 → 排除純冷色
- 「平衡現代」是折衷方向：冷色基底傳達科技感，暖色點綴傳達人情味

**注意**：這是教學示範決策，未經老闆實際核准或使用者測試驗證。實務上應生成三組樣張後，由老闆與設計師共同比較決定。預設參數方向（如「溫暖=慢動效」）是設計假設，需透過實際樣張比較確認。

```markdown
## 6. 元件設計原則

### 按鈕
- 主按鈕：背景 primary，文字 white，圓角 md，字重 600
  - normal：背景 primary
  - hover：背景 primary-hover
  - active：背景再深一階
  - focus：外框 2px solid accent（鍵盤導航可見）
  - disabled：背景 #B0BEC5，文字 white，游標 not-allowed
- 次按鈕：背景 transparent，邊框 1px primary，文字 primary
  - hover：背景 primary 10% 透明度
- 危險按鈕：背景 error，文字 white

（UX原則二：視覺層次——主按鈕高對比，次按鈕低調）

### 卡片
- 背景 surface，圓角 md，邊框 1px solid border
- 卡片間距 md，區塊間距 lg（UX原則三：Hick's Law 分群）

### 表單
- 輸入框：背景 surface，邊框 1px border，圓角 sm，內距 sm
  - focus：邊框變 primary，外框 2px accent 30% 透明度
  - 錯誤：邊框變 error，下方顯示友善文案
- 標籤：text-sm，text-muted，字重 400
- 取餐時間選擇器：按鈕樣式選項，選中狀態背景 primary，文字 white

### 通知
- 成功：左邊框 3px success，背景 surface，圖示+文字
- 錯誤：左邊框 3px error，背景 surface，搭配友善文案（UX原則五）
- 進度：左邊框 3px accent，背景 surface
- 不用整頁大紅警告

## 7. 佈局原則

- 手機優先（回溯：使用情境「通勤路上」）
- 斷點：手機 <640px / 平板 640-1024px / 桌面 >1024px
- 容器最大寬度 1200px
- 網格：手機 1 欄，平板 2 欄，桌面 3-4 欄

## 8. 動效原則

- 按鈕回饋：150ms ease-out（回溯：核心體驗目標「高效」——設計假設，待驗證）
- 頁面切換：200ms ease-in-out
- 進度更新：300ms，不做花俏動畫
- 支援 prefers-reduced-motion：使用者設定減少動效時，動效降為即時切換
```

### oh-my-pi 是什麼

[oh-my-pi](https://omp.sh)（簡稱 omp）是開源的終端機 AI 編碼助手（MIT 授權，[GitHub 35,000+ 星](https://github.com/can1357/oh-my-pi)）。它不是「聊天盒子上加一個 LLM」——它把開發者工具鏈直接建進 AI 裡：

| omp 能做什麼 | 說明 | 為什麼重要 |
|---|---|---|---|
| LSP 整合 | 透過語言伺服器導覽和重構程式碼，不是猜測 | AI 看到真實的符號定義和引用，不是文字猜測 |
| DAP 偵錯 | 可啟動偵錯器（lldb、delv、debugpy），逐步執行 | AI 能在崩潰點檢查變數，不是只看錯誤訊息 |
| 檔案讀寫 | 直接讀取和修改專案檔案 | 不需要手動複製貼上程式碼 |
| Hash-anchored edits | 用內容指標定位程式碼，不是行號 | 檔案修改後行號會變，hash 不會——更少 token 浪費 |
| 200+ 模型 | 支援 40+ 提供商、200+ 模型 | 帶你自己的訂閱或 API key，不被綁在單一服務 |

**為什麼選 omp 而非其他工具**：

### 模型來源與設定

omp 是「帶你自己的模型」——它是一個執行框架，模型來源由你選擇。支援三類來源：

**類型一：訂閱登入（OAuth）**

如果你已有 ChatGPT Plus 訂閱，可以直接登入使用，不需要額外付費：

```bash
# 在 omp 中登入 ChatGPT Plus 訂閱
```

其他支援訂閱登入的 provider：Anthropic（Claude Pro/Max）、GitHub Copilot、Google Gemini CLI（[官方文件](https://omp.sh/docs/providers)）

**類型二：API Key（付費或免費）**

設定環境變數即可，omp 會自動發現：

| 來源 | 設定方式 | 費用 | 適合情境 |
|---|---|---|---|
| **DeepSeek API** | `export DEEPSEEK_API_KEY=your_key` | 按用量（極低） | API 自動化、批量處理 |

```yaml
providers:

    api: openai-completions
    apiKey: GROQ_API_KEY  # 環境變數名稱

      - id: openai/gpt-oss-120b
        name: GPT-OSS 120B
        contextWindow: 131000
```

```bash
# 在清單中選擇你要使用的模型
```

### 免費雲端 LLM 詳細額度

### 讓 omp 讀取 DESIGN.md

DESIGN.md 放在專案根目錄是必要條件，但不是充分條件——omp 不會自動讀取 DESIGN.md 這個檔名。omp 有自己的上下文載入機制，DESIGN.md 需要透過以下方式之一被引用：

**方式 A：在 Prompt 中明確引用（最簡單，每次使用）**

```bash
# 在 omp 中用 @ 語法引用檔案
@DESIGN.md 請根據這份設計規格生成早餐店顧客端首頁
```

`@檔案路徑` 是 omp 的檔案引用語法——omp 會讀取該檔案內容放入當前對話上下文。每次新對話需重新引用。

**方式 B：建立自訂 skill（推薦，一次設定永久生效）**

[omp 的 skill 系統](https://github.com/can1357/oh-my-pi/blob/main/docs/skills.md)會在啟動時自動發現 `skills/` 目錄中的 `SKILL.md` 檔案。建立一個前端設計 skill：

```
skills/
  frontend-design/
    SKILL.md
```

`SKILL.md` 內容：

```markdown
# Frontend Design Skill

## 使用時機
當使用者要求生成前端 UI、元件、頁面時。

## 規則
1. 先讀取專案根目錄的 DESIGN.md
2. 所有色彩、字體、間距、圓角使用 DESIGN.md 中的 tokens
3. 元件需包含完整的互動狀態（normal/hover/focus/active/disabled）
4. 手機優先設計
5. 確保 WCAG AA 對比度
```

skill 被發現後，omp 會在系統提示中加入 skill 的名稱和描述，並在需要時讀取完整內容。這表示 omp「知道」有這個 skill，會在生成前端 UI 時自動參照。

**方式 C：安裝前端設計 skill 套件**

omp 的[插件系統](https://omp.sh/docs/plugins)支援從 npm、GitHub 或 marketplace 安裝套件：

```bash
# 安裝包含 frontend design 等技能的社群套件
omp plugin install @ifi/oh-pi-skills
```

`@ifi/oh-pi-skills` 包含 frontend design、web search、debug helper、git workflow 等技能。安裝後重啟 omp 即可使用。

**方式 D：繼承 IDE 設定**

omp 在首次啟動時會[繼承你現有 IDE 的 MCP 設定](https://esphome.cloud/docs/en/clients/oh-my-pi.html)——讀取 `.claude`、`.cursor`、`.windsurf`、`.gemini`、`.vscode` 等設定檔。如果你已在其他工具中設定好設計系統規則，omp 會自動繼承。

### 預設式 Prompt 範例

在 omp 中生成前端頁面：

```
@DESIGN.md 請根據這份設計規格，生成「雲端早餐店」顧客端首頁。

風格預設：平衡現代（冷暖混搭）

```

在 Claude Artifacts 中驗證單一頁面：

```
以下是專案的 DESIGN.md 規格：

[貼入 DESIGN.md 完整內容]

請根據這份規格，用 HTML/CSS 生成「等待取餐進度頁」——
這是 CJM 情緒最低點的頁面，需要傳達安心感。
使用 DESIGN.md 中的色彩和間距 tokens。
等待頁面留白要比其他頁面多（用 lg/xl 間距）。
```

### 避免 AI 味的負面約束

在餵給 AI 的 Prompt 中加入以下負面約束：
- 不要紫藍漸層背景
- 不要過度 SaaS 感（千篇一律的儀表板配色）
- 不要抽象幾何背景裝飾
- 不要用 emoji 當圖示
- 不要全部圓角 16px（過度柔和）
- 不要 Inter + 漸層文字標題（太常見的 AI 組合）

### 人工修正重點

1. **色彩是否回溯到情緒需求**：AI 可能選了好看但跟服務無關的顏色
2. **字體是否回溯到品牌人格**：AI 可能用了花俏字體
3. **空間是否回溯到服務節奏**：AI 可能留白太多或太擠
4. **信任感頁面是否穩重**：AI 可能在付款頁用了花俏色彩
5. **一致性是否維持**：AI 可能在不同頁面用了不同風格
6. **互動狀態是否完整**：AI 常漏掉 hover/focus/disabled 狀態
7. **中文閱讀是否舒適**：AI 可能用英文字距和行高，不適合中文

### 規格一致性驗證練習

AI 說「已讀取 DESIGN.md」不算驗證。用以下步驟確認：

1. 在 DESIGN.md 中修改一個明確的 token（如 `--color-primary` 從 `#1B6E8C` 改為 `#FF0000`）
2. 要求 omp 重新生成頁面
3. 檢查生成的程式碼和畫面是否跟著更新
4. 如果沒有更新，表示 DESIGN.md 未被正確載入——檢查引用方式
5. 確認後改回原本的值

## 十九、本週核心一句話

**服務藍圖是業務描述轉向工程描述的轉換點——所有選項必須變成決定。風格預設是降低決策負擔的工程化方法——選一個有理由的方向，再微調參數，而不是從空白頁面開始猜測 50 個設計值。Design.md 讓每個設計決策有憑有據，AI 生成程式碼時不再猜測。**

決定版不是「我覺得選A比較好」，是「選了A，因為[具體理由]，代價是[具體限制]，這個代價在[具體條件]下可接受」。風格預設不是「我覺得好看」，是「決定版推導出三個情緒方向，每個方向綁定一組參數，生成樣張比較後選定——選定的理由能回溯，捨棄的理由也記錄」。
