## 3. 一條需求長什麼樣

spec 裡的每一條需求都要能**往回指**：

```
REQ-012  顧客在製作完成後，不得提前得知可取餐
  ├─ 來源任務句：T-05（廚師完成）／T-06（店員備妥入櫃）
  ├─ 來源物件：OBJ-02 訂單（S5 → S6）
  ├─ 對應 AC：AC-12（不得提前通知）
  └─ 對應檢查：verify-stories（自動）
```

| 欄位 | 寫什麼 |
|---|---|
| 編號 | REQ-xxx |
| 需求陳述 | 一句話，業務語言 |
| 來源 | 任務句／物件／決策的編號 |
| 驗收 | 對應的 AC 編號 |
| 驗證方式 | 自動／人工／使用者測試 |

**沒有「來源」的需求，就是憑空想的。**

## 4. 十條寫作規則

| # | 規則 | 反例 |
|---|---|---|
| 1 | **不得出現技術名** | Redis、Kafka、WebSocket、React |
| 2 | 不得出現框架與套件名 | Tailwind、Vue |
| 3 | 不寫資料表結構、API 路徑 | `POST /orders` |
| 4 | 不寫演算法 | 用 LRU 快取 |
| 5 | 形容詞要可操作 | ❌「介面要現代」✅「主 CTA 對比 ≥4.5:1」 |
| 6 | 時效寫成**業務參數** | ✅「狀態變更後 1 秒內四端一致」 |
| 7 | 每條都要有來源 | 指回任務句／物件／決策 |
| 8 | 每條都要有驗收 | 指回 AC |
| 9 | 用現在式、主動語態 | 「店員確認後，顧客看到可取餐」 |
| 10 | 一句話只講一件事 | 一條需求一個述詞 |

## 5. 時效與非功能：寫「誰在等」，不寫「用什麼」

| 誰在等 | 需求寫法 | 不寫 |
|---|---|---|
| 顧客站在櫃前 | 狀態變更後 **1 秒內**顧客端可見 | 用 WebSocket 推播 |
| 廚師盯 KDS | 新單 **3 秒內**出現在佇列 | 用訊息佇列 |
| 老闆看報表 | 營收可落後 **1 小時**，但金額必須正確 | 用批次排程 |

> 判準：**換一種技術，這條需求還成立嗎？** 成立 → 它是業務需求；不成立 → 它是技術決策，搬到 plan.md。

## 6. 三項指標（本週的驗收）

| 指標 | 公式 | 標準 |
|---|---|---|
| **技術名殘留** | 出現的技術名數量 | **0** |
| **可追溯率** | 有來源的需求 ÷ 需求總數 | **100%** |
| **驗收覆蓋率** | 有 AC 的需求 ÷ 需求總數 | **100%** |

三項都過，spec 才算完成。

```
node check-spec.mjs   # 自動檢查三項指標
```

> 這支檢查器在示範答案上**抓到作者自己寫的「佇列」**（技術詞），改成「待製作清單」才過——這正是它存在的理由。

## 7. spec 與 plan 的分界（本週最容易錯）

| | spec.md | plan.md |
|---|---|---|
| 回答 | 要什麼、為什麼、怎樣算做到 | 用什麼做、怎麼做 |
| 可以寫 | 1 秒內一致、四端同步、離線可用 | 資料庫、快取、訊息佇列、部署 |
| 讀者 | 老闆、設計、工程、驗收 | 工程 |
| 誰核准 | 業主 | 技術負責人 |

```
spec：狀態變更後 1 秒內，四端顯示一致
plan：用推送 + 單一寫入點達成上述要求
```

## 9. 五個常見失分

| # | 失分 | 為什麼 |
|---|---|---|
| 1 | spec 裡寫「用 WebSocket」 | 那是 plan 的事，技術一改需求就作廢 |
| 2 | 需求沒有來源 | 無法判斷是否該存在 |
| 3 | 需求沒有 AC | 無法驗收 |
| 4 | 一條需求講三件事 | 驗收時無法判斷通過與否 |
| 5 | 直接把前幾週的檔案貼上 | 語氣不一致、重複、矛盾 |

---

## 10. 一句話

> **spec 不是「把前面的檔案合併」，是「把證據排成一份別人看得懂、驗得動的文件」。**
> 技術名出現的那一刻，它就變成 plan 了。
