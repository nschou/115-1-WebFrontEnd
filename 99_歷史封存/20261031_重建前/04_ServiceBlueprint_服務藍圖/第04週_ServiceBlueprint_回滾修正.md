## 一、為什麼：Service Blueprint 的第一性原理

從 CJM 到 Blueprint 的推導

第 3 週的產出是 CJM。CJM 告訴我們：

| 已知 | 來自 | 還不知道 |
|---|---|---|
| 顧客在每個階段做什麼 | CJM 行動欄位 | 為了讓這些行動發生，背後需要做什麼 |
| 顧客透過什麼接觸服務 | CJM 接觸點欄位 | 每個接觸點背後的系統和流程 |
| 顧客在哪裡最痛苦 | CJM 情緒曲線最低點 | 後台要怎麼改善才能消除這個痛苦 |
| 設計機會是什麼 | CJM 機會欄位 | 機會需要哪些後台系統來實現 |

第一性原理推導：

CJM 只看到顧客視角（前台）
→ 但每個前台接觸點都需要後台支持
→ 如果只設計前台、不設計後台，前台會沒有可靠支撐
→ 例如：顧客下單（前台），但後台沒有接單製作 → 訂單永遠不會被做
→ 支持系統的角色就是在後台
→ 需要在 CJM 下方加上後台行為和支援系統
→ 這就是 Service Blueprint

為什麼需要可見線和內部互動線

核心事實：不是所有後台行為都需要即時，也不是所有系統都直接面對顧客。

推導：

後台行為有些是顧客看得到的（店員確認訂單），有些通常看不到（更新庫存記錄）
→ 需要一條線區分「顧客看得到」和「通常看不到」
→ 這就是可見線

後台行為有些直接支持前台（店員接單），有些是間接的（記錄銷售資料）
→ 需要一條線區分「直接支持」和「間接支持」
→ 這就是內部互動線

兩條線把 Blueprint 分成三層：
→ 可見線以上 = 前台（顧客端 UI）
→ 兩線之間 = 後台（店員端 UI）
→ 內部互動線以下 = 支援系統（系統後端）

三層 Persona 在 Blueprint 中的角色

| Persona 層 | 在 Blueprint 中的位置 | 具體貢獻 |
|---|---|---|
| 顧客 Persona（張家豪） | 前台行為的來源 | CJM 的接觸點 → Blueprint 前台行為 |
| 支持系統 Persona（陳美玲） | 後台行為的來源 | 角色對應的工作事項 → Blueprint 後台行為；痛點 → 後台要解決的問題 |
| 老闆 Persona（王建興） | 解決方案的決策者 | Blueprint 定義需求後，服務設計師為老闆思考解決方案選項；老闆評估成本/風險/ROI，決定投資什麼 |

Blueprint 不是軟體專屬工具

第一性原理推導：

服務設計的根本問題：如何把價值從企業交付到顧客手中？
→ 交付需要前台行為（顧客看得到）和後台行為（通常顧客看不到）
→ 後台行為需要支撐——但支撐不一定是軟體
→ 支撐可能是：人工流程、實體設備、空間配置、資料記錄、供應鏈、培訓制度……
→ 如果把「支援系統」窄化為「數位資訊系統」，就等於在 Blueprint 階段就預設了「一定要寫軟體」
→ 這違反了第一性原理——我們應該先定義「需要什麼」，再決定「怎麼實現」
→ Service Blueprint 是一套通用思維工具，可以用在任何需要產出服務或產品的領域中
→ 不是專為軟體系統設計的

關鍵區分：

|  | Blueprint 階段 | 解決方案階段 |
|---|---|---|
| 回答的問題 | 後台需要做什麼？需要什麼資料？ | 用什麼方式做到？ |
| 產出 | 需求清單（後台行為 + 支援需求） | 解決方案（數位/人工/實體/混合） |
| 誰負責 | 服務設計師 + 支持系統 Persona | 服務設計師提案 → 老闆 Persona 決策 |

為什麼這個區分重要：

如果在 Blueprint 階段就預設「一定要用軟體」，會限制解決方案空間

老闆可能不需要一套軟體——也許重新設計人工流程就解決了，成本更低

服務設計師的價值不在「寫軟體」，而在「找到最優的交付方式組合」

這也是為什麼老闆 Persona 是三層 Persona 中的第一層——最終是老闆決定投資什麼

Blueprint 之後：服務設計師為老闆思考解決方案

第一性原理推導：

Blueprint 標定完成 → 揭示了「後台需要做什麼」和「需要什麼支撐」
→ 但「怎麼做到」有多種選擇：
   - 數位化（開發 App/系統）
   - 人工流程優化（重新設計 SOP）
   - 實體設備改善（換廚房設備、改動線）
   - 外包（委外製作、第三方服務）
   - 混合（部分數位 + 部分人工）
→ 服務設計師的價值：在這些選項中，找到最符合老闆目標（成本/效率/ROI）的組合
→ 老闆 Persona 的角色：評估解決方案，決定投資什麼

服務設計師的思考方式：

拿 Blueprint 的每個後台需求和支援需求

列出所有可能的實現方式（數位/人工/實體/外包/混合）

對每個選項評估：成本、效率、可靠度、學習曲線

對照老闆 Persona 的目標和資源限制

提出推薦方案 + 理由

這不是「全部數位化」，而是「哪些數位化能帶來最大體驗提升和營運效率，哪些用人工流程就夠了」。

★ 最高指導原則：用業務用語描述，不用工程用語

在進入 Blueprint 的結構之前，必須先建立一個貫穿全程的描述原則：

Blueprint 必須使用業務邏輯與用語來描述，不能使用工程用語。這是在描述需求和方案設計，不是在設計技術實作。

為什麼

第一性原理推導：

Blueprint 的目的是定義「服務需要什麼」
→ 服務的需求用業務語言表達（誰做什麼、顧客經歷什麼、需要什麼支撐）
→ 如果用工程用語描述（系統做什麼、API、UI、資料庫）
→ 等於在需求階段就預設了技術方案
→ 這違反了「先定義需求，再決定實現」的第一性原理
→ 而且業務相關人（老闆、店長、服務設計師）看不懂工程用語
→ Blueprint 變成只有工程師能參與的文件 → 失去服務設計的意義

業務用語 vs 工程用語對照

| ❌ 工程用語（不該出現在 Blueprint） | ✅ 業務用語（應該用這個） |
|---|---|
| 系統顯示菜單 | 顧客查看菜單 |
| App 接收訂單 | 店員接收顧客訂單 |
| 系統更新訂單狀態 | 店員更新進度狀態 |
| 系統排入佇列 | 安排製作順序 |
| UI / 介面 | 顧客面 / 店員面 |
| 訂單管理系統 | 訂單接收與處理方式 |
| API / 資料庫 / 後端 | （這些是實作細節，不該出現在 Blueprint） |

記住

Blueprint 是給業務相關人看的——老闆要能看懂、店長要能確認、服務設計師要能討論

工程用語出現在 Blueprint = 在需求階段就做了技術決策 = 太早了

技術實作的細節（用什麼 API、什麼資料庫、什麼框架）是第 7 週 spec.md 以後的事

你在寫 Blueprint 時，假裝你不懂寫程式——你只懂這門生意怎麼運作

## 二、做什麼：Service Blueprint 的結構

3 層 2 線

Service Blueprint 是在 CJM 下方加上兩層，用兩條線分隔：

┌─────────────────────────────────────────────┐
│  前台行為（顧客看得到的）                      │  ← 從 CJM 接續
├─────── 可見線 ──────────────────────────────┤
│  後台行為（通常顧客看不到，支持系統做的）          │  ← 支持系統角色的工作
├─────── 內部互動線 ──────────────────────────┤
│  支援需求（設施、流程、資料或底層支援）          │  ← 不限數位，包含人工/實體/流程
└─────────────────────────────────────────────┘

前台行為

是什麼：Blueprint 的最上層，直接承接 CJM 的接觸點，描述顧客在這個接觸點經歷什麼。

為什麼：

Blueprint 不是從零開始，是 CJM 的延伸

前台行為 = 顧客在這個接觸點看到、聽到、感受到什麼

這一層連接顧客視角和後台視角

做什麼：把 CJM 的接觸點轉成顧客體驗描述，放在 Blueprint 最上層。

怎麼做：

拿 CJM 的每個接觸點

問「顧客在這個接觸點經歷什麼？」

寫成一行顧客體驗描述（不是系統功能描述）

範例：CJM 接觸點「菜單頁」→ 前台行為「顧客查看菜單品項與價格」

注意：前台行為描述的是顧客的行為和體驗，不是系統的功能。「系統顯示菜單」是系統功能描述，「顧客查看菜單」才是服務行為描述。用什麼方式讓顧客看到菜單（App、紙本、看板）是解決方案階段的事。

後台行為

是什麼：為了讓前台體驗發生，背後需要做什麼事。描述的是「需要做什麼」，不是「用什麼系統做」。

為什麼：

每個前台體驗都需要後台支持

如果不設計後台，前台會沒有可靠支撐

後台行為描述「需要做什麼」，由誰做、用什麼方式做是解決方案階段的事

這一層是後續解決方案設計的來源

做什麼：為每個前台行為，找出對應的後台行為（需要做什麼）。

怎麼做：

拿每個前台行為，問「為了讓顧客有這個體驗，背後需要做什麼？」

用角色對應的工作事項來推導需要做什麼

範例：前台「顧客查看菜單」→ 後台「提供最新菜單內容」（誰提供？怎麼提供？→ 解決方案階段決定）

注意：後台行為描述的是「需要做什麼」，不是「系統做什麼」。「系統更新菜單內容」是系統功能描述，「提供最新菜單內容」才是服務行為描述。由誰提供（老闆、員工、系統）是設計決策，不是 Blueprint 階段的預設。

支援需求

是什麼：支撐後台行為的設施、流程、資料或底層支援，是 Blueprint 的最底層。不限定數位系統——可能是軟體系統、實體設備、人工流程、資料記錄，或它們的組合。

為什麼：

後台行為需要某種支撐才能執行

如果預設支撐一定是軟體，就等於在 Blueprint 階段就決定了解決方案——這太早了

正確做法：先定義「需要什麼支撐」，再在解決方案階段決定「用數位、人工、實體還是混合」

這一層揭示「需要什麼能力」，是後續解決方案設計的輸入

做什麼：列出每個後台行為所需的支撐需求，標注可能的實現方式。

怎麼做：

拿每個後台行為，問「這件事需要什麼支撐才能完成？」

支撐分三類標記：

數位系統：軟體、App、API、資料庫

實體設施：設備、空間、動線、硬體

人工流程：SOP、培訓、人力調度、檢核制度

每項支援需求列出多種可能，不預設一定要用數位

範例：後台「接收訂單」→ 支援需求「訂單傳遞方式」→ 可能選項：App 系統（數位）/ 口頭+紙本（人工）/ 混合

常見錯誤示範：系統導向 vs 服務導向

以下是初學者最常犯的錯誤——不自覺地從「系統功能」角度描述 Blueprint，而不是從「服務行為」角度。這個對照表來自實際的修正過程，值得仔細對比。

前台行為的錯誤示範

| ❌ 錯誤寫法（系統導向） | ✅ 正確寫法（服務導向） | 為什麼錯 |
|---|---|---|
| 系統顯示菜單品項與價格 | 顧客查看菜單品項與價格 | 前台是顧客的體驗，不是系統的功能。用什麼方式讓顧客看到菜單是解決方案階段的事 |
| App 接收訂單並顯示確認 | 顧客提交訂單；顧客收到訂單確認 | 「App」預設了接收方式。用什麼方式接收、由誰接收是待決定的設計問題 |
| 系統顯示訂單進度 | 顧客查看訂單進度 | 顧客的行為是「查看」，系統的行為是「顯示」——Blueprint 描述的是顧客的體驗 |
| 取餐櫃叫號 | 顧客聽到取餐叫號 | 前台是顧客聽到/看到/感受到什麼，不是設備做了什麼 |

後台行為的錯誤示範

| ❌ 錯誤寫法（系統導向） | ✅ 正確寫法（服務導向） | 為什麼錯 |
|---|---|---|
| 系統更新菜單內容 | 提供最新菜單內容（誰提供？→ 設計決策） | 「系統更新」預設了由系統做。誰提供（老闆、員工、系統）是設計決策，不是 Blueprint 階段的預設 |
| 系統維護品項庫存 | （與前台「查看菜單」無直接關係） | 這是獨立的後台需求，不該混在「提供菜單」這個前台行為的後台。庫存管理是另一個服務需求 |
| 系統接收訂單排入佇列 | 接收訂單並安排製作順序 | 「系統接收」預設了由系統做。由誰接收、用什麼方式是解決方案階段的事 |
| 系統即時更新訂單狀態 | 更新進度狀態 | 系統只是實現方式之一，不是預設。用人工看板更新也是合法的實現方式 |
| 系統推播進度通知 | 通知顧客進度 | 「推播」預設了數位方式。用口頭告知、看板顯示也是合法的實現方式 |

支援層的錯誤示範

| ❌ 錯誤寫法（系統導向） | ✅ 正確寫法（服務導向） | 為什麼錯 |
|---|---|---|
| 支援系統：訂單管理系統 | 支援需求：訂單接收方式 | 「訂單管理系統」預設了要開發/採購一套軟體。Blueprint 階段應描述「需要什麼能力」，不是「要買什麼系統」 |
| 支援系統：推播服務 | 支援需求：進度通知方式 | 「推播服務」預設了數位實現。用人工喊號也是合法的 |
| 支援系統：POS 系統 | 支援需求：銷售記錄方式 | 「POS 系統」預設了特定產品。用紙本記帳也是合法的 |

為什麼初學者容易犯這個錯誤

第一性原理推導：

初學者（尤其是資工系學生）習慣從「系統功能」角度思考
→ 因為日常接觸的是軟體、API、資料庫
→ 寫 Blueprint 時不自覺地把後台行為寫成系統功能
→ 把「提供最新菜單」寫成「系統更新菜單內容」
→ 把「接收訂單」寫成「系統接收訂單」
→ 結果：在 Blueprint 階段就預設了「一定要用軟體」
→ 這限制了後續的解決方案空間
→ 老闆可能不需要一套軟體——也許重新設計人工流程就解決了

記住：Blueprint 描述的是「服務」（誰需要做什麼），不是「系統」（系統做什麼）。系統只是實現服務的選項之一。

可見線

是什麼：一條水平線，分隔前台（顧客看得到）和後台（通常顧客看不到）。

為什麼：

定義「什麼要設計給顧客看，什麼不用」

可見線以上 → 顧客端 UI（第 6 週設計的頁面）

可見線以下 → 店員端 UI 和系統後端

做什麼：在 Blueprint 上畫一條線，標示前台和後台的邊界。

怎麼做：畫在前台行為和後台行為之間。線以上是顧客看得到的，線以下是通常看不到的。

內部互動線

是什麼：一條水平線，分隔後台（直接支持前台）和支援系統（間接支持）。

為什麼：

定義「什麼是即時需要的，什麼可以非同步」

兩線之間 → 店員端 UI（店員直接操作）

以下 → 系統後端（自動化或間接支持）

做什麼：在 Blueprint 上畫一條線，標示後台和支援系統的邊界。

怎麼做：畫在後台行為和支援系統之間。線以上是直接支持前台的，以下是間接的。

## 三、怎麼做：逐步操作

步驟 1：從 CJM 接續前台行為

是什麼：把第 3 週 CJM 的接觸點轉成 Blueprint 的前台行為。

為什麼：

Blueprint 不是重新設計，是 CJM 的向下延伸

前台行為是 CJM 接觸點的「顧客體驗視角」

做什麼：為每個 CJM 階段的接觸點，寫出顧客經歷什麼。

怎麼做：

拿第 3 週 CJM 的接觸點清單

每個接觸點問「顧客在這裡經歷什麼？」

寫成前台行為

範例：接觸點「訂單狀態頁」→ 前台行為「顧客查看訂單進度（製作中/可取餐）」

步驟 2：用角色填後台行為

是什麼：為每個前台行為，找出對應的後台行為。

為什麼：

每個前台行為都需要後台支持

支持系統的角色就是在後台

不填後台，前台就是空中樓閣

做什麼：用第 2 週 Persona 拆分出的角色的工作事項，填入後台行為。

怎麼做：

拿角色對應的工作事項（從 Persona 拆分而來）

每個前台行為問「為了讓顧客有這個體驗，背後需要做什麼？」

寫成後台行為

範例：前台「顧客查看訂單進度」→ 後台「店員接收訂單」「店員通知廚師製作」「廚師製作餐點」「廚師回報進度給店員」「店員更新進度狀態」

步驟 3：列支援需求

是什麼：為每個後台行為，列出所需的支撐——設施、流程、資料或底層支援。

為什麼：

後台行為需要某種支撐才能執行

支撐不一定是數位系統——可能是人工流程、實體設備、或混合

這一層揭示「需要什麼能力」，是後續解決方案設計的輸入

做什麼：列出每個後台行為所需的支撐需求，標注可能的實現方式。

怎麼做：

每個後台行為問「這件事需要什麼支撐才能完成？」

分類：軟體系統、硬體設備、人工流程

範例：後台「接收訂單」→ 支援需求「訂單傳遞方式」→ 可能選項：App 系統（數位）/ 口頭+紙本（人工）/ 混合

步驟 4：畫可見線和內部互動線

是什麼：在 Blueprint 上畫兩條水平線，分隔三層。

為什麼：

兩條線定義了顧客端、店員端、系統後端的邊界

這個邊界是後續 UI 設計和系統架構的基礎

做什麼：畫可見線（前台/後台之間）和內部互動線（後台/支援之間）。

怎麼做：

可見線：畫在前台行為和後台行為之間

內部互動線：畫在後台行為和支援系統之間

標記：可見線以上 → 顧客端 UI；兩線之間 → 店員端 UI；以下 → 系統後端

步驟 5：連結痛點到下游

是什麼：把 CJM 的痛點和機會，透過 Blueprint 的後台行為，連結到下游的風格設計和功能設計。

為什麼：

痛點不連結到下游，就只是「發現問題」

機會需要後台系統來實現

這一步讓 Blueprint 不只是地圖，而是設計依據

做什麼：為每個 CJM 機會，找出需要的後台行為和支援系統，標記下游影響。

怎麼做：

拿第 3 週 CJM 的機會清單

每個機會問「實現這個機會需要哪些後台行為？」

每個機會標記：「→ 影響風格：[方向]」「→ 影響功能：[功能描述]」

範例：機會「即時進度通知」→ 後台「更新進度狀態」「通知顧客進度」→ 支援需求「進度更新與通知方式」→ 影響功能「訂單狀態即時更新 + 通知」

步驟 6：更新因果鏈追蹤表

是什麼：在設計因果鏈追蹤表新增 Blueprint 相關的決策列。

為什麼：

每個後台決策都要能回溯到上游 CJM 和角色的工作事項

追蹤表讓學生不會忘記「為什麼做這個決策」

做什麼：新增 Blueprint 相關的決策到追蹤表。

怎麼做：

每個後台行為 → 記錄「依據：角色的工作事項」

每個支援系統 → 記錄「依據：後台行為需求」

每個痛點的下游影響 → 記錄「影響：風格/功能」

支持系統 Persona 回顧與角色對應

| 欄位 | 內容 |
|---|---|
| 姓名 | 陳美玲 |
| 基本資料 | 35 歲，餐飲業 8 年，管理 1 家門市 3 名員工 |
| 使用情境 | 每天 5:30 到店確認備料，尖峰時段調度人力，下午看營收報表 |
| 目標 | 尖峰不漏單、員工快速上手、營收達標 |
| 痛點 | App/現場訂單混淆、人力調度困難、培訓耗時 |
| 期望感受 | 秩序感、安心感、成就感 |
| 不期望感受 | 漏單混亂、尖峰失控 |
| 擔任角色 | 店員/店長——接收訂單、確認訂單、更新進度、收錢交貨、清潔 |

角色—Persona 對應表

在 Blueprint 中，後台行為用角色來標記「誰負責做什麼」。一個人可能兼任多個角色，一個角色也可能由不同人擔任——這本身是設計決策。

重要觀念：不是所有角色都是人。在服務設計中，會與顧客產生互動的設施（如取餐櫃、店內看板）也是「角色」——它們在服務中執行動作、產生互動。這些設施角色不是 Persona（Persona 是人的原型），但在 Blueprint 中用同樣的「角色+動作」格式描述。

| 角色類型 | 角色 | 職責 | 由誰/什麼擔任 | 備註 |
|---|---|---|---|---|
| 人力角色 | 店員/店長 | 接收訂單、確認訂單、更新進度、收錢、交貨、清潔 | 陳美玲 | 支持系統 Persona |
| 人力角色 | 廚師 | 製作餐點、回報製作進度 | 王建興（老闆兼任）或專任廚師 | 初期老闆兼，穩定後另聘——這是老闆的決策 |
| 人力角色 | 老闆 | 決定菜單、管理庫存、看營收、做決策 | 王建興 | 老闆 Persona |
| 設施角色 | 取餐櫃 | 通知客戶取餐號碼 | 實體設施 | 非Persona，但會與顧客產生互動 |
| 設施角色 | 店內看板 | 顯示取餐號碼、訂單進度 | 實體設施 | 非Persona，但會與顧客產生互動 |

角色類型說明：

人力角色：由人擔任，對應到 Persona。一個人可能兼任多個角色（如老闆兼廚師）。

設施角色：由實體設施擔任，不是 Persona，但在服務中執行動作、與顧客互動。取餐櫃「通知」客戶、看板「顯示」資訊——這些都是服務行為，不是被動的設備。

關鍵設計決策：

廚師角色由誰擔任，是老闆的決策——初期自己兼，穩定後另聘。

取餐櫃和店內看板用什麼方式實現（電子看板/號碼牌/人工喊號），是解決方案階段的事。

這些都是「服務設計師為老闆思考解決方案」的一部分。

改進案例：Blueprint 描述的演進

以下展示 Blueprint 後台行為描述如何從初學者寫法逐步改進到最終版本。這個演進過程本身就是很好的學習教材。

| 版本 | 描述 | 問題 |
|---|---|---|
| v1 系統導向 | 系統接收訂單排入佇列 | 用工程用語；預設了系統做 |
| v2 服務導向（無角色） | 接收訂單並安排製作順序 | 沒有標角色——誰接收？ |
| v3 加角色（括號） | （店員）接收訂單；（店員）通知廚房 | 角色在括號裡像附註；通知廚房是地方不是角色 |
| v4 角色為主詞 | 店員接收訂單；店員通知廚師 | 角色是動作主詞；通知對象是角色不是地方 |
| v5 完整互動 | 店員接收訂單；店員通知廚師；廚師製作餐點；廚師回報進度給店員；店員更新進度 | 補上角色間的 handoff——完整說明「誰做什麼」 |

改進了什麼：

v1→v2：從工程用語改為業務用語（系統→服務行為）

v2→v3：加上角色標記（誰做什麼）

v3→v4：角色從括號附註變成動作主詞；通知對象從地方改為角色（廚房→廚師）

v4→v5：補上角色間的 handoff（廚師回報進度給店員→店員才能更新進度）

設施角色的改進案例：

| 版本 | 描述 | 問題 |
|---|---|---|
| v1 | 取餐櫃叫號 | 可以，但沒有說明動作對象 |
| v2 | 取餐櫃通知客戶取餐號碼 | 更好——角色+動作+對象完整 |

記住：取餐櫃不是 Persona，但它是服務中的角色——它執行動作、與顧客互動。在 Blueprint 中用同樣的「角色+動作」格式描述。

Blueprint 表格

注意：以下表格的描述方式是服務行為導向——前台描述顧客的體驗，後台描述「需要做什麼」（不是「系統做什麼」），支援需求描述「需要什麼支撐」。由誰做、用什麼方式做，是解決方案階段的事。

| 階段 | 前台行為（顧客經歷什麼） | 後台行為（誰做什麼） | 支援需求（需要什麼支撐） |

| 等待取餐 | 顧客查看訂單進度；顧客看到取餐號碼 | 廚師製作餐點；廚師回報製作進度給店員；店員更新進度狀態；店員通知顧客進度 | 製作流程與順序管理；進度通知方式（人工/系統）；取餐號碼顯示方式（電子看板/號碼牌） |
| 取餐 | 顧客聽到取餐叫號；顧客領取餐點 | 廚師完成餐點；店員放置餐點至取餐處；店員收錢；店員標記訂單完成 | 取餐動線與空間設計；訂單完成標記方式（人工/系統）；收款方式 |
| 用餐 | 顧客用餐；顧客離開 | 店員維護環境清潔；老闆記錄銷售資料 | 清潔流程（人工 SOP）；銷售記錄方式（POS/紙本） |

解決方案思考：服務設計師為老闆提案

Blueprint 定義了「需要什麼」，接下來服務設計師為老闆（王建興）思考「怎麼做到」。以下是針對所有服務需求的選項分析——本週只列選項和分析，不做最終定案。第 5 週老闆會根據這些選項做出決定。

| # | 服務需求 | 選項 | 分析 | 建議方向 |
|---|---|---|---|---|
| 1 | 訂單接收方式 | A.數位點餐為主　B.現場口頭為主　C.混合並重 | A：符合數位化目標50%+，但初期顧客不熟悉需推廣；B：顧客熟悉但無法達成老闆目標；C：折衷但管理複雜 | A（數位為主，保留現場輔助） |
| 2 | 廚房接收訂單方式 | A.廚房顯示器(KDS)　B.紙本訂單　C.口頭叫號 | A：即時排序、計時提醒、不漏單，但需購設備(1-2萬)；B：成本低但尖峰易漏單；C：零成本但無法排序 | A（KDS，停電時用B備案） |
| 3 | 進度更新與通知方式 | A.數位推播+店內看板　B.店員喊號　C.僅店內看板 | A：通勤路上也能看進度，直接解決CJM最低點；B：零成本但通勤中無法收到；C：到店才看到，通勤中仍焦慮 | A（推播+看板） |
| 4 | 取餐號碼顯示 | A.店內電子看板(大字體)　B.紙本號碼牌 | A：解決「號碼字太小」痛點，大字體遠處可見；B：成本低但字小、不醒目 | A（電子看板） |
| 5 | 支付方式 | A.線上支付為主+現場付現　B.僅現場付現 | A：數位化記錄支援數據驅動，降低排隊，但有手續費1.5-2%；B：無手續費但無數位記錄、尖峰排隊 | A（線上為主，保留付現） |
| 6 | 菜單資訊維護 | A.數位菜單系統　B.紙本菜單定期更換 | A：即時同步供應狀態，避免點了沒有；B：成本低但更新慢、缺貨無法即時反映 | A（數位菜單） |
| 7 | 銷售記錄方式 | A.POS系統　B.紙本記帳 | A：自動記錄客單價、品項銷量，支援展店決策，但有月費/買斷成本；B：零成本但無法分析、易遺失 | A（POS系統） |
| 8 | 庫存盤點方式 | A.系統自動(與POS整合)　B.人工每日盤點　C.初期人工後半自動 | A：精確即時但需POS穩定+設定食譜配方；B：成本低但精確度依賴人工；C：先B建立基線，POS穩定後升級A | C（分階段：先人工後半自動） |
| 9 | 環境清潔流程 | A.數位排程系統　B.人工SOP | A：自動提醒但清潔是人工行為，數位化效益低；B：SOP確保一致性，省下系統成本投入更有價值的數位化 | B（人工SOP） |
| 10 | 顧客經營與會員系統 | A.數位會員系統　B.暫不導入(用POS記錄) | A：累積顧客資料、支援回訪率和個人化，但初期1店效益未現；B：先用POS記錄顧客資料，展店前再導入 | B（初期暫不導入，展店前再建） |
| 11 | 經營數據分析 | A.POS報表(手動查看)　B.暫不導入(靠POS基本報表) | A：老闆可自行解讀日報週報，初期數據量小足夠；B：同A，但可能錯過早期趨勢 | A（POS報表，數據累積後再升級） |

服務設計師的提案邏輯：

不是「全部數位化」，而是「哪些數位化能帶來最大體驗提升和營運效率，哪些用人工流程就夠了」

顧客接觸點（前台）優先數位化——因為直接影響體驗感受

內部營運（後台）按 ROI 決定——高頻高痛點的先數位化，低頻低痛點的用人工

老闆 Persona 的目標和資源限制是最終決策依據

以上是服務設計師的建議方向，不是最終定案——第 5 週老闆會根據成本、風險、資源做最終決定，並記錄理由和代價

這就是服務設計師展現價值的地方：不只是畫出 Blueprint，更是從 Blueprint 中看出「哪些地方值得投資數位化，哪些地方人工就好」，然後為老闆做出有依據的提案。

## 五、AI 協作：用 AI 推導後台行為

AI Prompt 範例

你是一位服務設計師。請根據以下 CJM 和 Persona（用於拆分角色），推導 Service Blueprint 的後台行為和支援需求。

【CJM 接觸點（前台行為）】
階段：決定 / 下單 / 等待取餐 / 取餐 / 用餐
前台行為：顧客查看菜單 / 顧客提交訂單 / 顧客查看進度 / 顧客聽到叫號 / 顧客用餐

【支持系統 Persona】
姓名：陳美玲
職位：門店店長
工作內容：確認備料、調度人力、看營收報表
痛點：App/現場訂單混淆、人力調度困難、培訓耗時
目標：尖峰不漏單、員工快速上手、營收達標

【CJM 最低點】
等待取餐（情緒 -2）：不知道訂單進度，感到焦慮
機會：即時進度通知 + 預計完成時間

【要求】
1. 為每個前台行為，推導 1-3 個後台行為
2. 為每個後台行為，列出所需的支援系統
3. 標出可見線和內部互動線的位置
4. 為 CJM 最低點的機會，找出需要的後台行為和支援系統
5. 標記每個機會的下游影響（風格/功能）

人工修正重點

後台行為是否完整：AI 可能漏掉關鍵的後台步驟（例如：忘記「支付閘道」）

前台後台對應是否正確：AI 可能把後台行為放錯階段

支援系統是否具體：AI 可能寫「系統」而非具體的「訂單管理系統」

可見線位置是否合理：AI 可能把顧客看得到的行為放到後台

痛點連結是否到位：AI 可能只列後台行為，不連結到下游影響

## 六、課堂流程：180 分鐘

## 九、本週核心一句話

CJM 告訴你顧客在哪裡痛苦，Blueprint 告訴你後台要怎麼解決。

只設計前台、不設計後台，等於蓋了一棟漂亮的房子但沒有水管和電線——外面看得到的部分很美，但一住進去就什麼都不能用。Service Blueprint 就是把前台體驗和後台營運連起來，讓設計不只是好看，還能運作。
