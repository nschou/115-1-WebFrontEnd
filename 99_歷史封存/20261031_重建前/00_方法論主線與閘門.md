## 三、輸入—產出契約審計（2026-10-30）

這次流程修正先逐站檢查三件事：前站是否真的產出本階段需要的證據、證據是否足以支撐本階段的決策、階段結束時是否有可交接的明確產出。不是把文件順序調漂亮，而是確認每條箭頭都有依據。

| 階段 | 前站證據為什麼足夠 | 本階段作法 | 本階段產出為什麼能交給下一站 |
|---|---|---|---|
| W1 課程定位 | 題目、服務情境、設計因果鏈與週次契約先定義問題空間；W1 不假裝已經有市場證據 | 先說明輸入／活動／產出／閘門，建立追蹤表 | W2 有明確題目、問題假設與要驗證的商業問題，不會直接跳到畫面 |
| W2 市場與 Persona | W1 的問題假設提供驗證對象；行業資料與角色結構提供供給側與需求側證據 | 先驗證市場與老闆投入意願，再選細分市場，最後拆出三層 Persona | W3 能知道誰的哪段旅程要被描寫、誰會在後台支持服務、各角色有哪些目標與痛點 |
| W3 CJM | W2 的顧客使用情境、目標、痛點與期望感受已足以建立時間軸 | 依顧客旅程寫階段、接觸點、情緒、痛點與機會，標出數位接觸點 | W4 能把每個前台接觸點向下追問「背後需要做什麼」，不會憑空發明後台 |
| W4 Blueprint 選項版 | W3 的接觸點、痛點、機會，加上 W2 的支持系統 Persona，足以拆出前台／後台／支援與服務方案候選 | 標記角色任務、交接、失敗點、支援需求與多個可行方案；不在本週選定方案 | W5 得到「要解決什麼」與「有哪些選項」，但仍不能直接餵給 Design／UX；必須先經決策定案 |
| W5 決策與 Blueprint baseline | W4 的方案選項，加上 W3–W4 痛點／服務承諾、W5 物件／資訊流約束，足以比較方案 | 逐項完成 SD-01–SD-11：採用方案、理由、代價／限制；再把 baseline-draft 與 `05_decisions.md` 整併成 `service-design-baseline.md`（Blueprint baseline） | 後續拿到的是已凍結的服務設計輸入，不再帶著 A／B／C 開放選項進入 Design、UX 或 spec |
| W5 Design | `service-design-baseline.md` 已定案的角色配置、服務承諾、決策、物件、資訊流與例外 | 依 baseline 產出 `DESIGN.md`、tokens 與遠距規格，並保留每項視覺決定的回溯 | W6 同時取得已定案的業務基線、物件／時效／狀態與視覺約束，不會用未定案選項畫 UX |
| W6 服務需求到原型 | baseline 提供「已選哪個服務方案」；W3 痛點提供「為什麼」；W4 任務提供「誰做什麼」；W5 Design 提供「如何呈現的限制」 | 先整合服務需求並寫 US-B；再推導元素、資訊規格、狀態、線框；最後寫 US-I、AC 並做走查 | W7 收到的是已定案且帶來源、狀態、例外與驗收的完整業務證據 |

### 審計結論

1. **Blueprint 先產生選項版**：W4 的 `04_blueprint.md` 描述服務問題、角色任務、交接與候選方案；此時不能直接當成已定案需求。
2. **11 項決策是必要的定案閘門**：W5 必須從 Blueprint 選項逐項選定 SD-01–SD-11，記錄採用、理由、代價與限制。
3. **`service-design-baseline.md` 是 Blueprint baseline**：它由 baseline-draft 與 `05_decisions.md` 整併而成，是後續 Design、UX、spec 的凍結服務輸入；不能帶著 A／B／C 開放選項往下游走。
4. **User Story 需要兩個時間點**：US-B 必須在 UX 之前，讓 UX 有需求側的價值目標；US-I 必須在線框與狀態完成後，讓故事有實際路徑與驗收依據。
5. **角色任務不能被 User Story 取代**：角色任務保留供給側的分工、交接與設施角色；它是服務完整性的檢查來源。
6. **`spec.md` 必須最後彙整**：資料／資訊、Wireframe、US、AC 與 baseline 都要先在各自階段產出；W7 不重新做決策或 UX。

## 四、溯源鏈：同一條線走到底

這條線要能從「顧客的一句話」追到「一個 CSS 變數」。追得通，設計就有依據；追不通，就是憑感覺。


```
CJM 痛點「不知道要等多久」（情緒 −2）
   ↓
Blueprint 交接：店員確認備妥 → 顧客可見
   ↓
OBJ-02 訂單（狀態 S5 完成待確認 → S6 可取餐）
   ↓
INFO-04 顧客需要知道：能不能取（而不是「廚師做完沒」）
   ↓
動態原型：廣播型 · 四端 · ≤1 秒
   ↓
SD-04 取餐號碼顯示（受「號碼一次性」「距離 4 公尺」約束）
   ↓
SCR-05 訂單狀態（ST：default／error／success）
   ↓
AC-12 廚師標記完成時，仍顯示製作中、不得通知顧客
   ↓
MSG-23「完成（等待店員確認）」／ 禁止寫「可取餐」
   ↓
token --dsp-number: 96px ／ --color-success
```

> 這條線上的每一格，學生都要能指著說「它從哪裡來」。這就叫**可查帳**。

## 六、閘門沒過要退回哪

| 失敗現象 | 通常退到 | 為什麼 |
|---|---|---|
| Blueprint 沒有足夠方案選項 | **S3／S4** | CJM 痛點／機會或角色任務不足，不能直接進 11 項決策 |
| 11 項決策選不出來 | **S4／S5／S6／S7** | 方案、物件、資訊流或成本／限制依據不足；不能先做 baseline |
| baseline 仍含 A／B／C 開放選項 | **S7** | `service-design-baseline.md` 必須是凍結的服務輸入 |
| US-B 寫不出來或沒有價值 | **S3／S4／S7／S9** | 先回看 CJM 痛點、角色交接與已定案服務，再重做服務需求整合 |
| 任務句沒有狀態或 B 不知道什麼 | **S4／S5** | Blueprint 沒寫清楚交接，或物件沒有提供決策依據 |
| 線框不知道放什麼 | **S9／S5／S6** | 先查服務需求、角色×物件×需求與資訊流，不在畫面上猜 |
| AC 寫不出來 | **S10 的狀態表／S4 的業務規則** | AC 來自狀態與例外，不是從畫面外觀猜 |
| US-I 路徑走不通 | **S10 的任務流／元素去處** | 操作元素沒有終點或狀態轉換不完整 |
| 決策講不出理由 | **S4／S5／S6／S7** | 缺 Blueprint 選項、物件、資訊流或上游痛點依據 |
| DESIGN.md 回溯不到 | **S7 Blueprint baseline** | 視覺決定沒有服務或商業依據 |
| spec 出現技術名 | **S12 自己** | 寫錯層；技術手段移到 plan，不需回退上游 |

## 七、五個最常迷路的地方

**Q1：這個東西要不要算物件？**
四條判準全過才列：跨角色、影響決策、有生命週期、可持有／傳遞／更新。
只給一個角色用的，是**欄位**，不是物件。

**Q2：AC 從哪裡來？**
從**狀態表與業務規則**來：一個狀態／例外 → 一條 AC。禁止型的 AC 來自業務規則（例：廚師完成 ≠ 可取餐）。
不要從「畫面」想 AC，畫面是結果，不是來源。

**Q3：User Story 何時寫？**
先在 S9 寫 **US-B**，確認角色任務與 CJM 痛點形成有價值的需求；完成資訊規格、狀態與線框後，在 S11 寫 **US-I**，補上路徑與 AC。

**Q4：先寫 AC 還是先畫線框？**
順序是：**US-B → 任務／元素／狀態 → 線框 → US-I ＋ AC**。
AC 需要狀態與例外，但不能等到 spec 才第一次思考；線框也不能脫離 US-B 自由發明。

**Q5：Blueprint 的選項什麼時候才算定案？**
W4 `04_blueprint.md` 是選項版；W5 用 `05_decisions.md` 逐項完成 11 個決策，再整併成 `service-design-baseline.md`。只有 baseline 通過 G5，才可餵給 DESIGN、UX 或 spec。
