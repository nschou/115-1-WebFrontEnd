# 課程綱要：第 2–16 週

> 雲端早餐店訂餐管理系統 — AI 協作前端產品開發  
> 每週 3 小時；每週產出可被下一週直接引用的文件、決策或可驗證原型。

---

## 全課程的技術與服務設計分層

| 層次 | 週次 | 主題 |
|---|---|---|
| 01 服務與問題理解 | 2–4 | 市場／Persona、CJM、服務藍圖 |
| 02 需求與介面契約 | 5–7 | 物件／資訊流／Design、UX、spec |
| 03 前端基礎落地 | 8–10 | HTML／CSS／JavaScript |
| 04 元件化與框架 | 11–13 | React、設計系統、元件化 |
| 05 整合驗證與交付 | 14–16 | API、部署、驗收、發表 |

> 第 1 週的完整課程地圖在 `第01週_課程大綱.md`；本檔補充第 2–16 週的執行契約。

---

## 共同規則：每週先驗輸入，再交付輸出

每週都回答四個問題：

1. **輸入是什麼？** 必須指向上一週的檔案、表格或已鎖定決策。
2. **本週怎麼推導？** 說明整理、轉譯、設計或實作的方法。
3. **輸出是什麼？** 必須有檔名／格式與完成判準。
4. **下一週為什麼能用？** 說明輸出如何成為下一階段的輸入；不夠就退回補證據。

---

## 第 2 週：市場、角色與 Persona

**輸入**：第 1 週問題定義、服務情境與研究問題。  
**方法**：市場三層分析、角色盤點、訪談／觀察資料整理、Persona 假設與證據標註。  
**輸出**：

- `01_market.md`：市場、細分選擇與理由。
- `02_persona.md`：顧客、店員、廚師、老闆／支持系統的目標、任務、痛點與限制。
- 研究問題與假設清單。

**驗收**：每個角色都有可觀察任務與痛點；每個選擇有資料或明確假設；不先寫頁面功能。  
**交給 W3**：角色、情境、痛點是 CJM 的節點與情緒／資訊需求來源。

---

## 第 3 週：CJM（顧客旅程地圖）

**輸入**：W2 的市場／Persona、研究問題與服務情境。  
**方法**：依時間軸整理階段、行動、接觸點、想法／情緒、痛點、機會、物件與資訊需求。  
**輸出**：

- `03_cjm.md`：至少一條完整主旅程。
- 痛點／機會清單：含角色、階段、證據、嚴重度與可觀察結果。
- 物件與資訊候選。

**驗收**：每個主要階段至少一個痛點或機會；情緒曲線與角色行動一致；每個機會可回指 Persona。  
**交給 W4**：痛點／機會成為 Blueprint 要補足的服務結果、交接與失敗點；不直接跳成 User Story。

---

## 第 4 週：Service Blueprint（選項版）

**輸入**：W3 CJM、痛點／機會、物件／資訊候選；W2 Persona 作角色核對。  
**方法**：沿旅程拆前台／後台／支援、角色任務、交接與失敗點；每個服務需求列出數位／人工／實體／混合候選方案，但不在本週定案。  
**輸出**：

- `04_blueprint.md`：角色任務、交接、失敗點、支援需求與方案選項。
- 物件、狀態與資訊流候選。
- 方案選項與 CJM 痛點／機會的對照。

**驗收**：每個 CJM 痛點有服務行為或缺口；每個交接有接收者；每個服務需求有候選方案；設施標明服務／替代誰。  
**交給 W5**：W5 以這份選項版進行 11 項決策；它尚不是 Design／UX 的凍結輸入。

---

## 第 5 週：物件、資訊流、11 項決策與 Blueprint baseline

**輸入**：W4 Blueprint 選項版、W3–W4 Persona／CJM／痛點／服務承諾。  
**方法**：

1. 先建立物件與資訊流，補足各方案的資料、時效與限制。
2. 逐項完成 `05_decisions.md` 的 SD-01–SD-11：採用方案、理由、代價／限制。
3. 將 baseline-draft 與 `05_decisions.md` 整併為 `service-design-baseline.md`，形成凍結的 Blueprint baseline。
4. 只從 baseline 推導 `DESIGN.md`、`tokens.css` 與遠距規格。

**輸出**：

- `05_decisions.md`：11 項決策定案。
- `service-design-baseline.md`：市場、Persona、CJM、Blueprint、角色配置與服務方案決定版。
- `06_objects.md`、`07_infoflow.md`、`08_DESIGN.md`、`09_tokens.css`。

**驗收**：11／11 有採用方案、理由、代價；開放選項 0；baseline 可回指 W4 選項與 W3–W5 依據。  
**交給 W6**：W6 必須使用已定案 baseline，不可直接從 W4 的 A／B／C 選項畫 UX。

---

## 第 6 週：UX 設計——從服務需求到 SCR

**輸入**：W3 CJM 痛點／機會、W4 Blueprint 任務／交接、W5 `service-design-baseline.md`、物件／資訊流／DESIGN。  
**方法與順序**：

1. 建立服務需求索引：角色任務＋交接＋物件／狀態＋CJM 痛點／機會。
2. 寫 **US-B**：業務價值意圖，不含頁面、按鈕或技術。
3. 從任務句、物件屬性與資訊流推導元素、端別、任務流與狀態。
4. 依決策順序畫 Wireframe，補六態、文案與互動，形成 SCR。
5. 線框與狀態定案後寫 **US-I**（實際 SCR 路徑）與 **AC**（狀態／例外／規則）。
6. 跑規則層與體驗層走查，留下交接證據。

**輸出**：

- `10_tasks.md`：服務需求索引＋US-B＋任務句七格。
- `11_elements.md`：資訊元素 11 欄。
- `12_UX.md`、`13_wireframes/`：任務流、狀態、文案、SCR。
- `14_stories.md`：US-B／US-I／AC。
- `15_review.md`：自動檢查、負向測試、體驗走查。

**驗收**：US-B 有來源且無畫面詞；每個元素有用途／來源／去處；每個例外有狀態；US-I 指回 US-B；AC 指回狀態或規則。  
**交給 W7**：W7 只彙整 `10_tasks` 至 `15_review`，不在 `spec.md` 首次發明需求或畫面。

---

## 第 7 週：spec.md——業務需求彙整與鎖定

**輸入**：W2–W6 全部已驗收產出，尤其 W6 `10_tasks`–`15_review`。  
**方法**：去重、補來源、建立需求—痛點—任務—US-B—US-I—AC—SCR 追溯矩陣；將證據重排成業主、設計、驗收都能讀的十章業務規格。  
**輸出**：

- `16_spec.md`：範圍、角色／任務、需求、資料／資訊、流程／狀態、介面行為、驗收、優先級、風險與追溯。
- 需求來源與交叉審計紀錄。
- `spec.md`／`plan.md` 分界決策。

**驗收**：每條需求有來源、理由、US-B／US-I（若為介面需求）、AC 與 SCR；不出現資料庫、框架、API 等技術方案。  
**交給 W8+**：工程計畫只能從已鎖定的 spec 產生，不可反向改寫業務意圖。

## 第 8 週：HTML 語意化與頁面結構

**輸入**：W7 `16_spec.md` 的範圍、SCR、狀態與驗收；W5 `DESIGN.md`。  
**方法**：把已鎖定的介面行為落成語意 HTML 與可讀 DOM；不新增未經 spec 的需求。  
**輸出**：顧客端首頁／菜單頁 HTML、DOM 結構說明、需求到元素的對照。  
**驗收**：語意標籤、可達性與 DESIGN 結構一致；Live Preview 正常。

---

## 第 9 週：CSS 版面與 RWD

**輸入**：W8 HTML、W5 `DESIGN.md`／`tokens.css`、W6 Wireframe 與遠距顯示約束。  
**方法**：盒模型、Flex／Grid、手機優先與斷點；只使用已鎖定 token。  
**輸出**：首頁／菜單頁 CSS、手機／桌面版、規格與實作對照表。  
**驗收**：視覺 token、版面順序、RWD、可讀性與線框一致。

## 第 10 週：JavaScript 互動基礎

**輸入**：W8–9 頁面、W6 狀態／互動／AC、W7 spec。  
**方法**：事件、DOM、狀態與表單驗證；逐條實作 AC，保留錯誤與成功狀態。  
**輸出**：購物車、金額計算、送單、表單驗證與 AI 修改紀錄。  
**驗收**：正常流程與主要例外可重現；互動不違反 spec／AC。

## 第 8 週：React 元件化實作

**技術樹層次**：04 元件化與框架管理層（中）

**核心知識點**：
- 元件化第一性原理（重複 → 抽取 → 可重用）
- 把早餐店拆成元件樹
- MenuCard、CartPanel、OrderItem、PrimaryButton
- Props 傳遞資料
- State 管理互動
- 事件處理

**學生流程**：拆解元件 → 實作各元件 → 組合頁面 → 用 Antigravity 代理輔助生成元件骨架

**產出**：
- 至少 5 個可重用 React 元件
- 顧客端首頁用元件組合而成
- 元件 Props / State 文件

**驗收標準**：
- 元件可重用（同元件不同資料能正確顯示）
- Props 類型合理
- State 變更能正確更新畫面
- 元件風格符合 DESIGN.md

---

## 第 9 週：React 路由與跨頁面狀態

**技術樹層次**：04 元件化與框架管理層（中下）

**核心知識點**：
- SPA 第一性原理（不重新載入頁面、前端路由）
- React Router 基礎
- 跨元件狀態管理（Context 或簡單狀態提升）
- 顧客端多頁面 SPA（首頁 → 菜單 → 購物車 → 訂單確認）

**學生流程**：安裝 React Router → 建立多頁面 → 實作頁面切換 → 管理跨頁面狀態（購物車跨頁保留）

**產出**：
- 顧客端 SPA（至少 3 個頁面 + 路由）
- 購物車狀態跨頁保留
- 頁面切換動畫（簡單）

**驗收標準**：
- 頁面切換不重新載入
- 購物車資料跨頁保留
- 路由網址正確（/menu, /cart, /checkout）
- 無障礙：鍵盤可導航

## 第 10 週：設計系統落地與元件庫

**技術樹層次**：04 元件化與框架管理層（下）

**核心知識點**：
- 設計系統第一性原理（一致性 = 規則 + 可重用元件）
- 把 DESIGN.md 落地成 React 元件庫
- CSS Modules / Tailwind / StyleX 概念比較
- 設計 token 變數化（色彩、字體、間距）
- 元件庫的價值（跨頁面一致、易維護）

**學生流程**：把 DESIGN.md 的 token 轉成 CSS 變數 → 建立統一元件庫 → 店員端用同一套元件 → 體驗一致性

**產出**：
- 設計 token 檔（CSS 變數或 JS 物件）
- 統一元件庫（Button、Card、Input、Table）
- 店員端管理頁（用同一套元件）

**驗收標準**：
- 顧客端與店員端視覺一致（同品牌）
- 改一個 token 全站同步更新
- 元件有 props 可自訂
- 店員端資訊密度較高但風格統一

## 第 11 週：API 規格與假資料

**技術樹層次**：06 整合驗證與交付層（上）

**核心知識點**：
- 前後端分離第一性原理（關注點分離、契約）
- REST API 概念（GET / POST / PATCH / DELETE）
- 用 AI 協助生成 API 規格文件
- Mock Server（JSON Server 或簡單 Node）

**學生流程**：用 AI 根據需求文件生成 API 規格 → 建立 Mock Server → 生成假資料 → 測試 API

**產出**：
- API 規格文件（至少 5 個端點）
- Mock Server 運行中
- 假資料 JSON（餐點、訂單）

**驗收標準**：
- API 規格涵蓋顧客端與店員端需求
- Mock Server 可正確回應
- 假資料結構合理
- AI 生成的規格有人工修正

## 第 12 週：前後端串接

**技術樹層次**：06 整合驗證與交付層（中上）

**核心知識點**：
- fetch / axios 第一性原理（HTTP 請求 → 回應 → 狀態更新）
- 載入狀態（loading）、錯誤處理（error）、空狀態（empty）
- 從假後端拉訂單與餐點資料
- 店員端讀取訂單列表、更新訂單狀態
- 非同步處理（async / await）

**學生流程**：串接 Mock Server → 實作載入狀態 → 實作錯誤處理 → 店員端讀取與更新訂單

**產出**：
- 顧客端可送出訂單到 Mock Server
- 店員端可讀取訂單列表、更新狀態
- 載入與錯誤狀態完整

**驗收標準**：
- 訂單能正確送到假後端並被讀取
- 載入中有 loading 狀態
- 網路錯誤有友善提示
- 店員端能更新訂單狀態（備餐中 → 已出餐）

## 第 13 週：效能與品質

**技術樹層次**：06 整合驗證與交付層（中）

**核心知識點**：
- 效能第一性原理（載入時間 = 髩路 + 處理 + 渲染）
- Lighthouse 與 Web Vitals
- 用 AI 生成效能改善清單
- 程式碼重構思維
- 基本測試概念

**學生流程**：跑 Lighthouse → 把報告摘要餵給 AI → AI 生成改善清單 → 實作 2–3 項改善 → 重構重複程式碼

**產出**：
- Lighthouse 報告（改善前後）
- AI 生成的效能改善清單
- 至少 2 項效能改善實作
- 至少 2 項重構

**驗收標準**：
- Lighthouse 分數有提升
- 改善有具體效果（如圖片壓縮、lazy loading）
- 重構後程式碼更可讀
- AI 建議有人工篩選與理由
