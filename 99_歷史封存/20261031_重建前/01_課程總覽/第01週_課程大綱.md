# 第 1 週課程大綱｜從服務問題到可實作規格

> 版本 v2.0 ｜ 2026-10-30  
> 主題：建立整門課的設計因果鏈、輸入／產出契約與回退規則  
> 主專案：雲端早餐店訂餐管理系統

---

## 一、這門課到底在做什麼

這不是「先畫一個網站，再逐週加功能」的課，而是把一個服務問題逐步轉成可驗收、可實作的前端產品。

```text
服務問題
→ 市場與三層 Persona
→ CJM
→ Service Blueprint（選項版）
→ 物件／資訊流
→ 11 項決策定案
→ Blueprint baseline（service-design-baseline.md）
→ DESIGN.md／tokens
→ 服務需求索引＋US-B
→ UX：資訊規格／狀態／線框
→ US-I／AC／可走原型
→ spec.md
→ plan.md
→ 前端實作與驗證
```

**每一站的輸出都必須能成為下一站的輸入。**  
如果下一站只能靠猜，表示上一站的產出不足，應回退補證據，而不是在下游加假設。

## 二、第一週要建立的三個觀念

### 1. 先定義服務，再決定介面

先回答：

- 誰遇到什麼問題？
- 誰提供服務？
- 不同角色如何交接？
- 哪些物件與資訊會改變？
- 哪些規則不能違反？

之後才決定：

- 需要哪些介面？
- 每個角色看什麼？
- 哪些狀態要呈現？
- 用什麼技術實作？

### 2. User Story 不是角色任務的替代品

| 層次 | 回答的問題 | 來源 |
|---|---|---|
| 角色任務 | 誰必須做什麼、交給誰？ | Service Blueprint |
| US-B 業務版 | 誰想達成什麼、為什麼？ | 角色任務＋CJM 痛點／機會 |
| US-I 介面版 | 這個價值如何沿著哪些介面完成？ | US-B＋UX 路徑 |
| AC | 怎樣算完成或不能發生？ | 狀態機＋業務規則＋例外 |

因此 User Story 會出現兩次：

```text
角色任務＋CJM 痛點
→ US-B（UX 之前，確認值得做）
→ 資訊／狀態／線框
→ US-I（UX 之後，確認走得完）
→ AC（確認驗收）
```

### 3. `spec.md` 是彙整與鎖定，不是第一次設計

`spec.md` 可以完整呈現資料／資訊、Wireframe、US、AC 的索引與需求，但這些內容必須先在各自階段產出。

```text
UX 需要 US-B 作為需求目標
AC 需要狀態與例外
線框需要資訊元素與決策順序
spec.md 最後把以上證據整理成業務契約
```

若先把所有內容留到 `spec.md`，會形成「spec 等 UX、UX 又等 spec」的循環。

## 四、W2–W7 的輸入／產出契約

### W2｜市場與三層 Persona

**輸入**：W1 的專案題目、問題假設與商業情境。  
**作法**：

1. 驗證問題是否具有市場情境與具體數字。
2. 分析老闆是否願意投入資源。
3. 選定一個細分市場。
4. 分析付款者、決策者、使用者、受益者。
5. 依角色結構決定哪些支持角色需要完整 Persona。

**產出**：

- `01_market.md`
- 問題／需求假設
- 老闆投入意願分析
- 行業細分與選擇理由
- 三層 Persona：老闆、顧客、支持系統
- Persona 決策表與因果鏈更新

**交給 W3 的理由**：CJM 需要知道旅程主體、使用情境、目標、痛點與期望感受；Blueprint 需要知道哪些支持角色實際參與交付。

### W3｜CJM

**輸入**：W2 的顧客 Persona、支持系統 Persona、商業範圍。  
**作法**：

1. 切出顧客從需求開始到服務結束的階段。
2. 每階段記錄行動、接觸點、情緒、痛點與機會。
3. 標出數位接觸點與情緒最低點。
4. 把痛點轉成可供下游追蹤的機會。

**產出**：

- `03_cjm.md`
- 五階段旅程表
- 情緒曲線
- 每階段至少一個痛點
- 機會清單與數位接觸點清單

**交給 W4 的理由**：Blueprint 的前台行為必須承接 CJM 接觸點；後台行為必須回應 CJM 痛點與機會，不能脫離顧客情境自行發明。

### W4｜Service Blueprint（選項版）

**輸入**：W3 的接觸點、痛點、機會，加上 W2 的支持系統 Persona。  
**作法**：

1. 將顧客接觸點改寫成前台行為。
2. 對每個前台行為追問「背後需要做什麼」。
3. 標記角色任務、handoff、失敗點與支援需求。
4. 對每個服務需求列出數位／人工／實體／混合等候選方案。
5. 保持業務語言，不在此階段選定方案或預設 API、資料庫、框架。

**產出**：

- `04_blueprint.md`：角色任務、交接、失敗點、支援需求與候選方案。
- 前台→後台對應表。
- 物件候選與資訊需求線索。
- 因果鏈更新。

**交給 W5 的理由**：W5 需要同時知道「要解決什麼」與「有哪些方案可選」；Blueprint 選項版不能直接當成 Design 或 UX 的定案輸入。

### W5｜物件、資訊流、11 項決策與 Blueprint baseline

**輸入**：W4 Blueprint 選項版、W3–W4 的 Persona／CJM／痛點／服務承諾。  
**作法**：

1. 從 Blueprint 對象與任務建立物件、角色×物件×需求矩陣。
2. 描述資訊流、變更、傳播、時效與競爭熱點。
3. 以物件／資訊流與 Persona／CJM 約束 11 項服務決策。
4. 逐項填寫 `05_decisions.md`：採用方案、理由、代價與限制。
5. 將 baseline-draft 與 `05_decisions.md` 整併成 `service-design-baseline.md`，凍結為 Blueprint baseline。
6. 只能從已凍結 baseline 推導 `DESIGN.md`、`tokens.css` 與遠距規格。

**產出**：

- `05_decisions.md`：SD-01–SD-11 的 11 項決策定案。
- `service-design-baseline.md`：市場、Persona、CJM、Blueprint、角色配置與服務方案的決定版。
- `12_物件與資訊架構.md`、`14_資訊流與動態需求.md`。
- `DESIGN.md`、`tokens.css`、整併／審計紀錄。

**驗收**：11／11 決策都有採用方案、理由、代價；開放選項 0；baseline 能回指 W4 選項與 W3–W5 依據；Design 不引用未定案方案。

**交給 W6 的理由**：UX 不只需要「誰做什麼」，還需要一份已定案的服務基線，才能避免把 A／B／C 選項直接畫成互相矛盾的介面。

### W6｜服務需求整合與 UX

**輸入**：W3 痛點／機會、W4 角色任務／交接、W5 `service-design-baseline.md`、物件／資訊流／DESIGN。  
**作法**：

1. 先建立服務需求索引，把「角色任務＋CJM 痛點／機會＋交接＋物件」放在同一列。
2. 從索引寫 US-B，確認角色想達成的價值。
3. 將任務句拆成資訊元素與用途。
4. 建立資訊規格、任務流、狀態表與文案。
5. 依資訊與狀態畫線框，組成 SCR 三件套。
6. 再把 US-B 落成有路徑的 US-I，從狀態與業務規則寫 AC。
7. 跑規則層與體驗層走查。

**產出**：

- `10_tasks.md`：服務需求索引、任務句七格、US-B
- `11_elements.md`：資訊元素表
- `12_UX.md`：SCR、任務流、狀態、互動、文案
- `13_wireframes/`：線框與狀態變體
- `14_stories.md`：US-B、US-I、AC
- `15_review.md`：規則層與體驗層證據
- `prototype/`：可走、可查、可驗的原型

**交給 W7 的理由**：W7 不再設計需求，而是將所有已形成的證據整理成同一份業務契約；沒有 US-B→US-I→AC 的鏈，spec 只能變成畫面清單。

### W7｜spec.md

**輸入**：W2–W6 的全部產出。  
**作法**：

1. 依十章骨架摘要，不重寫上游原始文件。
2. 將每條需求連到任務句／物件／決策／US／AC。
3. 檢查各章沒有矛盾、技術名或無法驗收的形容詞。
4. 建立可追溯率與驗收覆蓋率。

**產出**：

- `16_spec.md`
- 需求清單（來源＋驗收）
- 三項指標：技術名 0、可追溯 100%、驗收覆蓋 100%
- 交叉審計紀錄

**交給 W8+ 的理由**：`spec.md` 定義要什麼、為什麼、怎樣算完成；`plan.md` 才能在不重新猜需求的前提下決定用什麼技術實作。

## 五、每站都要問的三個審計問題

| 問題 | 通過判準 |
|---|---|
| 前站真的產出本階段需要的輸入嗎？ | 能指出檔案、欄位與來源，不只說「前面做過」 |
| 輸入充分支持本階段的決策嗎？ | 不需要在本階段憑空補角色、痛點、物件、狀態或價值 |
| 本階段產出真的能被下一站使用嗎？ | 下一站能直接引用、轉換或驗證；若只能猜，回退補產出 |

### 典型回退

| 發現 | 回退 |
|---|---|
| 沒有市場數字，卻要決定客群 | W2 的市場分析 |
| CJM 沒有痛點，Blueprint 不知道要解決什麼 | W3 的 CJM |
| 任務沒有交接或狀態，UX 無法拆元素 | W4 Blueprint／W5 物件與資訊流 |
| US 沒有價值或只是在描述按鈕 | W6 服務需求索引與 US-B |
| AC 沒有狀態依據 | W6 狀態表或 W4 業務規則 |
| spec 需要技術方案才能成立 | 留在 W7 的需求層，將技術移到 plan |

## 七、W1 交件與驗收

| 產出 | 完成標準 |
|---|---|
| 問題假設句 | 能說出誰、什麼問題、發生情境 |
| 課程地圖 | 每週有輸入、活動、產出、下一站用途 |
| 設計因果鏈 | 每個箭頭都能回答「依據是什麼」 |
| 輸入／產出契約 | 能指出 W2–W7 的直接輸入與明確產出 |
| 回退規則 | 至少能判斷市場、CJM、Blueprint、US、AC、spec 的回退位置 |

**W1 的完成不是畫出頁面，而是知道之後每一站要用什麼證據、產出什麼、何時算完成。**
