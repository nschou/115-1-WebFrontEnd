# 第 1 週學生操作指南：建立工作區與證據鏈

> 本手冊的目標不是讓你先做畫面，而是建立一個能從 `01_market.md` 一路追到 `18_spec.md` 的工作區。
> 本週完成後，你應該能說明每個階段需要什麼輸入、產出什麼文件，以及缺資料時應該退回哪一階段。
> 課程中段請回看 `../00_課程中間回顧與思考框架.md`；先檢查證據鏈，再決定是否退回上游，不要直接請 AI 補後段文件。

## 1. 本週位置

```text
W1 方法與工作區
  ↓
W2 01_market.md、02_persona.md
  ↓
W3 03_cjm.md
  ↓
W4 04_blueprint.md（候選方案）
  ↓
W5 05_objects～10_tokens（決策與 Design）
  ↓
W6 11_service-requirements～17_UserStory-I_AC
  ↓
W7 18_spec.md
```

本週不產出 UI、線框、API、資料庫或技術方案。

### 1.1 如何使用這套教材

本課程採「先理解，再產出；先證據，再決定」的學習方式：

1. 先讀本週講義，知道本週要回答的問題。
2. 再讀本操作手冊，依步驟建立文件。
3. 用示範案例對照文件責任與推導方式，不直接複製內容。
4. 完成自己的產出後，執行本週檢查，再交給下一週。

每週都要保留三件事：本週輸入、自己的產出、交給下一週的具體欄位。若不知道某個結論，寫「待確認」並放入未決問題，不要請 AI 直接補成確定答案。

### 1.2 學習時不要跳過的檢查

- 不要從畫面、按鈕、API 或框架開始。
- 不要跳過上游文件直接產生 UX、Prototype 或 `18_spec.md`。
- 不要把示範案例當成作業答案；要重新用自己的服務推導。
- 不要把空白主線檔案當成完成。
- 文件的 ID、狀態、數量或來源不一致時，先修正上游，不要繼續往後堆文件。

課程中段迷路時，回看 `../00_課程中間回顧與思考框架.md`；它用來重新定位證據鏈、學生卡關點、Prototype 整合流程與 SpecKit 銜接，不是另一份主線產出。

## 2. 需要的教材

從本週工具包開啟：

- `00_W01_上課講義.md`
- `00_W01_學生工具包說明.md`
- `98_示範案例/雲端早餐店/`（若教師另提供）

若使用自己的專案，請先決定一個服務，例如早餐店、診所、校園借用、社區物流。服務必須有至少兩種角色互相交接，不能只有單一個人使用的工具。

## 3. Step 1：建立專案工作區

在自己的電腦建立下列目錄。`project-name` 換成你的專案名稱。

```text
project-name/
├── 00_project-brief.md
├── 00_document-index.md
├── 00_open-questions.md
├── 01_market.md
├── 02_persona.md
├── 03_cjm.md
├── 04_blueprint.md
├── 05_objects.md
├── 06_infoflow.md
├── 07_decisions.md
├── 08_service-design-baseline.md
├── 09_DESIGN.md
├── 10_tokens.css
├── 11_service-requirements.md
├── 12_role-tasks.md
├── 13_UserStory-B.md
├── 14_elements.md
├── 15_UX.md
├── 16_wireframes/
├── 17_UserStory-I_AC.md
├── 18_spec.md
├── changelog.md
└── adr/
    └── 000_template.md
```

本週先建立前三個 `00_` 檔案與空目錄；其餘主線檔案可以先建立空白檔，但不可把空白檔誤當成已完成產出。

## 4. Step 2：完成 `00_project-brief.md`

把下列內容複製到檔案，再逐欄填寫：

```markdown
# 專案摘要

## 服務名稱

- [填寫]

## 要改善的服務問題

- 誰在什麼情境遇到什麼問題？
- 問題發生的頻率與嚴重程度是什麼？
- 若不處理，誰承擔代價？

## 初步角色

| 角色           | 目前猜測的責任 | 需要再確認的事 |
| -------------- | -------------- | -------------- |
| 付費／決策者   |                |                |
| 主要使用者     |                |                |
| 交付服務者     |                |                |
| 設施或支援角色 |                |                |

## 專案範圍

- 本課程要研究的服務範圍：
- 明確不處理的範圍：

## 目前假設

- [H-01]
- [H-02]
```

規則：不知道的地方寫「待確認」，不要用想像補成事實。

## 5. Step 3：完成 `00_document-index.md`

建立主線索引。每一列要寫「這一檔回答什麼問題」與「它直接交給誰」。

|  編號 | 文件                            | 本文件回答的問題                | 直接輸入          | 直接交給   |
| ----: | ------------------------------- | ------------------------------- | ----------------- | ---------- |
|    01 | `01_market.md`                  | 選哪個市場、機會與限制？        | 研究資料          | 02         |
|    02 | `02_persona.md`                 | 誰有問題、誰決策、誰交付？      | 01                | 03、04     |
|    03 | `03_cjm.md`                     | 顧客旅程哪裡中斷？              | 02                | 04         |
|    04 | `04_blueprint.md`               | 前台背後誰做什麼？              | 02、03            | 05、06、07 |
|    05 | `05_objects.md`                 | 有哪些跨角色業務物件？          | 04                | 06、07     |
|    06 | `06_infoflow.md`                | 物件如何變更、誰在等？          | 04、05            | 07、08、11 |
|    07 | `07_decisions.md`               | Blueprint 候選採用哪一個？      | 01–06             | 08         |
|    08 | `08_service-design-baseline.md` | 唯一的服務設計基準是什麼？      | 04–07             | 09–18      |
|    09 | `09_DESIGN.md`                  | 視覺與互動契約是什麼？          | 08                | 10、15     |
|    10 | `10_tokens.css`                 | 如何重用設計尺度？              | 09                | 15、16、18 |
| 11–17 | W6 文件                         | 如何把需求變成可走、可驗的 UX？ | 08–10             | 18         |
|    18 | `18_spec.md`                    | 已驗證的業務需求是什麼？        | 08–17、validation | plan／實作 |

````

完成後，用箭頭再畫一次最短主線：

```text
01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10
08 → 11 → 12 → 13 → 14 → 15 → 16 → validation → 17 → 18
````

每一條箭頭旁邊補一句「上游提供了哪個具體欄位」。例如：

```text
03_cjm → 04_blueprint：提供階段、前台行動、接觸點、痛點與機會。
04_blueprint → 05_objects：提供角色任務中的對象欄。
07_decisions → 08_baseline：提供每個 SD 的採用方案、理由與限制。
```

## 6. Step 4：完成 `00_open-questions.md`

## 7. Step 5：建立修改紀錄規則

建立 `changelog.md`：

```markdown
# Changelog

## YYYY-MM-DD

- 建立專案工作區、主線索引與未決問題。
```

建立 `adr/000_template.md`：

```markdown
# ADR-000：標題

- 狀態：提案中／已採用／被取代
- 提出者：
- 決策者：
- 受影響者：
- 背景與證據：
- 考慮過的選項：
- 決定：
- 影響範圍：
- 代價與回滾方式：
- 驗證方式：
```

本週不要求產生正式 ADR，但要知道：若改變文件責任、主線順序、ID 規則或重要決策，之後必須留下 ADR。

## 8. 交件前逐項檢查

- [ ] 專案目錄已建立，檔名遵守主線命名。
- [ ] `00_project-brief.md` 有服務問題、角色、範圍與假設。
- [ ] `00_document-index.md` 有 18 檔主線、直接輸入與直接輸出。
- [ ] 每條主要箭頭都寫了具體交接欄位，不只寫「上一週完成」。
- [ ] `00_open-questions.md` 至少有 3 個未決問題與預定解決週次。
- [ ] 沒有先寫頁面、按鈕、API 或框架。
- [ ] 交件內容不把空白主線檔案宣稱為完成。

## 9. 交給 W2 的輸入

W2 開始前，必須能提供：

1. `00_project-brief.md`：問題假設與初步角色。
2. `00_open-questions.md`：待研究問題。
3. `00_document-index.md`：主線與交接欄位。

若問題假設仍只有「想做一個方便的 App」，先不要進 W2；把它改寫成「誰在什麼情境遇到什麼問題，以及願意付出什麼代價」。
